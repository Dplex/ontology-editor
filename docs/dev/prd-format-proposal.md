# PRD 티켓 형식 제안 — 개발 쪽 AI 가 티켓을 정확하고 적게 읽도록

PM 께 드리는 제안입니다. 판단이 필요한 것은 두 가지입니다: **수용 기준 앞에 AC 번호 붙이기**와 **"검증 (이 repo)"·"메모" 절 정리**.
나머지(티켓에서 ADR·시험·코드로 가는 링크)는 개발 쪽 도구로 해결해서, 티켓에 따로 적어 주실 것은 없습니다(ADR-0048).

## 지금 개발이 티켓 하나를 읽는 방식

개발은 보드 이슈 → 티켓 md 에서 시작합니다. 구현하려면 티켓 밖의 글이 더 필요합니다.

```
이슈 #n ──> 티켓 md(OE-ML-09) ──┬─ depends 의 R11·K5·D10 정의    → 예전: 113KB 문서를 검색 · 지금: 표의 그 줄만(1KB)
                                ├─ 이 티켓을 다룬 ADR             → 예전: ADR 48개를 뒤짐 · 지금: ADR 머리에서 자동으로
                                ├─ 수용 기준마다 재는 시험         → 시험 제목의 [OE-ML-09#4] 태그
                                └─ 코드                           → 코드 주석의 OE-ML-09
```

이 repo 의 지난 AI 작업 세션 83개를 확인했더니, 가장 많이 연 문서가 BIM→DT 문서(`docs/bim-to-dt-ontology.md`, 113KB)였습니다.
티켓의 `depends` 에 적힌 `R11` 하나를 확인하려고 문서 전체를 검색하거나 통째로 읽은 경우가 대부분입니다(검색 113번, 통째로 17번).
이제는 `npm run ctx -- OE-ML-09` 한 번으로 위 네 가지가 같이 나옵니다(6KB). 문서 챗봇의 `docs_ticket` 도 같은 내용을 답합니다.

이 도구는 **티켓 형식이 일정하다는 것**에 기대고 있습니다. 그래서 아래 두 가지를 제안드립니다.

## 제안 1. 수용 기준 앞에 AC 번호

시험은 `[OE-ML-09#4]` 처럼 "티켓 ID#기준 번호" 태그로 수용 기준을 가리킵니다(지금 498개). 이 번호는 **글머리표 순서**로 셉니다.
그래서 기준 하나를 지우거나 사이에 끼우면 뒤 기준의 번호가 하나씩 밀리고, 그 기준을 가리키던 시험·ADR 이 다른 기준을 가리키게 됩니다.
기준 수를 넘는 번호는 테스트가 잡지만, 밀려서 다른 기준을 가리키는 경우는 잡을 수 없습니다.

기준 앞에 번호를 적어 두면 순서와 상관없이 번호가 고정됩니다.

| 지금 | 제안 |
|---|---|
| `- 삭제 확인에서 영향 층과 관련 정보가 표시되고 취소 후 변경이 없다.` | `- **AC1** 삭제 확인에서 영향 층과 관련 정보가 표시되고 취소 후 변경이 없다.` |
| `- 샤프트 삭제 후 내부 배관·연결은 남고 소속만 해제된다.` | `- **AC4** 샤프트 삭제 후 내부 배관·연결은 남고 소속만 해제된다.` |

규칙은 세 가지입니다.

- 새 기준은 그 티켓의 마지막 번호 + 1 로 붙입니다. 사이에 끼울 때도 마찬가지입니다(순서와 번호가 달라도 됩니다).
- 지운 기준의 번호는 다시 쓰지 않고 비워 둡니다(AC1 · AC3 · AC4 처럼).
- 한 티켓에서 붙이면 그 티켓의 기준 전부에 붙입니다. 일부만 붙이면 테스트가 실패합니다.

판단이 필요합니다.

1. **한 번에 전부 붙이기 (개발 권장)** — `node scripts/prd-ac-label.mjs --write` 가 티켓 235개에 지금 순서대로 AC 번호를 붙입니다
   (나머지 15개는 기준이 아직 없는 티켓). 지금 순서 그대로라 이미 단 시험 태그 498개는 그대로 맞습니다 — 250개 티켓 전부로 확인했습니다.
   PM 께서 돌려 PR 로 올려 주시면 됩니다. 이슈 본문은 다음 `npm run board -- --apply` 때 같이 바뀝니다. AC 번호만 붙은 것은
   요구사항 변경으로 치지 않도록 보드 동기화를 고쳐 두어, `modified` 라벨은 붙지 않고 이슈 수정 이력에 "AC 번호 붙임" 한 줄만 남습니다.
2. **고치는 티켓부터 붙이기** — 기준을 고치는 티켓만 그때 붙입니다. 손이 덜 가지만, 고치기 전까지는 지금처럼 순서로 셉니다.
3. **붙이지 않기** — 지금 방식 그대로입니다. 기준을 지우거나 끼울 때 개발이 시험 태그 번호를 다시 맞춥니다
   (어느 시험을 고쳐야 하는지 테스트가 다 찾아 주지는 못합니다).

## 제안 2. "검증 (이 repo)"·"메모" 절 정리

두 절은 원래 개발이 쓰는 절이었는데, 2026-10-07 부터 개발은 PRD 를 고치지 않습니다. 그래서 그 뒤로 시험이 바뀌어도 두 절은 그대로입니다.

- 250개 티켓 중 "검증" 절이 빈 칸(—)인 티켓 176개, 문구가 있는 티켓 74개입니다. "메모" 절은 224개가 빈 칸입니다.
- 예: OE-ML-09 의 검증 절은 "…복원 검증이 필요하다." 인데, 지금은 기준 5개 중 4개에 시험이 붙어 있습니다.
  AI 는 이 문구를 지금 상태로 읽을 수 있습니다.
- 예: OE-UI-14 의 검증 절은 ADR-0013 을 가리키는데, 2026-10-10 에 그 내용이 `docs/dev/ui-notes.md` 로 옮겨져 이 링크는 끊겼습니다.
- 기준마다 어느 시험이 재는지는 `npm run ctx`·`ac-coverage.md` 가 시험 태그에서 매번 새로 뽑습니다.

판단이 필요합니다.

1. **두 절을 틀에서 빼기 (개발 권장)** — 티켓은 관련 티켓 · 요구사항 · 수용 기준 세 절이 됩니다(기획 소유 절만 남음). 검증 결과는
   PR 본문과 `ac-coverage.md` 에 있습니다. 메모에 남길 기획 내용이 있으면 요구사항 절로 옮겨 주시면 됩니다.
2. **절은 두고 내용을 비우기(—)** — 틀은 그대로이고, 낡은 문구만 없앱니다.
3. **그대로 두기** — 개발 쪽 도구는 두 절을 "2026-10-07 이후 고치지 않는 절" 이라고 표시해서 보입니다(지금 그렇게 되어 있습니다).

## 지금처럼 유지해 주시면 되는 것

도구가 기대는 형식입니다. 이미 지켜지고 있고, 앞으로도 이대로면 됩니다.

- **번호는 표의 첫 칸에서 정의합니다.** D·Q·U·P 는 `questions.md`, K·S 는 `PRD_011.md` 부록 표의 첫 칸. 새 번호도 같은 표에 넣어
  주시면 도구가 그 줄을 찾습니다(지금 `depends` 의 번호 162개가 모두 찾아집니다).
- **요구사항에서 언급한 티켓·번호는 `depends` 에도 넣습니다.** `prd.test.ts` 가 확인합니다.
- **다른 티켓을 가리킬 때는 ID 를 그대로 씁니다**(`OE-ML-03의 … 기준을 따른다`). 기준 하나를 가리키실 때는 `OE-ML-03#2` 처럼
  적어 주시면 시험 태그와 같은 꼴이 됩니다.

## 하지 않으셔도 되는 것

- **티켓에 관련 ADR·코드·시험 링크 적기.** ADR 머리의 `tickets`·`criteria`, 시험 제목의 태그에서 개발 도구가 거꾸로 찾습니다.
  티켓에 적으면 같은 정보가 두 곳에 생겨 어긋납니다.
- **번호의 정의를 티켓에 옮겨 적기.** `R11` 만 적어 두시면 도구가 정의된 줄을 찾습니다.

확인 부탁드립니다.
제안 1 은 1번이면 PM 께서 스크립트를 돌린 PR 을 올려 주시면 개발이 시험 태그가 그대로인지 확인하겠습니다. 2·3번이면 개발 쪽 변경은 없습니다.
제안 2 는 1번이면 같은 PR 에서 `prd.test.ts` 의 "절 네 개" 검사를 세 개로 바꾸는 작업을 개발이 함께 진행하겠습니다.
