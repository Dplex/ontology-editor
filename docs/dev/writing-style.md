# 이슈·PR 글 문체

이슈 코멘트·PR 본문처럼 **리뷰하는 사람(PM·다른 개발자)이 읽는 글**에 쓴다. 대화 말투는 CLAUDE.md 의 ELI30 이고, 커밋 메시지는
루트 CLAUDE.md 대로 한 줄 "~한다" 로 쓴다(`git log --oneline` 과 맞춘다). 2026-10-06 검토(#123), 2026-10-07 #340·#44·#45 코멘트,
2026-10-13 #501 본문에서
희록님이 고친 표현을 모았다 — 새로 고친 것이 생기면 규칙은 원칙에, 낱말은 아래 표에 더한다.

## 원칙

0. **전부 존댓말로 쓴다(2026-10-07).** PM 에게 묻는 코멘트만이 아니라 이슈 코멘트·PR 본문 전부다. 사용자 이름으로 올라가는 글이다.
   - 풀어 쓴 문장은 "~습니다"·"~합니다" 로 맺는다. "~한다"·"~다" 로 맺지 않는다.
   - 항목을 나열하는 목록·표 칸은 명사형으로 끝내도 된다("Duplex MEP 167대 중 160대 일치", "아직 열린 이슈", "검증·메모만 채움").
   - **문장 안에서는 명사로 끊지 않는다(2026-10-13 #501).** 서술어가 있는 문장의 끝이나 괄호 안 설명을 명사·조각으로 끝내지 말고,
     무엇을 했는지·왜 했는지까지 서술어로 맺는다.

     | 쓰지 않는 말 | 쓰는 말 |
     |---|---|
     | 틀은 `docs/adr/README.md`. | 틀은 `docs/adr/README.md` 에서 참고할 수 있습니다. |
     | `docs/dev/testing.md` 에 같은 안내. | `docs/dev/testing.md` 에도 같은 안내를 넣어 ctx 를 먼저 읽게 수정했습니다. |
     | (개발은 `--write` 를 돌리지 않음) | (개발은 `--write` 를 돌리지 않겠습니다) |

   | 쓰지 않는 말 | 쓰는 말 |
   |---|---|
   | 칩 숫자를 두 개로 바꿨다. 색은 앞 수치로 정한다. | 칩 숫자를 두 개로 바꿨습니다. 색은 앞 수치로 정합니다. |
   | 티켓 md 를 고쳐 이슈 본문이 어긋난다. `--apply` 는 돌리지 않았다. | 티켓 md 를 고쳐 이슈 본문이 어긋납니다. `--apply` 는 돌리지 않았습니다. |

1. **리뷰하는 사람이 모르는 내부 말을 쓰지 않는다.** 작업하는 쪽만 아는 이름(묶음 X·묶음 A·주말 브랜치·시작점 커밋)은
   PR 번호나 티켓 ID 로 바꾼다. 아직 PR 이 없으면 "다른 PR(OE-EQP-03, 아직 PR 생성 전)" 처럼 티켓으로 가리킨다.
2. **상태·한 일·할 일을 구분해 쓴다.** 상태는 명사형("아직 열린 이슈"), 한 일은 "~에서 진행"·"~완료", 할 일은 "~할 예정".
   "열어 둔다"·"들어갔다"·"맞춘다" 처럼 누가 무엇을 하는지 흐린 말은 피한다.
3. **용어는 현장에서 쓰는 말로.** PRD glossary 와 다른 말을 쓰면 처음 한 번만 괄호로 glossary 용어나 기호(h_c)를 단다.
4. **번호와 화면 이름은 처음 나올 때 풀고 링크를 단다.** `D12`·`PRD 1.8`·`R16` 같은 번호는 그 줄·절로 가는 링크와 "무엇을 정하는
   것인지" 한 줄을, 화면 요소(칩 등)는 "어디에 뜨는 무엇인지" 를 붙인다. #340 은 D12 를 번호만 적어 "먼말인지 모르겠다" 는 말을 들었다.
   - D12 → `[D12](…/docs/prd/questions.md#L18)(PRD 열린 결정: 등급 판정에 사전 채움을 넣을지)`
   - PRD 절은 절 제목 앵커로 건다 → `[PRD 1.8](…/docs/prd/PRD_011.md#18-bim-수용-기준선과-등급)`
5. **숫자는 실제 예시 하나로 읽는 법을 보인다.** `0/27(BIM) → 23/27(사전)` 처럼 분모와 출처를 숫자 옆에 붙이고, "이어진 기기 27대 중
   BIM 포트로 방향을 아는 기기 0대, 규칙으로 추정한 방향까지 넣으면 23대" 처럼 한 번 풀어 쓴다. `0/27 → 23` 만 적으면 뒤 숫자가 무엇인지 모른다.
6. **요약을 맨 위에 두 줄로 두고, 소제목마다 한 가지 내용만 쓴다.** 헷갈리기 쉬운 두 개념(계통 소속 · 계통 종류)은 문단으로 나누지 말고
   표로 비교한다.
7. **정의를 등호로 줄이지 않고 문장으로 쓴다(#45).** `"임포트 IfcSpace = 물리존, 룸 = 수동 편집의 하위 단위"` 처럼 적으면 작성자만 이해할 수 있다.
   언제 무엇이 무엇이 되는지를 서술어로 맺는다 → "BIM 파일을 불러오면 `IfcSpace` 가 물리존이 되며, 룸은 BIM 파일을 불러올 때
   만들어지지 않고 사람이 물리존 안에 직접 그려서 나눈 편집 단위입니다." 숫자가 바뀐 것을 보이는 화살표(원칙 5)는 그대로 쓴다.
8. **비유어 대신 대상의 이름과 상태를 쓴다(#44).** "이웃"·"길"·"품는다"·"갈 곳 없는" 은 무엇을 가리키는지 읽는 사람이 맞혀야 한다.
   "갈 곳 없는 설비" 대신 "배치되지 않은 설비" 처럼 오브젝트 이름과 그 상태로 쓴다(나머지 낱말은 아래 표).
9. **예시가 있어야 이해되는 것은 예시를 넣는다(2026-10-12 #194).** PM 질문만이 아니라 "추가 작업 필요"·"안 되는 것" 코멘트도 같다.
   "형상이 없는 구간에 경로를 그려 넣는 길이 없습니다" 만 적으면 무엇이 없는지 모른다. 실제 객체 하나를 들어 쓴다.
   - 그 객체에 **무엇이 있고 무엇이 없는지**(BIM ID·연결·계통은 있음, 좌표·형상은 없음)
   - 그래서 **어디에 어떻게 남는지**를 출력마다 적는다 — TTL 에는 연결이 있어 나가고, GeoJSON 에는 좌표가 없어 `geometry: null`,
     화면에는 "미반영". 같은 객체가 출력마다 다르게 남는 것이 판단할 사안이다
   - 지금 할 수 있는 것·없는 것과 우회 방법, 그 대가(지우고 새로 그리면 BIM ID 가 바뀜)
   - 얼마나 자주 생기는지(가진 파일 중 어디에 몇 개)
10. **개발 쪽에서 지은 우리말보다 널리 쓰는 용어를 쓴다(2026-10-13 #501).** "머리 칸"·"거꾸로 가리키는 티켓" 처럼 풀어 지은 말은
    무엇을 가리키는지 읽는 사람이 맞혀야 한다. 개발자가 아는 용어(FrontMatter·역참조)가 있으면 그것을 쓴다(아래 표).
    "티켓" 처럼 여러 가지로 읽히는 말은 처음 한 번 "PRD 티켓" 처럼 무엇의 것인지 붙인다.
11. **"추가 작업 필요" 는 항목마다 머리에 상태를 붙인다(2026-10-13 #501).** PR 본문의 마지막 절은 "남은 것" 대신 "추가 작업 필요" 로 쓰고,
    항목마다 소제목 뒤에 상태를 단다 — "반영 완료(#530)"·"수정 예정"·"아직 열린 일"·"보류"·"검토 예정"·"확인 요청".
    merge 뒤에 다시 볼 때 무엇이 끝났고 무엇이 남았는지가 소제목만으로 보인다. 다른 사람(PM)이 할 일이 끝났으면 그 PR 번호를 단다.
12. **아직 `제안` 상태인 결정은 확정처럼 쓰지 않는다(2026-10-13 #501).** ADR 상태가 `제안` 이면 "형식을 정했습니다" 대신
    "형식을 정해 보았습니다" 처럼 쓴다. 확인을 받아야 하는 일임이 문장에서 보인다.
13. **화면 UI에는 내부 포트 번호나 코드 동작 동사를 노출하지 않는다(2026-10-14).** `8084` 같은 포트 번호는 화면에 적지 않고
    `서버`로 쓴다("서버에 저장합니다", "서버에 저장한 편집"). `셉니다`·`잽니다`·`목표에 안 셈`·`잴 수 없음`처럼 코드가 내부에서 계산하는
    동작 대신 `불러옵니다`·`분석 중`·`판정 제외`·`측정 불가`처럼 사용자가 이해하는 상태와 결과로 적는다.
14. **UI 부품·데이터 구조는 억지 순우리말이나 문법 용어로 직역하지 않는다(2026-10-14).** RDF Subject를 `주어`로, 패널(Panel)을
    `판`으로, 카테고리(Category)를 `갈래`로, 수신 시스템을 `받는 쪽`으로 풀어 쓰면 뜻을 다시 추측해야 한다. 각각 `엔티티`·`패널`·`분류`·
    `DT 플랫폼`처럼 현업과 UI에서 널리 쓰는 말을 쓴다.
15. **사물을 의인화하거나 구어체 축약으로 안내하지 않는다(2026-10-14).** `BIM 포트가 말한 방향`·`규칙이 정한 방향`·`찍거나 끄는 점`·
    `넣어야 만듭니다` 대신 `BIM 포트 방향`·`규칙 추정 방향`·`클릭·드래그 지점`·`입력해 주세요`처럼 간결하고 명확한 안내문으로 적는다.

16. **화면 글자와 글에서 지어 낸 순우리말 대신 표준 UI 용어를 쓴다(2026-10-16).** 원칙 14 의 연장이다. `고른 것`·`단추`·`시간줄`·`끌기`
    처럼 풀어 쓴 말은 읽는 사람이 무엇인지 다시 맞혀야 한다. `선택 항목`·`버튼`·`타임라인`·`드래그` 처럼 쓴다(아래 표).
    화면에 보이는 글자(버튼 이름·툴팁·aria-label·안내문)도 같은 말로 맞춘다.

## PM 에게 묻는 코멘트 (`needs-pm`)

#123·#340 코멘트를 희록님이 고친 것에서 가져왔다. 위 원칙에 더해 아래를 지킨다.
**먼저 질문할 사안인지 본다** — PM 만 정할 수 있는 것(구현이 요구사항과 다름 · 기준끼리 어긋남 · PM 이 줄 값이 없음)에만 묻는다.
요구사항대로 이해하고 구현했으면 PR 본문에 "이렇게 이해하고 구현했습니다" 로 적고 끝낸다(`docs/dev/board.md` 의 `needs-pm`).

1. **요청을 지시형으로 쓰지 않는다.** "정해 주기 바란다" 대신, 선택지 중에서 골라 달라면 "판단이 필요합니다", 개발 쪽 안이 하나면
   "~하도록 요청드립니다"(#45). 맺음말 "확인 부탁드립니다." 를 따로 둔다.
2. **결과로 겁주지 말고 판단할 사안으로 묻는다.** "그러면 DT 가 이름을 찾을 수 없게 된다" 대신 "그걸 의도한 건지(우리가 술어 체계를
   관리할 것인지) 판단이 필요합니다". 우리 쪽에서 고를 수 있는 여지가 있으면 그것도 적는다("가져갈 것만 선택해도 될 것 같습니다").
3. **선택지마다 그 결과를 괄호로 단다** — "값은 GeoJSON 으로만 내보낼 예정 (즉, TTL 과 GeoJSON 의 술어 체계가 달라짐.)".
   선택지 제목은 "확인 대상", 권장안은 첫 번째에 "(개발 권장, 지금 구현과 같음)". 결과가 걱정거리면 단정하지 말고 존댓말로 짚는다 —
   "(즉, 한 칩에 뜻이 다른 두 지표가 섞임.)" 대신 "(오해의 소지는 있을 수 있습니다. 소속 / 종류)".
   - **선택지의 괄호에는 사용자가 무엇을 할 수 있게 되는지·없게 되는지를 쓴다(2026-10-12 #119).** 다른 티켓의 정의를 끌어와
     "그 패널은 속성을 표시하는 곳이다" 처럼 쓰면 판단할 사안이 보이지 않는다.
     - "(아무것도 고르지 않았을 때 레이어 패널에 목록이 보입니다.)" 대신 "(외곽선이 없는 물리존은 3D 에서 눌러 고를 수 없습니다.
       레이어 패널에 목록이 있으면 거기서 골라 바로 그릴 수 있습니다.)"
   - **상황이 낯선 질문은 예시 한 장면부터 쓴다.** "다시 받은 BIM 외곽선과 다를 때 알리는 기준" 은 읽히지 않았다. "외곽선이 없던
     회의실을 사람이 그렸는데, 고객사가 BIM 을 고쳐 다시 보내 회의실에 외곽선이 생긴 경우" 처럼 누가 무엇을 했을 때인지 먼저 쓰고,
     지금은 어떻게 되는지를 이어 쓴 뒤 묻는다.
   - **선택지는 PM 이 결과를 구체적으로 예상할 수 있게 구성한다.** "겹치는 넓이가 80% 보다 작으면" 처럼 기준값끼리의 비교는 PM 이 고를
     수 없다. "20% 넘게 다를 때만 알림 / 차이와 상관없이 늘 알림" 처럼 결과가 다른 것끼리 두고, 숫자 기준에는 예(20㎡ · 26㎡)를 붙인다.
   - 권장안이 없으면 "(개발 권장)" 을 억지로 달지 않는다. "(지금 구현과 같음)" 만 단다.
   - **선택지 문장은 "무엇을 받는다·안 받는다" 처럼 짧게, 번역투 없이 쓴다(2026-10-12 #118).** 구현 방법(라이브러리·번들)은
     선택지에 넣지 않고, 괄호에는 사용자가 하는 일만 쓴다.

     | 쓰지 않는 말 | 쓰는 말 |
     |---|---|
     | 이미지만 받고, PDF·DWG 는 이미지로 내보내 쓰게 안내한다 (즉, 도면을 한 번 이미지로 저장하는 손이 듦.) | 이미지만 받고, PDF·DWG 는 이미지로 바꿔서 올리도록 안내한다 (구축 담당자가 도면을 한 번 이미지로 바꿔야 합니다.) |
     | PDF 는 바로 받는다 (PDF 첫 페이지를 이미지로 그려 깝니다. PDF 라이브러리를 번들에 넣습니다.) | PDF 도 받는다 (PDF 는 바로 올릴 수 있습니다.) |
     | PDF·DWG 모두 바로 받는다 (DWG 변환이 필요해 범위가 커집니다.) | PDF·DWG 를 모두 받는다 (받은 파일을 그대로 올릴 수 있습니다. DWG 를 읽으려면 변환 서버가 필요합니다.) |

     "즉,"·"손이 듦"·"그려 깝니다"·"범위가 커집니다" 같은 말은 쓰지 않는다. 무엇이 어떻게 되는지 그대로 쓴다.
4. **우리 쪽 시험·문서 세부는 뺀다.** "1번이면 문서 몇 장을 수정하고 어느 테스트로 검증한다" 는 PM 이 결정할 사안이 아니다. 다만 **선택지마다
   해당 PR 을 어떻게 할지는 맺음말 아래에 적는다** — PM 이 고른 번호가 곧 merge 여부를 정하기 때문이다(#340):
   > 확인 부탁드립니다.
   > 2번인 경우에는 본 PR에 해당 내용 추가 작업 하고,
   > 1번인 경우에는 본 PR Merge,
   > 3번인 경우에도 본 PR은 Merge 하고 새로운 사전 데이터 추가하는 작업으로 신규 작업건으로 진행하겠습니다.
5. **존댓말로 바꾸면서 사실을 흐리지 않는다.** "지금은 내보내지 않는다" 를 "나갈 수 있는 샘플이 없다" 로 쓰면 기능은 있는데
   데이터가 없는 것으로 읽힌다. 우리가 지은 이름(`ex:areaM2`)을 "IFC 에 정의된 그대로" 라고 쓰지 않는다.
6. **안 되는 이유를 쓸 때 되는 것부터 적는다.** "등급 3 에서 안 되는 이유" 아래에 지표 정의만 두면 그 지표 자체가 안 되는 것으로 읽힌다.
   "계통에 묶인 기기 % 는 가능합니다" 를 먼저 쓰고, 안 되는 것(두 번째 숫자)과 그 까닭을 잇는다.
