# 이슈·PR 글 문체

이슈 코멘트·PR 본문처럼 **리뷰하는 사람(PM·다른 개발자)이 읽는 글**에 쓴다. 대화 말투는 CLAUDE.md 의 ELI30 이고, 커밋 메시지는
루트 CLAUDE.md 대로 한 줄 "~한다" 로 쓴다(`git log --oneline` 과 맞춘다). 2026-10-06 검토(#123)와 2026-10-07 #340·#44·#45 코멘트에서
희록님이 고친 표현을 모았다 — 새로 고친 것이 생기면 규칙은 원칙에, 낱말은 아래 표에 더한다.

## 원칙

0. **전부 존댓말로 쓴다(2026-10-07).** PM 에게 묻는 코멘트만이 아니라 이슈 코멘트·PR 본문 전부다. 사용자 이름으로 올라가는 글이다.
   - 풀어 쓴 문장은 "~습니다"·"~합니다" 로 맺는다. "~한다"·"~다" 로 맺지 않는다.
   - 항목을 나열하는 목록·표 칸은 명사형으로 끝내도 된다("Duplex MEP 167대 중 160대 일치", "아직 열린 이슈", "검증·메모만 채움").

   | 쓰지 않는 말 | 쓰는 말 |
   |---|---|
   | 칩 숫자를 두 개로 바꿨다. 색은 앞 수치로 정한다. | 칩 숫자를 두 개로 바꿨습니다. 색은 앞 수치로 정합니다. |
   | 티켓 md 를 고쳐 이슈 본문이 어긋난다. `--apply` 는 돌리지 않았다. | 티켓 md 를 고쳐 이슈 본문이 어긋납니다. `--apply` 는 돌리지 않았습니다. |

1. **리뷰하는 사람이 모르는 내부 말을 쓰지 않는다.** 작업하는 쪽만 아는 이름(묶음 X·묶음 A·주말 브랜치·시작점 커밋)은
   PR 번호나 티켓 ID 로 바꾼다. 아직 PR 이 없으면 "다른 PR(OE-EQP-03, 아직 PR 생성 전)" 처럼 티켓으로 가리킨다.
2. **상태·한 일·할 일을 구분해 쓴다.** 상태는 명사형("아직 열린 이슈"), 한 일은 "~에서 진행"·"~완료", 할 일은 "~할 예정".
   "열어 둔다"·"들어갔다"·"맞춘다" 처럼 누가 무엇을 하는지 흐린 말은 피한다.
3. **용어는 현장에서 쓰는 말로.** PRD glossary 와 다른 말을 쓰면 처음 한 번만 괄호로 glossary 용어나 기호(h_c)를 단다.
4. **번호와 화면 이름은 처음 나올 때 풀고 링크를 단다.** `D12`·`PRD 1.8`·`R16` 같은 번호는 그 줄·절로 가는 링크와 "무엇을 정하는
   것인지" 한 줄을, 화면 요소(칩 등)는 "어디에 뜨는 무엇인지" 를 붙인다. #340 은 D12 를 번호만 적어 "먼말인지 모르겠다" 는 말을 들었다.
   - D12 → `[D12](…/docs/prd/questions.md#L18)(PRD 열린 결정: 등급 판정에 사전 채움을 넣을지)`
   - PRD 절은 절 제목 앵커로 건다 → `[PRD 1.8](…/docs/prd/PRD_011.md#18-bim-수용-기준선과-등급)`
5. **숫자는 실제 예시 하나로 읽는 법을 보인다.** `0/27(BIM) → 23/27(사전)` 처럼 분모와 출처를 숫자 옆에 붙이고, "이어진 기기 27대 중
   BIM 포트로 방향을 아는 기기 0대, 규칙으로 추정한 방향까지 넣으면 23대" 처럼 한 번 풀어 쓴다. `0/27 → 23` 만 적으면 뒤 숫자가 무엇인지 모른다.
6. **요약을 맨 위에 두 줄로 두고, 굵은 머리말마다 한 가지만 쓴다.** 헷갈리기 쉬운 두 개념(계통 소속 · 계통 종류)은 문단으로 가르지 말고
   표로 나란히 둔다.
7. **정의를 등호로 줄이지 않고 문장으로 쓴다(#45).** `"임포트 IfcSpace = 물리존, 룸 = 수동 편집의 하위 단위"` 는 쓴 사람만 읽는다.
   언제 무엇이 무엇이 되는지를 서술어로 맺는다 → "BIM 파일을 불러오면 `IfcSpace` 가 물리존이 되며, 룸은 BIM 파일을 불러올 때
   만들어지지 않고 사람이 물리존 안에 직접 그려서 나눈 편집 단위입니다." 숫자가 바뀐 것을 보이는 화살표(원칙 5)는 그대로 쓴다.
8. **비유어 대신 대상의 이름과 상태를 쓴다(#44).** "이웃"·"길"·"품는다"·"갈 곳 없는" 은 무엇을 가리키는지 읽는 사람이 맞혀야 한다.
   "갈 곳 없는 설비" 대신 "배치되지 않은 설비" 처럼 오브젝트 이름과 그 상태로 쓴다(나머지 낱말은 아래 표).

## PM 에게 묻는 코멘트 (`needs-pm`)

#123·#340 코멘트를 희록님이 고친 것에서 가져왔다. 위 원칙에 더해 아래를 지킨다.

1. **요청을 지시형으로 쓰지 않는다.** "정해 주기 바란다" 대신, 선택지 중에서 골라 달라면 "판단이 필요합니다", 개발 쪽 안이 하나면
   "~하도록 요청드립니다"(#45). 맺음말 "확인 부탁드립니다." 를 따로 둔다.
2. **결과로 겁주지 말고 판단할 거리로 묻는다.** "그러면 DT 가 이름을 찾을 수 없게 된다" 대신 "그걸 의도한 건지(우리가 술어 체계를
   관리할 것인지) 판단이 필요합니다". 우리 쪽에서 고를 수 있는 여지가 있으면 그것도 적는다("가져갈 것만 선택해도 될 것 같습니다").
3. **선택지마다 그 결과를 괄호로 단다** — "값은 GeoJSON 으로만 내보낼 예정 (즉, TTL 과 GeoJSON 의 술어 체계가 달라짐.)".
   선택지 머리는 "확인 대상", 권장안은 첫 번째에 "(개발 권장, 지금 구현과 같음)". 결과가 걱정거리면 단정하지 말고 존댓말로 짚는다 —
   "(즉, 한 칩에 뜻이 다른 두 지표가 섞임.)" 대신 "(오해의 소지는 있을 수 있습니다. 소속 / 종류)".
4. **우리 쪽 시험·문서 세부는 뺀다.** "1번이면 문서 몇 장을 고치고 어느 시험이 지킨다" 는 PM 이 정할 거리가 아니다. 다만 **선택지마다
   걸린 PR 을 어떻게 할지는 맺음말 아래에 적는다** — PM 이 고른 번호가 곧 merge 여부를 정하기 때문이다(#340):
   > 확인 부탁드립니다.
   > 2번인 경우에는 본 PR에 해당 내용 추가 작업 하고,
   > 1번인 경우에는 본 PR Merge,
   > 3번인 경우에도 본 PR은 Merge 하고 새로운 사전 데이터 추가하는 작업으로 신규 작업건으로 진행하겠습니다.
5. **존댓말로 바꾸면서 사실을 흐리지 않는다.** "지금은 내보내지 않는다" 를 "나갈 수 있는 샘플이 없다" 로 쓰면 기능은 있는데
   데이터가 없는 것으로 읽힌다. 우리가 지은 이름(`ex:areaM2`)을 "IFC 에 정의된 그대로" 라고 쓰지 않는다.
6. **안 되는 이유를 쓸 때 되는 것부터 적는다.** "등급 3 에서 안 되는 이유" 아래에 지표 정의만 두면 그 지표 자체가 안 되는 것으로 읽힌다.
   "계통에 묶인 기기 % 는 가능합니다" 를 먼저 쓰고, 안 되는 것(두 번째 숫자)과 그 까닭을 잇는다.

## 이렇게 바꾼다

| 쓰지 않는 말 | 쓰는 말 | 왜 |
|---|---|---|
| 이슈는 열어 둔다 · 닫지 않는다 | 아직 열린 이슈 | 상태를 적는다 |
| #303 으로 들어갔다 | #303 에서 1차 개발을 진행 | 어디서 무엇을 했는지 |
| 묶음 X 가 31종으로 다시 맞춘다 | 다른 PR(OE-EQP-03, 아직 PR 생성 전)을 통해서 31종으로 맞출 예정 | "묶음" 은 내부 말, 앞으로 할 일은 "예정" |
| 지금 구현을 다시 대 봤다 · ~에 대 보고 | 지금 구현된 내용을 비교하면 아래와 같습니다 · ~와 비교해 | "대 보다"·"견주다" 는 입말이라 글에서는 "비교" |
| 반자 · 반자 높이 | 천장고 — 처음 한 번 "천장고(h_c, 천장 마감면 높이)" | 반자는 건축 법규 용어라 낯설다. "천장바닥" 은 천장 속 슬래브로 읽혀 쓰지 않는다 |
| 판본 (건축·설비 판본) | 모델 (건축 모델·설비 모델) | 현장 말(2026-10-05) |
| 판본 비교 | 버전 비교 | 같은 건물의 이전·이후 파일을 비교하는 것 |
| 정본 | BIM→DT 문서(`docs/bim-to-dt-ontology.md`) | 무엇의 정본인지 안 보인다 |
| 품는다 (층이 방을 품는다) | 포함합니다 | 비유 동사 대신 일반 동사 |
| ~로 읽었다 (요구사항을) | ~로 이해하고 구현했습니다 | 해석만이 아니라 그대로 구현까지 했다는 뜻이 보인다 |
| (TTL 에) 나간다 | 포함됩니다 · 내보냅니다 | 입말 |
| 칩 · 등급 꼬리표 | 등급 설명표 — 처음 한 번 "(파일을 열면 검토 화면 맨 위에 뜨는 등급 설명표)" | 칩은 개발 쪽 화면 부품 이름이다(#340) |
| 이름 사전은 기기를 계통에 묶지 않습니다 | 사전(이름 정보)으로 기기를 계통에 묶을 규칙이 없습니다 | 도구를 주어로 세우지 않고 규칙이 있다·없다로 쓴다. "사전" 은 처음 한 번 괄호로 푼다 |
| 임포트 · 임포트 시 | BIM 파일을 불러오면 · 불러올 때 | 동작으로 쓰면 따로 풀지 않아도 읽힌다(#45) |
| 맞닿은 이웃 · 이웃 물리존 | 닿은 물리존 | 비유 대신 오브젝트 이름(#44) |
| 합치기와 같은 길 | 합치기와 같은 방식 | "길" 은 비유(#44) |
| 지운 자리 | 지운 영역 | 공간은 "영역"(#44) |
| 갈 곳 없는 설비 | 배치되지 않은 설비 | 상태를 적는다(#44) |
| 이름은 자유 | 이름은 중복 허용 | "자유" 는 무엇이 자유로운지 안 보인다(#44) |
| 거의 안 겹친다 · 못 찾으면 | 거의 겹치지 않습니다 · 찾을 수 없으면 | 짧은 부정 대신 긴 부정(#44) |
| 이미 막혀 있다 | 이미 반영되어 있습니다 | 막는 동작이 요구사항대로 들어가 있다는 뜻이 보인다(#44) |
| 잇기 · 끊기 · 이은 연결 | 연결하기 · 연결 끊기 · 만든 연결 | 화면 버튼과 같은 말(2026-10-07). PRD 문구(OE-PIP-01 제목 등)는 PM 이 고친다 |

PRD(`docs/prd/`)의 문구는 PM 몫이라 이 표로 고치지 않는다 — glossary 는 아직 "반자(h_c)"·"판본" 이다. 코드의 테스트 이름도 그대로 둔다.
