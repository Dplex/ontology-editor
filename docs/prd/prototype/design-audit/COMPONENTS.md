2. **포커스 표시는 브라우저 기본이다.** 라이트에서도 색이 거의 검정 1px 이라 약하고, 다크에서도 같은 `rgb(16,16,16)` 라 어두운 면 위에서는 거의 안 보인다(작은 사진으로 확인: 다크 툴바 알약의 포커스 고리가 배경과 구분이 약함). WCAG 2.2 의 포커스 표시 기준(대비 3:1)을 시스템이 책임져야 한다.
3. **호버가 없는 단추가 많다.** 모드 스위치·접기 머리·진단 칩은 눌러도 되는지 알리는 단서가 호버에 없다.
4. 호버의 방향도 두 가지다: 툴바 알약은 accent 로, 사이드 탭은 진한 글자+선으로, 독은 흰색 10% 로.

## 비활성

| 모양 | 어디 | 비고 |
|---|---|---|
| `opacity 0.45` + `cursor: not-allowed` | `.ghost`(FBX·구축하기), 이름이 같은 계열 | 가장 흔한 규칙 |
| `opacity 0.42` | 하단 독 알약(고른 것 F) | 0.45 와 0.42 — 같은 의미에 두 값 |
| **브라우저 기본** | "고른 물리존으로 만들기"(편집 팔레트) | 스타일 없음(옅은 회색 글자, 기본 배경) |
| 활성인 `ghost` 인데 `cursor: pointer` | ▶ 리플레이 | 정상 |

`구축하기`가 비활성이면 액센트 선·글자가 옅어져 "눌러서는 안 되는지"와 "원래 약한 단추인지"가 구분되지 않는다(위 주요 단추 계열 지적과 같은 문제).

주의: 처음 돌린 계측에서 라이트 `color-contrast` 14건이 나왔으나 테마 전환 직후 색 전환 중에 axe 가 재서 생긴 거짓 양성이었다(전환 후 0.9초 기다리면 1건). 층 칩의 글자/배경 대비 1.03 도 계측 함수가 반투명 배경을 잘못 합성한 값이라 믿지 않는다(axe 는 이 칩을 위반으로 보지 않음).

# 시스템 시험 결과 (2026-10-15)

`DESIGN.md` 의 척도·컴포넌트·상태 규칙을 `system.css`(+ `themes.ts` Linear 토큰 + `fixes.css`)로 앱 위에 얹어 같은 계측을 다시 돌렸다. 대상은 Clinic(건축+HVAC)과 성수(건축+기계 `Factorial_*.ifc`, 19층·기기 4677·연결 19523), 1440px. 앱 코드는 그대로다. 대표 사진: `components-sheet-system.png`(원본은 `components-sheet.png`), 전후 화면은 `.local/design-audit/sys-*.png`.

| 단추 높이 종류 | 16 → 9 | 19 → 9 |

## axe(WCAG 2.2 AA) 전후

| | Clinic 원본 → 시스템 | 성수 원본 → 시스템 |
|---|---|---|
| 라이트 보기 | color-contrast 1 → **0** | 2 → 1 |
| 라이트 편집 | 1 → **0** | 2 → 1 |
| 다크 보기 | 1 → **0** | 1 → **0** |
| 다크 편집 | 3 → **0** | 3 → **0** |
| `scrollable-region-focusable`(`#warnings`) | 1 → 1 | 1 → 1 |
| `target-size` | 1 → 3 | 3 → 1 |

- 색 대비를 푼 방법은 세 가지다. (1) `--muted` 를 라이트 `#565a62`·다크 `#a2a5ad` 로 올림 (2) 편집 대상(공간·설비) 켠 칸의 글자를 흰색 하드코딩 대신 `--on-accent` 로 — 다크 accent 가 밝아 흰 글자가 2.9:1 이었다 (3) 계통 칩 `small` 글자를 본문색으로.
- 성수에 남은 라이트 1건은 `.aux`(보조 글씨 한 곳) 로, 아직 원인 클래스를 열어 보지 않았다.
- `#warnings`(경고 영역)는 키보드로 스크롤할 수 없다 — CSS 가 아니라 `tabindex="0"` 가 필요한 소스 수정이다.
- `target-size` 는 해석이 불확실하다. 깨끗한 새 페이지에서 axe 만 돌리면 위반이 없고(층별 요약 단추 70×24·42×24px), 상태 계측을 거친 뒤 재면 나온다. 스크롤한 위치에서 고정된 막대에 단추가 가려져 생기는 계측 현상으로 보이나 확인하지 못했다. 원본에도 같은 종류(미배치 목록 링크)가 있다.

## 시험이 알려 준 것(시스템 규칙에 반영)

1. 컨트롤 높이를 키우면 **좁은 곳이 깨진다**: 팔레트(8.5rem)의 천장·바닥 토글이 잘렸고, 규칙 점수 입력(`.grade-line`)이 줄바꿈됐고, 표 안 층 요약 단추가 행 높이를 키웠다. 컴포넌트 규칙에 "표 안 단추 24", "숫자 입력 폭 4.5rem", "팔레트 토글은 예외"를 넣은 이유다.
2. 다크에서 `--on-accent` 를 안 쓰고 흰색을 하드코딩한 곳은 그 자체로 대비 위반이다(편집 대상 켠 칸). 시스템은 "accent 면 위 글자는 항상 `--on-accent`" 를 규칙으로 둔다.
3. **성수에서도 같은 결과.** 19층·4677대 화면에서도 레이아웃이 깨지지 않았고 상태 규칙이 같게 적용됐다(`seongsu-*-states.json`, 다크 편집 스샷).
4. 원래부터 있던 3D 위 겹침: 편집 모드에서 3D 아래 안내 글(`설비 클릭: …`)이 오른쪽 범례(`미배치·소속 없음·위반`)와 겹쳐 "위반"이 안내 글을 가린다(성수 1440px, 원본과 시스템 모두). 시스템 CSS 가 만든 것이 아니다. 오버레이 자리 규칙(3D 위 요소의 영역을 나눔)이 필요하다는 근거다.

## 아직 못 한 것
- 성수는 상태·axe·스샷만 돌렸고 컴포넌트 인벤토리(서명 집계)는 Clinic 만 돌렸다.
- 시험 CSS 는 `!important` 덮어쓰기다. 실제 반영은 소스 치환이라 결과가 다를 수 있다(특히 서명 수).
- 호버·눌림의 "느낌"(속도·크기)은 눈으로 안 봤다. 값만 계측했다.
