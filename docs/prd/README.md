## 어느 문서가 어느 질문에 답하나

같은 질문에 두 문서가 답하면 반드시 어긋난다. 요구사항 등급표를 두 곳에 두었다가 같은 항목이 한쪽은 필수, 다른 쪽은 권장이
된 일이 있다. 그래서 문서는 주제가 아니라 **답하는 질문**으로 가르고, 서로는 번호로만 가리킨다.


| 자리                                                             | 답하는 질문                                                     | 소유                        |
| -------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------- |
| `PRD_011.md`                                                   | 제품 전체가 무엇을 왜 하나. 릴리즈 · KPI · 규칙 K · 요구조건 S                 | 기획                        |
| `features/` 티켓 파일                                              | 기능 하나가 사용자에게 무엇을 해 주고, 됐다고 치는 기준은 무엇인가                     | 요구사항·수용 기준은 기획, 검증·메모는 개발 |
| `questions.md`                                                 | 아직 정하지 않은 것은 무엇이고 누가 언제 정하나                                | 기획                        |
| [`../bim-to-dt-ontology.md`](../bim-to-dt-ontology.md) (개발 정본) | BIM 이 그중 어디까지 주고(등급 · 피처 F · 편집 E), 고객사에 무엇을 요구하나(R0\~R24) | 개발                        |
| `../../CLAUDE.md`                                              | 코드를 고치는 사람이 함정을 피하려면 무엇을 알아야 하나                            | 개발                        |


등급 · R · F · E 는 개발 정본에만 있다. PRD 는 번호로 가리키고 본문을 복사하지 않는다. 반대로 기능(# · OE) · 릴리즈 · D · KPI ·
K · S 는 여기에만 있다.

## 티켓 파일의 틀

```markdown

id: "OE-BIM-12"
epic: "E05"
epic_title: "초기 구축 — BIM 임포트 · 검토 화면"
title: "배치점 보정"
prd: "#6"                    # Epic 이 대응하는 PRD 기능 번호(옛 Confluence 표의 행 번호)
release: "R1"                # R1 | R2. R1.5 는 2026-10-01 에 R1 으로 합쳤다
priority: "P1"               # P1 필수(릴리즈 게이트) | P2 권장 | P3 선택
owner: "ontology-editor"     # ontology-editor | srcn | tbd
status: "prd-done"           # 아래 범례
status_note: "성수 277대 보정 표시"   # 있을 때만
blocked_by: []               # 이 결정·이슈가 나야 진행 — questions.md 의 번호
depends: ["R11"]             # 참고하는 티켓·요구사항·규칙·장
jira: ""                       # 쓰지 않는다(옛 Jira 칸). 이슈와는 제목 끝 (OE-XXX-nn) 으로 잇는다
---

# OE-BIM-12 배치점 보정

## 요구사항        ← 기획 소유
## 수용 기준       ← 기획 소유. "—" 는 상세 기획 때 채움
## 검증 (이 repo)  ← 개발 소유. 이 기준을 재는 테스트·검사 항목. "—" 는 아직 안 잼
## 메모            ← 개발 소유
```

머리 필드의 값은 전부 JSON 형식(따옴표 친 문자열, 대괄호 목록)이다. `prd.test.ts` 가 의존성 없이 읽기 위해서다.

**상태 범례** — 원문 기호를 보드 상태 이름으로 바꿨다(부록 F).


| status       | 원문  | 뜻                                |
| ------------ | --- | -------------------------------- |
| `prd-done`   | ✔   | prd 작성 완료되어, 개발 구현 시작해도 되는 상태.   |
| `prd-review` | ⏸   | prd 작성 중임, 개발 구현 시작 전 검토 필요한 상태. |


**주체(owner)** 는 이관 때 상태에서 추정한 **초기값**이다 — ✔·◐ 는 `ontology-editor`, SRCN? 는 `srcn`, 섞였거나 미구현이면 `tbd`.
운영 편집의 주체는 D10 이 열려 있으므로, 결정되면 그 티켓들의 `owner` 를 고친다.

**Epic 폴더의 `README.md`** 는 티켓 머리 필드(ID · 기능 · Rel · P · 상태 · 이슈)를 베낀 색인이다. GitHub 에서 폴더를 열면
바로 보이게 둔 것이고, 파생 정보라 티켓을 고치면 같이 고친다. 어긋나면 `prd.test.ts` 가 실패한다.

**`PRD_011.md` 3장의 "Epic 별 티켓 목록"** 도 같은 표를 한 번 더 베낀다 — 폴더를 열지 않아도 `OE-XXX-nn` 가 무엇을
정의하는지 PRD 안에서 한눈에 보려는 것이다. 요구사항·수용 기준 본문은 옮기지 않는다(옮기면 두 벌이 된다). 티켓을 고치면
Epic `README.md` 와 `PRD_011.md` 표를 같이 고친다 — `prd.test.ts` 가 셋의 일치를 확인한다.

## 고치는 법

1. **변경은 PR 이다.** 요구사항·수용 기준 절은 기획이, 검증·메모 절은 개발이 고친다. 한 PR 에서 둘이 같이 바뀌는 것이 정상이고,
 그것이 요구와 구현을 한 파일에 둔 이유다.
2. **ID 는 바꾸지 않는다.** 코드 주석과 보드 이슈가 번호로 가리킨다. 티켓이 없어지면 파일을 지우고(상태 값은 `prd-done` · `prd-review` 둘뿐이다)
 이슈는 "not planned" 로 닫고 이유를 코멘트에 남긴다. 다른 티켓의 `depends` 가 가리키던 번호는 `prd.test.ts` 가 잡으니 같은 PR 에서 고친다. 번호는 재사용하지 않는다(옛 부록 E 4항과 같다).
3. **릴리즈 · 우선순위 · 상태는 머리 필드만 고친다.** 본문에 "(R1.5 → R2 이동)" 같은 표시를 쓰지 않는다. 그것은 git 이력이다.
 `[v1.4]` 같은 판본 표시도 같은 이유로 떼어 냈다. 판 단위 요약은 `PRD_011.md` 의 변경 이력 표에 한 줄.
4. **열린 것은 `questions.md` 한 곳.** 티켓 본문에는 번호(`D1`)만 적는다. 결정되면 그 표에서 상태를 바꾸고 결론을 한 줄 쓴다.
5. **개발 정본(등급 · R · F · E)이 바뀌면** 같은 PR 에서 그것을 가리키는 티켓의 `depends` · 본문을 맞춘다. `requirements-ids.test.ts` 가
 정본과 IDS 를, `prd.test.ts` 가 티켓이 가리키는 R 번호의 존재를 본다.
6. **보드 이슈를 만들 때** 이슈 제목 끝에 `(OE-XXX-nn)`, 본문 첫머리에 이 파일의 경로를 둔다. `jira` 칸은 비워 둔다. 본문은 파일이 정본이다 —
 이슈와 갈리면 파일을 따른다. 제목 · 라벨 · 칸 규칙은 `PRD_011.md` 부록 F.
7. **새 티켓**은 Epic 폴더에 다음 번호로 만들고, Epic `README.md` 와 `PRD_011.md` 3장의 기능 수를 같이 고친다.

## PRD 정합성 검사 — `npm test` 의 `prd.test.ts`

- **목적** : docs/prd/features/** 하위에 작성한 Epic별  `(OE-XXX-nn).md`의 내용이 Epic별  `'README.md`와  `docs/prd/README.md`, `PRD_011.md`,  `glossary.md`가 **서로 모순되는 지점 없이 내용 정합성을 충족하는지** 검사한다. 
- 티켓 파일 수 = `PRD_011.md` 3장 색인의 기능 수 합. `id` = 파일 이름, 중복 없음, Epic 폴더와 ID 머리가 맞음.
- 머리 필드가 있고 값이 범례 안이다. 본문에 네 절이 다 있다.
- `depends` · `blocked_by` 가 가리키는 OE 티켓 · Epic 머리(`OE-ZON`) · R(개발 정본 4장) · K · S(`PRD_011.md` 부록) · D · Q · U · P(`questions.md`) 가 존재한다.
- Epic `README.md` 의 행이 폴더의 티켓과 같다(ID · 기능 · Rel · P · 상태 · 이슈). `PRD_011.md` 3장의 티켓 목록도 같다.
- `questions.md` 의 "영향 티켓" 이 실제 파일이다.
- `features/` 에 `[v1.4]` 가 남아 있지 않다.

## MD 티켓과 보드 내 티켓 동기화 — `npm run board`

- **목적** : docs/prd/features/** 내의 티켓 MD와 "온톨로지 자동화 구축" project 보드 내의 티켓의 내용이 서로 동기화 되는지 검사한다. 
- 티켓 md 가 정본이고 칸반 이슈는 파생이다. `scripts/sync-board.mjs` 가 md 를 이슈에 맞춘다. **`prd.test.ts` 와 달리 네트워크·사내 GitHub 인증(`gh`)이 필요하고 보드를 바꾸므로 테스트에 넣지 않고, 반영(`--apply`)은 사람이 로컬에서 수동으로 돌린다.** 점검은 Actions `Board check`(`.github/workflows/board-check.yml`, 55 러너)가
  티켓 md 를 고친 PR 과 main push 때 돌려 실행 요약에 남긴다 — PR 에서는 "merge 하면 어느 이슈의 본문·라벨이 바뀌나" 를 미리 보이고,
  main 에서는 반영 안 된 어긋남을 보인다. 반영을 자동으로 하지 않는 까닭: 문구만 다듬어도 개발이 손댄 이슈에 `modified` 가 붙어
  칸반이 In Progress 로 돌아가니, 무엇이 바뀌는지 보고 돌린다.

| 명령 | 하는 일 |
|---|---|
| `npm run board` | 점검만 한다(쓰지 않음). 어긋남이 있으면 종료 코드 1 |
| `npm run board -- --diff` | 어긋난 이슈마다 새로 쓸 수정 이력을 보인다 |
| `npm run board -- --apply` | 어긋난 이슈의 제목·본문·라벨 `phase-1/2`·Phase 칸을 고친다 |
| `--only=OE-COM-01,OE-COM-02` | 그 티켓만 (`--date=YYYY-MM-DD` 로 이력 날짜를 바꾼다) |

- **연결 키**는 이슈 제목 끝의 `(OE-XXX-nn)` 이다. 티켓의 `jira` 칸에 이슈 번호를 되적지 않는다.
- **맞추는 것**: 제목 `<md 제목> (<ID>)`, 본문(머리 3줄 + md 본문 사본), 라벨 `phase-1`(R1)·`phase-2`(R2), Phase 칸(R1 → `P1 · 1차 릴리즈`, R2 → `P2 · 후속`).
- **본문이 바뀌면** 본문 위 `수정 이력` 칸에 `(2026-10-02) 요구사항 수정 — 이전 문구: …` 줄을 덧붙인다. 이력은 이슈 본문에만 있고 md 에는 쓰지 않는다.
- **개발이 손댄 이슈의 요구사항이 바뀌면** 라벨 `modified` 를 붙인다. 개발이 손댄 이슈는 Status 가 In Progress·In Review·Done 인 것이고,
  바뀐 것으로 치는 절은 요구사항·수용 기준이다(검증·메모는 개발이 쓰는 절이라 세지 않는다). 떼는 것은 개발이 구현을 다시 본 뒤 손으로 한다.
  라벨 전체 정책은 위키 [라벨 정책](https://github.sec.samsung.net/IoT-Solution/bim-to-dt-ontology/wiki/라벨-정책).
- **이슈 본문을 직접 고치지 않는다.** 고치면 다음 `--apply` 가 md 로 되돌린다. 이미 고쳤으면 그 문구를 md 로 옮기고 돌린다.
- **라벨을 `🏷️ 라벨` 칸으로 옮겨 적는다**(보드의 모든 항목). 보드는 라벨을 열로 못 써서, 라벨 보드는 이 단일 선택 칸을 열로 쓴다.
  정본은 라벨이고 칸은 사본이라 칸을 손으로 고치지 않는다. 라벨이 둘 이상이면 `rejected` > `modified` > `needs-pm` > `blocked` >
  `needs-dev` > `enhancement` 순으로 하나만 적는다. 라벨을 붙이거나 뗀 뒤 `--apply` 를 돌려야 보드 열이 따라온다.
- **하지 않는 것**: Status 이동(개발이 판단 — `prd-done` 인데 `PRD in progress` 인 것은 "넘길 후보"로 알리기만), 코멘트, 이슈 닫기·만들기.
  `planned` 라벨이 없는 이슈(구현 완료 보고로 대체된 것)는 건드리지 않는다.
- `👀 In Review` 이슈도 본문을 고친다. 수정 이력이 무엇이 바뀌었는지 남긴다.
