# ADR-0001 문서 챗봇은 읽기 전용 MCP 로 55 의 gemini 에 붙인다

## 맥락

PRD 정본이 `docs/prd/` 의 md 276개(760KB)로 옮겨 왔고, 설계 결정은 `intent.md` 와 이 폴더(ADR)에 쌓인다.
"이 벽은 왜 못 옮겨?", "D10 이 어디에 걸려?" 같은 질문에 답하려면 여러 파일을 열어 맞춰 봐야 한다.
화면(8084)을 보던 사람이 그 자리에서 묻고 근거 파일까지 받고 싶다.

제약:
- 55 에는 gemini CLI(0.62, 사내 계정 oauth)가 있다. `GOOGLE_CLOUD_PROJECT` 가 없으면 바로 죽고, 한 번 묻는 데 10초 안팎이다.
- 55 는 pip·npm 레지스트리에 닿지 않는다(2026-09-23 실측). 55 의 node 는 22.14 라 TS 를 바로 못 돌린다.
- 8084 는 사내망 누구나 연다. 이 앱은 원래 API 가 없어 정문(8000)을 거치지 않는다.

## 결정

- 8084 화면에서 Alt+Shift+K 로 채팅 창을 연다. 창은 앱 코드(src)가 아니라 `run.sh build` 가 dist 에 끼워 넣는
  `scripts/docs-chat.js` 다. 앱 상태(열어 둔 BIM, 고른 요소)는 넘기지 않는다.
- 창은 같은 서버의 `POST /__chat` 에 묻고, `serve.mjs` 가 띄워 둔 `gemini --acp` 에 묻는다(`scripts/docs-chat.mjs`). 처음에는 질문마다 headless(`-p`)로 띄웠고, 2026-10-06 에 바꿨다(`docs/dev/deploy55.md`).
- gemini 가 쓸 수 있는 도구는 **이 repo 의 문서만 읽는 MCP 서버(`scripts/docs-mcp.mjs`) 하나**다.
  admin 정책으로 그 밖의 도구(셸·파일 읽기·쓰기·웹)는 전부 막는다.
- MCP 서버는 의존성 없는 node 다. 검색은 wiki-mcp(AI-Agent-Wiki-Template)를 따라 문자 2-gram BM25 에 식별자 통 토큰,
  섹션 단위로 읽기.
- 챗봇은 문서를 고치지 않는다. 고칠 곳은 "이 파일의 이 절을 이렇게" 까지 제안하고, 고치는 건 사람이 PR 로 한다.

## 고려한 다른 길

- **앱(src)에 패널을 넣고 고른 요소를 질문에 붙인다** — "이 벽" 에 바로 답할 수 있지만, 앱이 서버를 아는 순간
  PRD 1.7 의 데이터 교환 방식(①파일)과 섞인다. 문서만으로 먼저 쓸모를 본다.
- **챗봇이 ADR 초안을 쓰거나 repo 에 커밋한다** — 누구나 여는 화면에서 쓰기 경로가 생기면 인증·검토 장치가 따로 필요하다.
  무엇을 결정으로 남길지는 판단이 필요한 일이라 자동화하지 않는다(wiki-mcp 와 같은 이유).
- **Python fastmcp 로 wiki-mcp 를 복사한다** — 55 에서 pip 로 받을 수 없다. 이 repo 의 서버 코드는 전부 node 다.
- **임베딩 검색** — 문서 수백 개 규모에서는 색인 비용이 이득보다 크다. 매 호출 전체를 훑어도 수십 ms 다.

## 결과

- 정문을 거치지 않는 API(`/__chat`)가 생긴다. 지키는 것은 "문서 읽기만" 이라는 도구 제한이고, 비용은 55 계정의 gemini 사용량이다.
  동시 실행 수와 질문 길이를 서버에서 묶는다.
- 문서가 바뀌면 55 의 체크아웃이 pull 될 때(배포) 챗봇도 따라온다. 8087 검토 판은 그 판의 체크아웃을 읽는다.
- 되돌리려면 `run.sh` 의 끼워 넣기와 `serve.mjs` 의 `/__chat` 을 빼면 된다. 앱 코드는 건드리지 않았다.
