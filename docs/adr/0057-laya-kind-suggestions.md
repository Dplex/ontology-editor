# ADR-0057 종류를 모르는 패밀리에 Laya 후보를 한 줄 더 보인다

## 맥락

편집 화면 "종류를 모르는 패밀리" 칸은 사람이 종류(39개)를 고르는 곳이다. 지금의 후보(kind-suggest.ts)는 이름의 낱말과 같은 건물에서
닮은 패밀리로 셋을 낸다. 화면이 이미 단서(이름·IFC 클래스·계통·이웃·위치)를 글로 모아 두고 있어서, 글을 읽고 라벨 하나를 고르는
분류 모델(Laya, 인코더 3억 파라미터, choice·score·noul 을 한 번에 답한다)을 붙여 볼 만했다. 사람이 고른 결과가 그대로 학습 줄이 된다.

55 는 GPU 드라이버가 없어서 133(RTX 5090)에 둔다. 추론 한 번 20ms 안팎, VRAM 1.5GB 다.

실측(2026-10-13). 정답은 종류를 아는 패밀리 — 사전(이름)이나 BIM 타입이 정한 것 — 이다. 기준선은 지금의 후보다.

- **이름을 가렸을 때**(`P12`·`CH1` 처럼 이름이 아무것도 말하지 않는 경우를 흉내 냄). 기준선은 닮은 패밀리(check:sample 의
  `evaluateSuggestions` 와 같은 셈)다. top3 맞힌 수:

  | 건물 | 패밀리 | 학습 전 | 다른 건물로 학습 | 그 건물도 5겹으로 학습 | 기준선 |
  |---|---|---|---|---|---|
  | 병원 | 46 | 9 | 30 | 32 (top1 27) | 38 (top1 26) |
  | 성수 | 64 | 12 | 19 | 33 (top1 22) | 54 (top1 41) |
  | Duplex | 20 | 6 | 13 | 16 (top1 13) | 14 (top1 14) |

- **이름은 보이는데 사전이 못 읽은 것**(BIM 타입이 정답). 기준선은 이름의 낱말 + 닮은 패밀리다. 그 건물도 5겹으로 학습했을 때
  top1/top3 는 병원 17/20 (기준선 16/21), 성수 3/5 (3/5), Duplex 10/11 (6/11)이다.
- 학습 재료는 가진 BIM 8벌에서 패밀리 362줄뿐이다. 학습 한 번에 40~180초다.
- 실제 화면에서 모르는 패밀리를 보면 이렇다. 성수 23개는 대부분 "자신 없음"(확률 50% 아래)으로 물러난다. `CE-1`·`CE-3` 은 배기팬 68% 로
  높게 낸다. Duplex 의 `M_Thermostat` 은 조명 96% 로 높게 틀린다. 라벨에 온도조절기가 없으면 가까운 것을 자신 있게 고른다.

## 결정

- **한 줄 더 보일 뿐, 지금의 후보를 대신하지 않는다.** 위 숫자에서 Laya 는 작은 건물(Duplex)과 top1 에서는 기준선과 비슷하거나 낫고,
  성수에서는 크게 못하다. 둘이 맞히는 패밀리가 달라서 나란히 둔다. "Laya:" 줄에 확률과 함께
  셋을 보이고, 확률이 `LAYA_SURE`(0.5) 아래면 흐리게 "자신 없음" 을 붙인다. 0.5 는 잰 값이 아닌 임시값이다 — 보정할 집합이 없다.
- **정하지 않는다.** 누르면 여느 후보처럼 그 패밀리 전체에 붙고, 출처는 "편집" 이다(OE-EQP-14). 모델이라는 출처를 따로 만들지 않았다.
  눌러 정한 것은 사람이 정한 것이다.
- **임포터는 부르지 않는다.** 같은 IFC 는 언제나 같은 결과여야 한다(이어서 하기, check:sample). 모델 판이 바뀌면 달라지는 값을 임포트 결과에
  넣지 않는다.
- **단서 글은 앱 한 곳에서 만든다**(`family-clues.ts` 의 `familyClues`·`clueText`). 화면 단서, 학습 재료(`scripts/laya/export.test.ts`),
  서버에 묻는 글이 모두 이것을 쓴다. 학습한 글과 묻는 글이 어긋나면 체크포인트가 엉뚱하게 답해서다. 줄 순서·낱말을 바꾸면 다시 학습한다.
  학습 글에 타입(declaredType)은 넣지 않는다. 화면 단서에 없고, BIM 이 정답인 패밀리에서는 답을 알려 준다.
- **질문(지시문·라벨 39개)은 133 의 서버가 정한다**(`scripts/laya/serve.py`). 앱은 단서 글만 보낸다. 넘기는 길은 `GET /__laya`·
  `POST /__laya/kinds` 둘뿐이다(`scripts/laya-proxy.mjs`, 8084 와 dev 가 같이 쓴다). `LAYA_URL` 이 없거나 133 이 안 받으면 줄이 안 보인다.
- 넘김은 fetch 가 아니라 프록시를 타지 않는 `node:http` agent 로 한다. 사내 PC 는 `NODE_USE_ENV_PROXY=1` 이라 fetch 와 기본 agent 가
  사내 프록시로 나갔다. Node 가 NO_PROXY 의 `10.*.*.*` 를 알아보지 못해 133 에 닿지 않았다.

## [설비 더하기] 에서 이름을 치면 종류 후보 (2026-10-13 더함)

[설비 더하기] 를 누르면 3D 왼쪽 위에 이름 칸이 뜬다. 이름을 치면 사전이 읽은 종류(출처 사전)가 먼저, 이어서 Laya 의 후보가 확률과 함께
칩으로 뜬다. 칩을 누르거나 Enter 로 첫 칩을 받은 뒤 바닥을 누르면 그 이름·종류로 놓인다(출처 편집). **고르지 않으면 지금처럼 종류 미상으로
놓인다**(OE-EQP-13 "종류는 미상으로 들어와 사용자가 지정"). 고른 종류가 지금 놓는 면(천장 모드인가)에 놓이지 않는 종류면 알리기만 한다.

- 묻는 글은 `newEquipmentText`(laya.ts) 두 줄이다 — 이름과 놓는 면. 놓기 전이라 방·계통·이웃은 모른다. 같은 서버·체크포인트가 패밀리
  단서와 이 글을 둘 다 배운다(질문 하나, 라벨 39개).
- 실측. 가진 BIM 의 설비 이름(패밀리 이름, 설비 이름에서 Revit 요소 번호를 뗀 것) 중 **이름만으로 사전이 못 읽는 줄**을, 그 건물을 빼고
  배운 체크포인트로 쟀다. 기준선은 이름의 낱말 후보(`suggestByName`)다. 첫 후보 / 셋 안:

  | 건물 | 줄 | Laya | 이름의 낱말 |
  |---|---|---|---|
  | 병원 | 53 | 29 / 39 | 18 / 25 |
  | Duplex | 23 | 14 / 20 | 7 / 11 |
  | ifc4Mep | 54 | 11 / 40 | 4 / 4 |
  | 성수 | 20 | 6 / 16 | 2 / 2 |

  합쳐 150줄 중 첫 후보 60 대 31, 셋 안 115 대 42 다. 패밀리 단서(위)와 달리 여기는 같은 건물의 닮은 패밀리가 없어 기준선이 약하다.
  성수의 `EAE_SATURN_VE_16W`(조명)는 변압기 68% 로 높게 틀린다 — 제품 코드만 있는 이름이다.
- 사람이 칠 법한 한국어 이름 12개를 만들어 Duplex 에서 쳐 봤다(정답지가 아니라 눈으로 본 것이다). 8개는 사전이 먼저 읽는다(배기팬·펌프·
  소화기·CCTV·FCU …). Laya 가 보탠 것은 "스프링클러" → 스프링클러 헤드 100% 다(사전이 일부러 읽지 않는 종류). 틀린 것은 "천장형 냉난방기" →
  방열기 45%, "냉온수 헤더" → 냉동기 83%, "온도조절기" → 디퓨저 39% 다. 학습한 이름이 거의 영어 Revit 이름이고, 헤더·온도조절기는 라벨이 없다.
  이름 하나에 칩이 뜨기까지 0.35초(치기를 멈추고 0.15초 기다림 포함)다. 5% 아래 Laya 후보(`LAYA_MIN`)는 보이지 않는다 — 0% 칩이 자리를 채웠다.
- 이름 칸을 팔레트(3D 왼쪽 아래)에 두었더니 팔레트가 커져 바닥을 가렸고, 바닥을 누른 것이 [천장] 토글에 떨어져 더하기가 취소됐다. 3D 왼쪽 위에 띄운다.

## 한국어 이름을 학습에 더했다 (2026-10-22 더함)

[설비 더하기] 에서 "공기조화"·"씨씨티비"·"에어컨"·"소화기" 같은 한국어 이름이 후보에 안 떴다. 학습 재료가 BIM 의 영어 Revit 이름뿐이라서다
(위 "사람이 칠 법한 한국어 이름 12개" 에서 이미 보인 한계다). 서버나 호출 쪽 문제가 아니었다.

- **재료.** 라벨 39개마다 한국어 이름 6~8개(`scripts/laya/ko-names.json` 의 `train`, 256줄)를 이름 줄 형식(`newEquipmentText`) 그대로
  `ko.adds.jsonl` 로 써서 학습에 더한다. 형식은 바꾸지 않았으니 다시 학습할 일이 늘지는 않는다. 줄임말·음역·영어 섞기도 넣었다.
  사람이 지은 추정이고 정답지가 아니다 — 현장 이름이 모이면 `ko-names.json` 에 더한다.
- **잰 방법.** 학습에 넣지 않은 한국어 이름 132개(`test`, 말 모양이 다른 것)를 `ko_eval.py` 로 쟀다. 첫 후보 / 셋 안:
  이전 체크포인트 56 / 74, 한국어를 더한 것 96 / 111 이다. 영어 이름은 건물 하나씩 빼고 재는 방식(`--adds`)으로 한국어를 뺀 때와 견줬다
  (같은 데이터·설정, 병원·Duplex·ifc4Mep·성수 합): 64 / 83 대 61 / 87 로 오차 안이다.
- **버린 길.** 이름에 층·번호를 붙인 변형(`3층 CCTV`, `펌프 2`)을 함께 넣어 512줄로 학습하면 한국어는 100 / 118 이지만 영어 이름이
  50 / 78 로 나빠진다(ifc4Mep 첫 후보 14→6). 한국어 줄이 영어 줄(435)보다 많아져 균형이 깨진 것으로 본다. 이름만 넣은 256줄로 했다.
- **한계.** 틀린 것은 말이 라벨과 멀 때다("에이에이치유닛"·"천카세트"·"지열 천공"). 라벨에 없는 종류(헤더·온도조절기)는 여전히 가까운 것을
  고른다. 시험 이름이 학습 이름과 같은 사람의 추정이라 실제 현장 이름으로 재면 더 낮을 수 있다.
- 서버 체크포인트는 `out-all2/final` 에서 `out-ko3/final` 로 바꿨다(이전 것은 서버에 그대로 있다).

## 확률을 학습에 안 쓴 줄로 보정하고, Enter 로 종류 목록을 연다 (2026-10-22 더함)

[설비 더하기] 에서 사전 칩 하나만 뜨고 Laya 칩이 안 보였다. 서버는 답하고 있었다. Laya 가 확률을 첫 후보에 몰아 줘서
(에어컨 → 실내기 100%, 둘째 0%) 첫 후보는 사전 칩과 겹쳐 빠지고, 둘째부터는 `LAYA_MIN`(5%)에 걸렸다. 틀릴 때도 99% 로 틀렸다
("냉온수 헤더" → 냉동기 99%, "가습기" → 위생기구 99%). 순위는 그대로 두고 확률이 말하는 바를 바로잡은 뒤, 그 순위를 목록으로 보인다.

- **보정은 temperature scaling 이다**(Guo et al., "On Calibration of Modern Neural Networks", ICML 2017). 로짓을 온도 T 하나로 나눠
  확률을 편다. 같은 수로 나누니 순위는 바뀌지 않는다. 체크포인트에 든 T(1.63)는 laya 가 학습 재료의 10% 로 맞춘 값이라 모델이 이미 본
  말투로 맞춘 것이다. `scripts/laya/calibrate.py` 가 학습에 안 쓴 449줄로 다시 맞춰 `out-ko3/calibration.json` 에 쓰고(T 3.16),
  serve.py 가 `LAYA_CALIB` 로 읽는다. 449줄은 건물 하나를 빼고 배운 체크포인트(`out-ko3-adds`)에 그 건물의 이름 줄·이름 가린 패밀리·
  BIM 타입이 정답인 패밀리를 물은 317줄과, 서버 체크포인트에 학습에 안 넣은 한국어 이름을 물은 132줄이다.

  | 449줄 | 보정 전 (T 1.63) | 보정 후 (T 3.16) |
  |---|---|---|
  | 첫 후보 / 셋 안 맞힘 | 211 / 280 | 211 / 280 |
  | NLL (정답 확률의 −log 평균) | 2.75 | 2.20 |
  | ECE (말한 확률과 실제 맞힌 비율의 어긋남) | 0.29 | 0.06 |
  | 90% 넘게 자신하고 틀린 수 | 66 | 5 |
  | 둘째 후보 확률의 가운데 값 | 2.3% | 4.7% |

  교차 확인: 형제 체크포인트 317줄로만 맞춘 T(3.48)를 서버 체크포인트의 한국어 132줄에 대면 NLL 1.34 → 1.25, 90% 넘게 틀린 수
  10 → 0 이다. ECE 는 0.157 → 0.167 로 조금 나빠진다 — 한국어 줄이 쉬워서 그 T 로는 덜 자신한다. 거꾸로 한국어로만 맞춘 T(2.57)를
  317줄에 대면 ECE 0.36 → 0.18 이다. 두 무리가 고르는 T 가 2.6~3.5 로 달라서 둘을 합쳐 맞췄다. 합친 T 에서 한국어 132줄의 ECE 는
  0.16 → 0.11 이다.
- **`LAYA_SURE`(0.5)가 잰 값이 됐다.** 보정 후 449줄에서 첫 후보 확률이 0.5 이상인 답은 50%이고 그 안에서 26%가 틀렸다. 0.7 이면
  40% · 19%, 0.8 이면 24% · 13% 다. 0.5 를 그대로 둔다. 올리면 목록이 첫 줄을 미리 가리키는 경우가 줄어 Enter 두 번으로 끝나는 일이 준다.
- **Enter 로 목록을 연다**(WAI-ARIA APG 의 combobox). 사전이 못 읽은 이름에서 Enter, 아무 때나 ↓ 로 연다. 줄은 사전 종류(있으면) →
  Laya 순위 5개 → [전체 40종 보기] → [종류 미상으로 두기] 다. 전체 보기도 Laya 순위다 — 서버가 라벨 39개를 다 돌려줘서, 셋 안에
  못 든 정답도 대개 위쪽에 있다. 사전이 읽은 이름의 Enter 는 지금처럼 사전 종류를 받는다.
  - 열 때 첫 줄을 미리 가리키는 것은 사전이 읽었거나 Laya 첫 후보가 `LAYA_SURE` 이상일 때뿐이다. 자신 없으면 아무것도 가리키지 않아,
    Enter 두 번이 버릇처럼 눌려도 아무것도 붙지 않고 ↓ 로 골라야 붙는다(OE-EQP-13 "종류는 미상으로 들어와 사용자가 지정").
  - [종류 미상으로 두기] 는 라벨에 없는 종류(헤더·온도조절기)에서 빠져나갈 길이다. 열린 집합 분류(open-set recognition)에서 "모름" 을
    따로 두는 것과 같은 뜻인데, 모델이 "모름" 을 배우게 하지는 않았다 — 그런 학습 줄이 없다. 대신 그런 이름은 보정 후 확률이 낮게 나와
    "자신 없음" 이 붙는다(온도조절기 → 실내기 7%).
  - Laya 답이 오기 전에 Enter 를 치면 0.15초 기다림 없이 바로 묻고 "묻는 중" 을 보인다. 목록에서 칩 밖의 종류를 고르면 [목록] 칩으로
    앞에 선다 — 안 그러면 무엇을 골랐는지 화면에 안 보였다.
- **실제 화면**(Duplex, 보정한 서버). 천장형 냉난방기 → 실내기 40% · 실외기 9% (자신 없음), 냉온수 헤더 → 냉동기 66%,
  온도조절기 → 실내기 7% (자신 없음), 가습기 → 위생기구 74%, 에어컨 → 실내기 80%. 가습기는 여전히 틀리지만 99% 가 74% 로 내려왔다.
- **버린 길.** 히스토그램 비닝(laya 의 `fit_binning_map`)은 칸 15개에 449줄이면 칸마다 30줄 꼴이라 흔들린다. 온도 하나로 했다.
  비슷한 예시를 찾아 후보 라벨을 좁히는 길(Brick-DICL, arXiv 2606.17637)과 라벨당 몇 줄로 배우는 few-shot 학습(SetFit, 2022)은
  학습 방식을 바꾸는 일이라 이번에 하지 않았다. 학습 재료가 늘면 견줘 본다.
- **다시 학습하면 다시 보정한다.** 체크포인트를 바꾸면 `--adds` 로 형제 체크포인트를 다시 만들고 calibrate.py 를 돌린다
  (`docs/dev/deploy55.md`). 다른 체크포인트에 맞춘 calibration 을 주면 laya 가 경고를 찍고 그대로 읽는다.

## 계통 후보는 Laya 없이 거리 순으로 (2026-10-13 더함)

계통이 없는 설비를 고르면 패널의 계통 상자 아래에 근처 계통 셋을 보인다(`system-suggest.ts`). 같은 층에서 15m 안에 구성원이 있는 계통을
가장 가까운 구성원까지의 거리 순으로 놓는다. 누르면 상자에서 고른 것과 같다(출처 편집, OE-PIP-02). 성수는 계통이 1,037개라 상자에서 고르기 어렵다.

**Laya 로 순서를 다시 매기지 않는다.** 가진 BIM 에서 계통이 있는 설비 960대(병원 400 · Duplex 55 · ifc4Mep 105 · 성수 400)를, 그 설비에 이미
이어진 덕트·배관을 빼고(막 놓은 설비를 흉내 냄) 그 건물을 학습에서 빼고 쟀다. 한 설비가 계통 여럿에 들면 그중 어느 것이든 맞은 것으로 셌다.
첫 후보 / 셋 안:

| 방법 | 960대 |
|---|---|
| 가장 가까운 계통(지금 화면) | 608 / 897 |
| Laya 가 후보 계통을 고름(후보 글에 거리 포함) | 병원만 123 / 263 (가장 가까운 계통 234 / 371) |
| Laya 가 후보 계통을 고름(거리 빼고) × 거리 감쇠 exp(-d/0.5) | 541 / 888 |
| Laya 가 계통 종류를 고름 → 그 종류 후보 중 가장 가까운 것 | 569 / 856 |
| Laya 계통 종류 확률 × 거리 감쇠 exp(-d/0.5) | 582 / 864 |

근처 후보끼리는 계통 종류도 대개 같아서(성수는 급기 계통만 753개, 이름은 "기계 급기 28" 처럼 번호만 다르다) 가르는 것이 거리뿐이다.
ifc4Mep 만 Laya × 거리(τ=2)가 첫 후보 65 로 가장 가까운 계통 50 보다 나았다. 실험 코드는 `scripts/laya/train.py` 의 `--picks`·`--sysk` 와
`combine_picks.py` 에 남긴다 — 학습 재료가 늘면 다시 잰다.

## 고려한 다른 길

- **Laya 를 지금의 후보 대신 쓴다** — 위 숫자로 접었다. 성수 top3 가 33 대 54 다. 성수는 FCU2·FCU3·FCU2_250 처럼 거의 같은 형제 패밀리가
  많아서 닮은 패밀리 셈이 아주 잘 맞는다.
- **laya-serve(laya 의 범용 HTTP, `/v1/systemone`)를 그대로 연다** — 앱이 질문·라벨까지 보내야 해서 학습 때의 질문과 어긋날 수 있다.
  누구나 아무 질문이나 133 GPU 에 던질 수 있게도 된다. 질문을 고정한 작은 서버로 했다.
- **55 에서 CPU 로 돌린다** — README 기준 CPU 는 4문항에 453ms 다. 패밀리 50줄이면 수 초라 편집 화면이 기다린다. 55 에 드라이버를 깔기 전에는 133 이다.
- **임포트할 때 모르는 종류를 Laya 로 채운다** — 위 "임포터는 부르지 않는다" 와 같은 까닭으로 접었다. 정확도도 사전에 못 미친다.
