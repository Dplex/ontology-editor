# docs/adr/ — 아키텍처 결정 기록

**왜 이렇게 만들었나** 를 결정 하나에 파일 하나로 남긴다. PRD(`docs/prd/`)가 "무엇을" 이라면 ADR 은 "어떻게, 왜 그 길을" 이다.
`intent.md` 의 절들도 결정이지만 이미 서사로 자리 잡아서 옮기지 않는다 — ADR 에서 그 절을 링크한다.

55 의 문서 챗봇(8084 에서 **Alt+Shift+K**)이 이 폴더와 `docs/prd/`·`intent.md` 를 읽고 답한다(docs/dev/deploy55.md).
그래서 아래 틀을 지키면 챗봇이 상태·관련 티켓으로 찾아 준다.

## 언제 쓰나

작업하다 아래에 해당하는 결정을 하면 **같은 PR 에** ADR 을 하나 더한다. 세션에서 정하고 코드에만 남긴 결정은 챗봇에게 없는
것이다 — "왜 이렇게 했어?" 에 "문서에 없다" 가 나온다.

- **쓴다**: 길이 둘 이상 있었고 하나를 골랐다(구조·저장 위치·라이브러리·데이터 모양) · 실측하고 접은 방법(숫자와 함께 —
  "FootPrint 만 읽으면 Revit 방이 0개") · 임계값을 정했다(SNAP 5cm, 배치점 0.5m 같은 것과 그 근거 파일) · PRD 와 다르게 가거나
  PRD 가 비워 둔 것을 개발이 정했다(관련 D##·티켓을 frontmatter 에)
- **쓰는 것은 온톨로지 프로젝트 본연의 결정뿐이다** — BIM 을 어떻게 읽고(임포트·판정·합치기), 사람이 무엇을 어떻게 고치고(편집),
  온톨로지에 무엇을 어떻게 내는가(TTL·GeoJSON·3D·보고서). **인프라·GitHub·개발 규칙은 ADR 로 쓰지 않는다** — 서버·배포·저장 방식·
  권한·잠금(55·133·`src/server/`), 문서 챗봇, 칸반·CI·검토 판, 티켓·시험 태그 같은 개발 도구는 그 코드의 머리 주석과 `docs/dev/` 에 둔다.
  2026-10-13 에 이 기준으로 0001(문서 챗봇)·0014·0039(임시 저장본·잠금)·0037(반영 버전 폴더)·0038(사람·역할)·0048(티켓→ADR 도구)·
  0052(FBX 서버 변환)를 지웠다.
- **안 쓴다**: 버그 수정, 이름·문구 손질, 티켓 요구사항을 그대로 구현한 것(그건 PR 본문의 확인 방법·테스트가 맡는다),
  화면 조작 세부(3D 빛·단축키·팔레트·초점 — `docs/dev/ui-notes.md` 에 절로 더한다)
- **같은 티켓·같은 장치의 작은 후속 결정은 새 ADR 대신 앞 ADR 에 더한다**(결정 줄 끝에 "(YYYY-MM-DD 더함)"). 2026-10-10 에 0012→0004,
  0027→0026, 0042→0040, 0043→0037 을 합치고 0013·0020·0044 를 ui-notes 로 옮겼다
- **상태**: 사람이 세션에서 고른 것이면 `채택` 에 `deciders` 를 그 사람으로, Claude 가 혼자 정한 것이면 `제안` 으로 쓰고
  PR 본문에 "ADR-nnnn 확인 부탁" 을 적는다. merge 로 `제안` 이 저절로 `채택` 이 되지는 않는다 — 사람이 고친다
- 맥락에는 **왜**와 **실측한 숫자**를, 결과에는 **되돌리려면 무엇을 고치나**를 적는다. 챗봇이 가장 자주 받는 질문이 그 둘이다
- 새 ADR 을 쓰기 전에 **같은 티켓(`tickets`)을 가진 ADR 을 읽는다.** **앞 결정을 바꾸면 앞 ADR 을 지금 결정으로 고친다** — 대체됨으로
  남기거나 머리에 메모를 달지 않는다. 옛 글은 git 이력에 있고, 왜 바꿨는지는 바꾼 ADR(또는 고친 ADR)의 맥락에 한 줄 적는다. 두 ADR 은
  `related` 로 서로 잇는다. 결정 전체가 필요 없어지면 파일을 지운다(번호는 다시 쓰지 않는다). 번호·목록·`related` 의 어긋남은
  `src/lib/adr.test.ts` 가 막는다 — 결정 내용끼리의 모순은 사람이 읽어야 한다
- **진행 계획("다음 PR 이다" · 진행 순서 · 미룬 것의 목록)은 ADR 에 쓰지 않는다.** 일이 진행되면 그 줄만 낡아 결정과 엇갈린다
  (2026-10-10 에 0032·0033·0034·0037·0038 다섯 곳). 계획은 PR 본문·`NEXT.md` 에, 미룬 까닭이 결정이면 "무엇을 왜 하지 않는다" 로 쓴다.
- `docs/dev/` 의 작업 규칙(IFC 함정 등)은 그대로 둔다. 같은 내용을 ADR 로 옮기지 말고, 새 결정만 ADR 로 쓴다

## 파일 이름과 틀

`NNNN-짧은-제목.md`. 번호는 이어서 매기고 재사용하지 않는다. 지운 번호는 비워 둔다.

```markdown
---
id: "ADR-0011"
title: "층 단위 생성은 층마다 TTL·GeoJSON 두 파일로 export 하고, 층 파일을 모두 합치면 건물 전체 TTL 과 같은 triple 이 되도록 나눈다"
status: "채택"          # 제안 · 채택
date: "2026-10-03"
deciders: ["정희록"]
prd: ["#7", "#8"]       # 관련 PRD 결정·오픈 이슈·기능 (D##, Q##, #n)
tickets: ["OE-GEN-11"]  # 관련 티켓
criteria: []            # 이 결정이 답하는 수용 기준(티켓#번호). 번호는 시험 태그와 같게 센다 — 없으면 []
code: ["src/lib/export/storey-export.ts"]   # 이 결정을 바꾸려면 열어 볼 파일(시험 제외)
tests: []               # 이 결정을 지키는 시험
related: []             # 같이 읽어야 하는 ADR(바꾸거나 바뀐 ADR 포함)
---
```

- 본문에서 티켓은 `OE-XXX-nn`, 수용 기준은 `OE-XXX-nn#3`, PRD 결정은 `D10`, 다른 ADR 은 `ADR-0049` 로 적는다. 챗봇의 `docs_links` 가 이 꼴로 잇는다.
- **criteria · code · tests · related 는 개발하는 LLM 이 ADR 에서 바로 기준·코드·시험으로 가는 길이다(scripts/docs-ctx.mjs).** 티켓 md 는 PM 몫이라
  "관련 ADR" 을 적지 않는다 — `npm run ctx -- OE-XXX-nn`(챗봇은 `docs_ticket`)이 ADR 의 `tickets`·`criteria` 를 거꾸로 읽어 티켓 쪽에
  보인다. 그래서 이 칸이 빠지면 티켓에서 이 ADR 이 안 보인다. 본문에 적은 파일·기준과 같게 두고, 파일을 옮기면 같이 고친다
  (`adr.test.ts` 가 없는 파일·없는 기준을 잡는다). 결정을 구현한 커밋에서 시험 제목에 단 태그(`[OE-XXX-nn#n]`)와 `criteria` 가 맞으면 된다.
