# BIM 으로 DT 온톨로지를 어디까지 만들 수 있나

이 문서는 네 가지에 답한다.

1. DT 가 쓰려면 온톨로지에 무엇이 있어야 하는지를 정한다(피처 정의).
2. 그중 BIM 이 줄 수 있는 것이 어디까지인지를 실측으로 적는다.
3. 그러려면 고객사 BIM 에 최소한 무엇이 들어 있어야 하는지를 적는다.
4. 만들어진 온톨로지를 고치는 편집 기능이 무엇을 제공해야 하는지를 정한다.

BIM 으로 만드는 일과 만든 것을 고치는 일은 한 벌이다. BIM 이 못 주는 피처가 절반이고 BIM 이
주는 것도 현장과 어긋나므로, 편집이 없으면 온톨로지가 처음 한 번만 맞고 그 뒤로는 틀려 간다.

근거가 되는 수치는 전부 이 저장소의 코드로 다시 잴 수 있다. 재는 방법은 마지막 절에 있다.

기준일: 2026-09-23 · 관련 문서: `[DT2.0] PRD_011(온톨로지 구축 자동화 플랫폼)`

곁가지 둘을 따로 뺐다. **`docs/ifc-coverage.md`** 는 IFC 가 주는 것을 파일별로 잰 지도이고,
**`docs/research.md`** 는 선행 연구에서
무엇을 가져왔고 무엇이 우리 파일에서 안 됐는지의 기록이다. 이 문서가 정본이고 둘은 근거다.

**두 질문의 답이 있는 자리.** "BIM 에 무엇이 반드시 있어야 하나" 는 §3 의 필수 표(R0~R13),
"BIM 으로 온톨로지를 어디까지 넓힐 수 있나" 는 §2 끝의 등급표와 확장 표다.

## 1. DT 온톨로지의 피처

피처를 먼저 정하는 이유는 이것이 BIM 요구사항을 결정하기 때문이다. DT 의 어느 화면이 무엇을
묻는지를 적으면, 온톨로지가 들고 있어야 할 관계가 따라 나온다. 그 관계를 BIM 이 주는지 아닌지가
다음 절의 답이 된다.

### DT 가 온톨로지에 묻는 질문

| 소비처 | 질문 | 답하는 데 필요한 관계 |
|---|---|---|
| 이상 알림 | 이 설비는 어디서 났는가 | 설비 → 물리존 |
| 탐색기 트리 | 건물이 어떤 구조인가 | 사이트 → 건물 → 층 → 물리존 |
| 3D Map | 이 공간을 어떻게 그리는가 | 물리존의 외곽선과 높이 |
| 계통도 | 이 공조기가 담당하는 공간은 어디인가 | 설비 → 계통 → 공조존 |
| AI Agent | 회의실 온도가 몇 도인가 | 공간 이름 → 설비 → 관제점 |
| 로봇 관제 | 이 경로로 지나갈 수 있는가 | 벽·문·창의 통과 가능 여부 |

### 피처 목록

각 피처에 출처를 함께 적는다. **출처가 BIM 이 아닌 것이 절반이라는 점이 이 표의 요점이다.**

| # | 피처 | 관계·속성 | 출처 |
|---|---|---|---|
| F1 | 공간 계층 | `brick:hasPart` (사이트 > 건물 > 층 > 물리존) | BIM |
| F2 | 물리존 기하 | 외곽선 다각형, 면적, 층 높이 | BIM |
| F3 | 공간 이름 | `rdfs:label`, 방 번호 | BIM |
| F4 | 벽·문·창 형상 | 위치, 두께, 개구부 치수 | BIM |
| F5 | 개구부 소속 | 어느 벽에 난 문인가 | BIM |
| F6 | 공간 경계 | 이 물리존을 둘러싼 부재는 무엇인가 | BIM |
| F7 | 내력벽 | `loadBearing` | BIM (속성을 기입한 경우에만) |
| F8 | 설비 목록 | 종류, 이름, 용량 | BIM (MEP 를 포함한 경우에만) |
| F9 | 설비 위치 | x·y·z, 설치면 | BIM (MEP 를 포함한 경우에만) |
| F10 | 계통 | 공조기 → 덕트 → 토출구 | BIM (MEP 를 포함한 경우에만) |
| F11 | 설비 소속 물리존 | `brick:hasLocation` | **계산으로 만든다** |
| F12 | 공조존 | `brick:Zone`, 담당 관계 | IDF 또는 gbXML. IFC 에도 자리(`IfcZone`)는 있으나 실측 값이 없다 |
| F13 | 관제점 | `brick:hasPoint` | BAS. 센서 장치 자체는 BIM 에 있을 수 있다 |
| F14 | 커스텀존 | 운영자가 지정하는 다각형 | 사용자 |
| F15 | 로봇 통과 여부 | 문은 통과, 창문과 벽은 불가 | F4 에서 파생 |
| F16 | 설비 연결(상류·하류) | `brick:feeds` | BIM (포트에 흐름 방향이 있는 경우에만) |

**F11 이 이 과제의 핵심이다.** BIM 은 설비의 좌표를 주고 물리존의 외곽선을 주지만, "이 공조기가
회의실에 있다" 는 말은 하지 않는다. 그 관계는 좌표가 어느 외곽선 안에 드는지를 계산해서 만든다.
이것이 없으면 이상 알림이 발생 위치를 표시하지 못하고, 탐색기 트리에 설비가 걸리지 않는다.

**F12 와 F13 은 지금 BIM 에서 나오지 않는다.** 다만 "IFC 에 없다" 가 아니라 **"IFC 에 자리는
있는데 실제 파일이 비어 있다"** 이다. 공조존은 `IfcZone`·`IfcSpatialZone` 이나 Revit 의
`VentilationZoneName` 칸에 담을 수 있는데, 실측 파일은 그 칸에 템플릿 기본값만 넣었다. 관제점은
센서 장치(`IfcSensor`)까지는 BIM 에 있지만 관제점 ID 는 BAS 가 들고 있다. 그러니 지금은 IDF·BAS
에서 받아야 하고, 고객사에 요구하면 일부를 BIM 쪽으로 당길 수 있다(§3 의 R19·R20).

## 2. BIM 으로 어디까지 되는가

세 가지를 구분해서 적는다. 규격이 담을 수 있는 것과 우리가 뽑는 것과 실제 파일에 들어 있는 것이
서로 다르기 때문이다.

| 피처 | IFC4 규격 | 지금 임포터 | 실측 샘플(AC20-FZK-Haus) |
|---|---|---|---|
| F1 공간 계층 | `IfcBuildingStorey`, `IfcSpace` | 읽는다 | 층 2, 물리존 7 |
| F2 물리존 기하 | `FootPrint` 또는 `Body` 표현 | `FootPrint` + `Body/SweptSolid` 를 읽는다 | 7개 전부 추출, Buero 12.985㎡ |
| F3 공간 이름 | `Name`, `LongName` | 읽는다 | Schlafzimmer, Bad, Buero 등 7개 |
| F4 벽·문·창 | `IfcWall`, `IfcDoor`, `IfcWindow` | 종류·이름을 읽는다. **위치(좌표)는 안 읽는다** | 벽 13, 문 5, 창 11 |
| F4 벽 두께 | `IfcMaterialLayerSetUsage` | 읽는다 | 13장 전부. 내벽 0.24m · 외벽 0.3m |
| F4 개구부 치수 | `OverallHeight`, `OverallWidth` | 읽는다 | 16개 전부. 문 2.01 x 0.885m |
| F5 개구부 소속 | `IfcRelVoidsElement` + `IfcRelFillsElement` | 읽는다 | 16개 전부 벽에 이어짐 |
| F6 공간 경계 | `IfcRelSpaceBoundary` | 읽는다 | 7개 물리존 · 경계 66면 |
| F15 로봇 통과 | F4 에서 파생 | 개구부 종류에서 파생한다(`passable`). 방-문-방 연결은 아직 | 문 5개만 통과 가능 |
| 길이 단위 | `IfcUnitAssignment` | 읽어서 미터로 환산한다 | 미터 · 밀리미터 · 피트를 확인 |
| F7 내력벽 | `Pset_WallCommon.LoadBearing` | 읽는다 | **0 / 13. 속성 자체가 없음** |
| F8 설비 | `IfcDistributionElement` 하위 | 읽는다 | **0** |
| F9 설비 위치 | `ObjectPlacement` | 읽는다 | 해당 없음 |
| F10 계통 | `IfcSystem` + `IfcRelAssignsToGroup` | 읽는다 | **0** |
| F11 설비 소속 | 규격에 없다 | 계산해서 만든다 | 해당 없음 |
| F12 공조존 | `IfcZone`, `IfcSpatialZone`(IFC4) — **자리는 있다** | 안 읽는다 | 없음. Duplex 는 칸만 있고 값이 템플릿 기본값 |
| F13 관제점 | 센서는 `IfcSensor`, 관제점 ID 는 **IFC 에 없다** | 센서를 설비로 읽는다 | ifc4Mep 센서 7, 설비와 잇는 관계 0 |

정리하면 이렇다.

- **공간 골격은 BIM 으로 충분히 만들어진다.** 층, 물리존, 외곽선, 면적, 이름이 전부 나온다.
  좌표 변환까지 포함해 실제 모델로 확인했다.
- **벽 두께, 개구부 치수, 공간 경계까지 읽는다.** 특히 `IfcRelSpaceBoundary` 는 물리존을 둘러싼
  부재를 BIM 이 직접 알려 주므로, 벽을 고칠 때 영향받는 물리존을 기하 연산 없이 찾을 수 있다.
- **설비는 파일에 들어 있어야 읽을 수 있고, 실제로는 대부분 없다.** 이것이 가장 큰 제약이다.

### 설비가 든 BIM 은 따로 있다

공개 샘플을 여러 곳에서 모아 확인한 결과, 설비는 **건축 모델과 다른 파일에 들어 있었다.**
같은 프로젝트라도 디스플린마다 파일이 갈린다.

| 모델 | 출처 | 스키마 | 물리존 | 설비 | 계통 | 포트 |
|---|---|---|---|---|---|---|
| AC20-FZK-Haus | web-ifc 테스트 모델 | IFC4 | 7 | 0 | 0 | 0 |
| C20-Institute-Var-2 | web-ifc 테스트 모델 | IFC4 | 82 | 0 | 0 | 0 |
| Office_A | web-ifc 테스트 모델 | IFC2x3 | 99 | 31 | 0 | 0 |
| dental_clinic | web-ifc 테스트 모델 | IFC2x3 | 269 | 102 | 0 | 0 |
| **ifc4Mep** | opensourceBIM/TestFiles | **IFC4** | 0 | **2,202** | **37** | **4,232** |
| Duplex COBie Design | NIBS · DURAARK | IFC2x3 | 22 | 133 | **10** | 0 |
| Duplex Eng-HVAC | NIBS · DURAARK | IFC2x3 | 1 | 498 | 0 | **970** |
| Duplex Eng-MEP | NIBS · DURAARK | IFC2x3 | 42 (**같은 방 21 × 2**) | 926 | 0 | 0 |

여기서 네 가지를 읽을 수 있다.

첫째, **건축 모델에는 설비가 없고 설비 모델에는 물리존이 없다.** 위 표에서 두 값이 동시에 큰
행이 하나도 없다(Duplex MEP 의 42개는 건축 방의 사본이다 — 아래 "건축과 설비를 합쳐야"). F11 설비 소속 물리존을 만들려면 두 파일을 합쳐야 하고, 합치려면 두 파일이
같은 좌표계를 써야 한다. 공유 좌표를 요구사항에 넣는 이유가 이것이다.

둘째, **계통이 든 파일은 드물고 종류가 둘이다.** `ifc4Mep` 은 `IfcDistributionSystem` 으로
37개를 담았고, Duplex 는 **COBie 판본에만** 10개가 있었다. COBie 는 시설관리 인수용 규격이라
계통과 자산 정보를 함께 담는다. 우리 용도와 목적이 같으므로, 고객사에 요구할 때 "IFC 에 MEP 를
포함" 만 적지 말고 **계통 정보를 함께 요구하는 편이 확실하다.**

셋째, **포트가 있으면 연결 관계를 알 수 있다.** `ifc4Mep` 은 포트 4,232개와
`IfcRelConnectsPorts` 2,024건을 담았다. 어느 덕트가 어느 토출구에 붙는지가 파일에 그대로 있다.
계통이 없어도 포트만 있으면 연결을 되살릴 수 있다. 다만 **포트가 있다고 흐름 방향까지 아는 것은
아니다** — 아래 "연결(F16)은 포트가 있어야 한다" 에서 잰다.

넷째, **길이 단위가 파일마다 다르다.** 확인한 네 파일 중 둘은 미터가 아니었다.

| 모델 | 선언된 길이 단위 |
|---|---|
| AC20-FZK-Haus | METRE |
| ifc4Mep | METRE |
| Duplex Eng-HVAC | **MILLIMETRE** |
| Duplex Eng-MEP-1 | **FOOT** (환산 단위) |

`IfcUnitAssignment` 을 읽지 않으면 밀리미터 모델의 좌표가 1,000배로, 피트 모델이 3.28배로
들어온다. **오류가 나지 않고 숫자가 그럴듯해서 눈으로 보기 전에는 모른다.** 지금은 읽는다
(`src/lib/ifc/units.ts`). 같은 건물의 밀리미터 판본과 피트 판본이 같은 층 높이를 주는 것으로
교차 확인한다.

### 연결(F16)은 포트가 있어야 한다

설비가 이어져 있다는 것과 **어느 쪽으로 흐르는가**는 다른 문제다. 포트마다 `FlowDirection` 이
있고, 한쪽이 SOURCE 고 다른 쪽이 SINK 여야 방향을 안다. 실제로 세어 보면 이렇다.

| 모델 | 포트 | 연결 | 흐름 방향을 아는 연결 | 방향을 아는 비율 |
|---|---|---|---|---|
| ifc4Mep (IFC4) | 4,232 | **1,995** | **1,995** | 100% |
| Duplex Eng-HVAC (IFC2x3) | 970 | 485 | **190** | 39% |
| Duplex Eng-MEP (IFC2x3) | 0 | 0 | 0 | — |

Duplex HVAC 에서 나머지 61%가 빠지는 이유는 Revit 이 피팅과 덕트의 포트를 `SOURCEANDSINK` 로
내보내기 때문이다. **이어져 있다는 것만 알고 흐름은 모른다.** 그래서 요구사항에 "포트를 넣어
달라" 가 아니라 "포트에 흐름 방향을 넣어 달라" 를 적어야 한다.

**다만 모든 포트에 방향이 있을 필요는 없다. 연결마다 한쪽만 있으면 된다.** 한쪽이 SOURCE 면
반대쪽은 SINK 일 수밖에 없기 때문이다. 저작 도구가 모든 포트를 제대로 내보내게 만드는 것보다
이쪽이 훨씬 쉬우므로, 협의에서는 완화된 쪽을 먼저 제시한다(근거: Lilis 2025, `docs/research.md`).

**방향을 아는 길이 포트만은 아니다.** 요소의 역할(소스·싱크)을 알면 소스에서 싱크로 경로를 찾아
그 경로의 변에 방향을 줄 수 있고, 역할은 IFC 클래스 계층에서 공짜로 나온다. 그런데 **우리 파일
둘에서는 안 됐다** — 소스와 싱크가 같은 연결망 조각에 들어 있는 경우가 0 이었다(MEP 34조각,
HVAC 8조각). 보일러·펌프가 배관망과 기하적으로 닿아 있지 않아서다. 그러니 `brick:feeds` 가 비는
이유는 "포트가 없어서" 가 아니라 **"포트도 없고 소스·싱크가 한 망에 있지도 않아서"** 다.
측정표는 `docs/ifc-coverage.md` 에 있다.

포트를 요소에 매다는 관계는 스키마마다 다르다. IFC2x3 은 `IfcRelConnectsPortToElement`,
IFC4 는 `IfcRelNests` 다. **한쪽만 읽으면 다른 버전 파일에서 연결이 0 이 된다** — ifc4Mep 은
`IfcRelConnectsPortToElement` 가 92건뿐이고 나머지가 전부 `IfcRelNests` 에 있다.

**포트가 아예 없는 파일은 형상으로 추정한다.** Duplex MEP 판본(원본·Solibri 최적화본 모두)은
포트도 `IfcSystem` 도 0 이다. 그런데 요소 811개에 Revit 의 `System Name` 속성이 남아 있고,
배관 끝과 피팅 끝의 메시 꼭짓점이 5mm 안에서 맞닿는다. 계통이 같은 것끼리만 이으면 연결
690개가 나오고, 계통별 연결망이 아래처럼 갈라진다.

| 계통 | 이어진 요소 |
|---|---|
| Unit A/B Hydronic Supply In | 154 · 151 |
| Unit A/B Domestic Cold Water | 69 · 70 |
| Unit A/B Domestic Hot Water | 61 · 67 |

**못 이은 것은 이유를 갈라서 말한다.** 연결이 하나도 없는 설비를 "연결 없음" 하나로 뭉치면
고객사에 할 말을 정할 수 없다. 같은 계통의 상대가 50mm 안에 있으면 판정 오차 문제이고
(**"기준을 조정하겠다"**), 주변에 아무것도 없으면 접합 부재가 모델에 없는 것이다
(**"다시 그려 달라"**). Duplex MEP 의 224대를 갈라 보면 121대가 전자, 103대가 후자다.

**추정이 얼마나 맞는지도 쟀다.** ifc4Mep 은 포트가 완전해서 정답지가 되므로, 거기에 포트를
무시하고 형상 추정만 돌려 비교했다. 기본값 5mm 에서 **정밀도 79.6% · 재현율 75.8%** 다.
오차를 1mm 로 좁히면 정밀도가 88.8%로 오르지만 재현율이 47%로 떨어지고, 50mm 로 넓히면
재현율이 94.3%까지 오르지만 정밀도가 55.1%로 무너진다. **온톨로지는 틀린 관계가 들어가는
쪽이 빠지는 쪽보다 나쁘므로 5mm 를 유지한다.** 50mm 에서도 못 찾는 113개는 접합 부재가 아예
없는 것이라 알고리즘으로 메울 수 없다. 자세한 표는 `docs/ifc-coverage.md` §4.1 에 있다.

**추정은 추정으로 남긴다.** 연결마다 출처(`port` / `geometry`)를 들고 다니고, 형상으로 추정한
연결은 방향이 없으므로 `brick:feeds` 로 내보내지 않는다. 방향을 찍어서 내보내면, 온톨로지를
읽는 쪽이 BIM 이 말한 것과 우리가 추정한 것을 구별할 수 없다. 포트가 없는 BIM 에서 TTL 의
`feeds` 절이 통째로 비는 것이 맞고, **그 빈자리가 고객사에 포트를 요구하는 근거다.**

### 받는 쪽에 무엇이 닿나 — 연결이 아니라 기기로 센다

DT 는 우리 TTL 을 `ieum-pipeline` 의 `ttl.go` 로 읽는다. 그 파서로 실제 출력을 읽혀 보니
**흐름 연결이 받는 쪽에서 전부 사라지고 있었다**(ifc4Mep 1,995개 → 0). `brick:feeds` 를 주어의
블록 밖에 독립 문장으로 썼는데, `ttl.go` 는 `ex:X a 클래스` 로 시작하는 블록만 읽는다. Turtle
로는 맞는 출력이라 문자열을 보는 테스트는 통과하고 있었다. 지금은 `check:sample` 이 진짜
`ttl.go` 를 옆 저장소에서 복사해 빌드하고 우리 출력을 읽혀 본다.

고치고 나니 둘째 문제가 보였다. **덕트·배관은 `fso:` 라서 받는 쪽이 엔티티로 읽지 않는데,
흐름은 대부분 덕트에서 출발한다.** 공조기 → 덕트까지만 닿고 토출구에는 못 닿는다. 그래서 기기
블록에 **덕트·배관을 건너뛴 하류 기기**를 함께 적는다. Brick 은 원래 덕트를 모델링하지 않고
"공조기 feeds VAV" 처럼 쓰는 것이 관례라 Brick 에도 맞다. 건너뛸 때는 포트가 방향을 말한 변만
탄다 — 이어 붙인 결과도 추정이 아니다.

그래서 흐름 방향을 **연결이 아니라 기기로** 센다. 다른 기기와 덕트·배관으로 이어진 기기 중,
흐름 방향으로 이어진(공급하거나 공급받는) 기기의 비율이다.

| 파일 | 연결 단위 방향 | **기기 단위 방향** | 왜 |
|---|---|---|---|
| ifc4Mep | 1,995/1,995 (100%) | **37/103** | 나머지 66대는 난방·오수처럼 원천 기기(보일러·펌프)가 모델에 없는 망에 형제로만 매달렸다 |
| Duplex HVAC | 190/485 (39%) | **0/26** | 기기에서 출발한 방향 사슬이 전부 중간의 `SOURCEANDSINK` 에서 끊긴다 |
| Duplex MEP | 0/785 | **0/31** | 포트가 없다. 형상 추정은 방향이 없다 |

**연결 단위로 말하면 DT 가 받는 것을 크게 부풀리게 된다.** HVAC 는 "39%" 로 보이지만 DT 에서
"이 토출구는 어느 공조기 담당인가" 에 답할 수 있는 기기가 하나도 없다. 요구사항 R18 의 근거가
이 표다 — 포트에 방향을 넣되, **원천 기기에서 말단까지 사슬이 끊기지 않아야** 한다.

받는 쪽에 남은 어긋남이 하나 있다. **GUID 의 `$` 는 Turtle 규칙상 `\$` 로 써야 하는데 `ttl.go`
가 이스케이프를 풀지 않는다.** 그래서 ieum 의 키에 역슬래시가 남고 GeoJSON 의 id 와 이어지지
않는다(GUID 는 64자 알파벳이라 22자 중 `$` 가 하나라도 들어갈 확률이 약 30%다). 우리 쪽에서는
못 피하고, `ttl.go` 가 키의 `\X` 를 `X` 로 풀어야 한다. `check:sample` 이 이 어긋남을 박아 두고
있어서 저쪽이 고치면 바로 보인다.

### 건축과 설비를 합쳐야 F11 이 나온다

위 표의 첫째 관찰을 실제로 해 봤다. Duplex 의 건축 판본과 설비 판본을 합친다(`src/lib/merge.ts`).

**층은 GUID 가 아니라 이름으로 맞춰야 한다.** 같은 건물인데 층 GlobalId 가 판본마다 다르다
(건축 `1xS3BCk…`, 설비 `0o8nNAb…`). 이름(Level 1·Level 2·Roof)과 높이(0·3.1·6.0m)는 같았다.
좌표계도 같았다 — 설비 498대가 전부 건축 모델의 공간 범위 안에 들었다.

| 합친 것 | 합치기 전 | 합친 뒤 |
|---|---|---|
| 건축 + HVAC | 물리존 1, **기기 40대 전부 미소속** | 물리존 21, **기기 40대 전부 소속** |
| 건축 + MEP | 물리존 42 (**같은 방이 두 번**) | 물리존 21, BIM 이 말한 소속 167건 보존 |
| FZK-Haus + ifc4Mep (다른 건물) | — | 설비 2% 만 겹쳐 **"좌표계가 다르다" 경고** |

셋째 줄이 요구사항 "건축과 설비가 같은 좌표계" 의 근거다. 다른 건물을 합쳐도 **오류는 안
난다.** 층 높이 0 끼리는 짝까지 지어진다. 좌표가 겹치는지를 따로 재지 않으면 설비 2,202대가
전부 미소속으로 나오는 것만 보고 원인을 모른다.

두 가지를 합치면서 알았다.

- **Revit 설비 판본에는 방이 두 벌 들어 있다.** "MEP Space" 21개와 건축 Room 의 사본 21개다.
  설비 판본 하나만 열어도 온톨로지에 같은 방이 두 번 나간다. 합칠 때 같은 자리의 방은 하나만
  남기고(안쪽 점이 이미 있는 방에 드는가), 빈자리를 채우는 방은 받는다. 건축 판본의 복도 둘은
  외곽선이 없었는데(SurfaceModel), 같은 방 번호의 외곽선을 설비 판본에서 빌려 온다.
- **Revit IFC2x3 의 덕트 구간은 배치점이 층 원점이다.** HVAC 의 구간 231개가 전부 (0, 0) 이었다.
  형상은 제자리다. 이대로 판정하면 **원점이 든 방 하나에 덕트가 전부 몰린다** — Duplex 는 원점이
  건물 밖이라 "미소속" 으로 끝났을 뿐이다. 배치점이 자기 형상에서 0.5m 넘게 떨어지면 형상 중심을
  좌표로 쓰고, 몇 대를 고쳤는지 경고로 남긴다.

### F11 은 얼마나 맞나 — BIM 이 말한 소속을 정답지로

Duplex MEP 판본은 설비 167대를 `IfcSpace` 에 직접 매달아 두었다. 설계자가 적은 소속이니
정답지가 된다. 그 말을 가리고 좌표로만 판정해서 대 봤다.

| 판정 | 맞음 | 어느 방에도 안 듦 | 다른 방 |
|---|---|---|---|
| 점이 외곽선 안에 드는가 | 122 (**73.1%**) | 43 | 2 |
| + 외곽선 5cm 안이면 가장 가까운 방 | 160 (**95.8%**) | 5 | 2 |

**빠진 43대는 벽에 붙은 설비다.** 콘센트·스위치의 좌표가 정확히 벽면, 곧 방 외곽선 위에
있어서 점-다각형 판정이 떨어뜨린다(외곽선까지 거리 중앙값 0mm). 여유를 2cm·5cm·10cm·30cm 로
쓸어 보면 5cm 에서 포화하고, 30cm 까지 넓혀도 "다른 방" 은 2대 그대로다. 그래도 5cm 로 둔다 —
그 위로는 정답지가 없는 벽 속 배관만 더 붙는데, 그게 어느 쪽 방인지는 맞았는지 잴 수 없다.

같은 이유로 **합칠 때 BIM 이 말한 소속은 다시 판정하지 않는다.** 겹쳐서 뺀 방을 가리키면 같은
자리의 남은 방으로 옮겨 적는다. 처음에 좌표로 다시 판정했다가 말단 105대 중 41대의 소속을 잃었다.

### 어디까지 넓힐 수 있나 — 등급

고객사 파일을 받았을 때 **"이 BIM 으로는 여기까지 나옵니다" 를 한 줄로 말하기 위한 표**다.
위 등급은 아래 등급을 전제한다. 0+ 와 4+ 는 옆으로 붙는 확장이라 번호를 끼워 넣었다.

| 등급 | 온톨로지에 나오는 것 | 필요한 IFC | 도달한 샘플 |
|---|---|---|---|
| **0. 공간 골격** | F1–F7. 층, 물리존 외곽선, 이름, 벽·문·창, 공간 경계 | `IfcBuildingStorey`, `IfcSpace`(FootPrint 또는 SweptSolid), 벽·개구부, 배치 사슬, 단위 선언 | AC20-FZK-Haus, Duplex 건축 |
| **0+. 공간 의미** | 방 종류, 방 높이, 방-문-방 연결 | 방 분류(OmniClass 또는 `PredefinedType`), 공간 수량 `Height`, 문이 걸린 `IfcRelSpaceBoundary` | 재료는 샘플에 있다(아래 표). **코드가 아직 안 읽는다** |
| **1. 설비 목록** | + F8·F9. 설비 역할·이름·좌표 | `IfcDistributionElement` + 형상 위에 놓인 배치점 | Duplex MEP·HVAC, ifc4Mep |
| **2. 설비 소속** | + F11. `brick:hasLocation` | `IfcSpace` 가 같은 파일에 있거나, 다른 파일이면 **같은 좌표계와 같은 층 이름** | Duplex MEP(기기 141/141), Duplex 건축+HVAC(기기 40/40) |
| **3. 계통·연결망** | + F10·F16(방향 없음) | `IfcSystem` 또는 Revit `System Name`, 맞닿는 솔리드 | Duplex MEP(연결 785) |
| **4. 흐름 방향** | + F16(방향 있음). `brick:feeds` | 포트 + SOURCE/SINK, 원천 기기에서 말단까지 끊기지 않는 사슬 | **ifc4Mep 만.** 연결 1,995/1,995, 기기 단위 37/103 |
| **4+. 담당 공간(근사)** | 공조기 → 같은 계통의 말단 → 말단이 있는 방 | `IfcSystem` 이 공조기와 말단을 **같이** 묶을 것 + 등급 2 | **없다.** ifc4Mep 은 계통 2/37 이 조건을 갖췄는데 방이 없고, Duplex 는 방이 있는데 계통이 기기와 말단을 따로 묶었다(0/34) |
| **5. 운영** | + F12·F13. 공조존, 관제점 | IDF·gbXML·BAS. IFC 에 자리(`IfcZone`, `IfcRelFlowControlElements`)는 있으나 **실측 값 0** | 없다 |

**대부분의 고객사 BIM 은 1~3 등급에서 멈출 것이다.** 4 는 포트를 의식하고 내보낸 파일에서만
나왔고, 4+ 와 5 는 지금 샘플 중 어느 것도 닿지 못했다. 4+ 는 BIM 이 조금만 더 주면 되는
자리라서(계통에 공조기를 같이 넣는 것) 요구사항으로 당길 값어치가 있다.

### 넓힐 수 있는데 아직 안 한 것

IFC 에 자리가 있는지, 실제 파일이 채웠는지, 우리 코드가 읽는지를 따로 적는다. 마지막 열이
중요하다 — **기존 온톨로지가 쓰는 술어가 `feeds`·`hasLocation`·`hasPart`·`hasPoint` 넷뿐이라**
(§5), 클래스로 나가는 확장은 공짜지만 새 술어가 필요한 확장은 `ieum-pipeline` 과 먼저 맞춰야 한다.

| 확장 | DT 가 쓰는 곳 | IFC 의 자리 | 실측 | 지금 | 어디로 나가나 |
|---|---|---|---|---|---|
| 방 종류 | Agent 의 "회의실", 탐색기 | `IfcSpace.PredefinedType`, OmniClass Table 13 속성 | `PredefinedType` 0/4 파일. OmniClass Duplex 건축 **21/21**, AC20 0/7 | 전부 `brick:Room` | TTL 클래스. 술어가 안 늘어난다 |
| 방 높이 | 3D Map(복층·층고) | `Qto_SpaceBaseQuantities.Height` | AC20 **7/7**(2.5m·4m) | 층 높이만 | GeoJSON |
| 방-문-방 연결 | 로봇 경로, 피난 | 문이 걸린 `IfcRelSpaceBoundary` | 두 방을 잇는 문 AC20 3/5, Duplex 건축 **9/14**. COBie 판본은 경계가 없어 0 | 안 읽는다 | **새 술어가 필요하다** — 정해야 한다 |
| 벽·문·창 위치 | 3D Map, 로봇 | `ObjectPlacement` + 형상 | 확인한 파일 전부 있다 | **안 읽는다**(두께·치수만) | GeoJSON |
| 설비 종류 → Brick 클래스 | 이상 알림 분류, Agent | IFC4 구체 클래스·`PredefinedType`. IFC2x3 은 `ObjectType` 문자열뿐 | `PredefinedType` 말단 기준 0%. ifc4Mep 은 구체 클래스가 있다 | IFC4 클래스 9개만 Brick, 나머지 `ex:FlowTerminal` 등 | TTL 클래스 |
| 유체 종류 | 계통도(냉수·온수·급수·오수) | Revit `System Type` 속성 | Duplex MEP 811/926 | 안 읽는다(`System Name` 만) | TTL 계통 클래스 |
| 자산 정보 | 자산 관리, 유지보수 | COBie 속성(시리얼·보증·수명) | Duplex MEP **926/926** | 안 읽는다 | 온톨로지 밖(자산 대장)이거나 새 술어 — 정해야 한다 |
| 담당 공간(근사) | 계통도 "이 공조기가 담당하는 방" | `IfcSystem`(기기+말단) + F11 | 조건을 갖춘 파일 0 | 안 한다 | 추정이라 `brick:feeds` 로 내면 안 된다 — 표기를 정해야 한다 |
| 공조존 | 계통도, 용량 검증(Z-03) | `IfcZone`, `IfcSpatialZone`, `VentilationZoneName` | 자리는 있다. **값은 0**(템플릿 기본값, `IfcZone` 은 세대 구분) | 안 읽는다 | `brick:Zone` |
| 센서가 재는 설비 | `brick:hasPoint` 의 주인 | `IfcRelFlowControlElements` | ifc4Mep 센서 7, 관계 **0** | 센서를 설비로 읽는다 | `brick:hasPoint` |
| 지도 좌표 | 3D 스캔·GIS 정합 | `IfcMapConversion`(LoGeoRef 50) | **0/4.** 위경도(`IfcSite`, LoGeoRef 20)만 있다 | 안 읽는다 | GeoJSON 변환 |

수치는 전부 `npm run check:sample` 의 "확장 여지" 항목에 박혀 있다.

## 3. 고객사 BIM 요구사항

### 무엇을 필수라 부르나

**필수는 등급 0·1·2 를 여는 것이다.** 탐색기 트리(공간 계층), 3D Map(외곽선), 이상 알림의 발생
위치(설비 소속)가 이 셋에 걸려 있고, DT 가 첫날 쓰는 화면이 전부 여기다. 등급 3 이상을 여는 것은
권장이고, 없으면 무엇이 안 되는지로 협의한다. 등급 5 의 본체(관제점 ID, 실시간 값)는 IFC 밖이라
요구사항에 넣지 않는다. 다만 IFC 에 자리가 있는 공조존·센서 관계(R20·R21)는 권장으로 당긴다.

**요구는 검사할 수 있는 말로 쓴다.** "닫힌 경계", "공유 좌표" 로 쓰면 고객사도 우리도 통과
여부를 판정할 수 없다. 그래서 확인할 IFC 엔티티·속성을 같이 적고, 우리 샘플이 통과했는지를
옆에 둔다. 확인할 자리가 IFC 속성이면 IDS 로 옮길 수 있고, 기하면 우리가 열어 봐야 한다.

길어진다.

### 요구사항을 파일로 확인하는 방법

필수와 권장의 설비 쪽을 담은 IFC4 파일이 `src/lib/ifc/fixtures/mep.ifc` 에 있다. 설비마다 좌표가
있고, 용량 파라미터가 붙고, `IfcSystem` 으로 묶이고, 포트로 연결된다. 빠진 경우도 일부러 넣어
두었다. 용량이 없는 토출구가 하나 있고, 좌표가 없는 센서가 하나 있다. 문서로 설명하는 대신 이
파일을 받아서 우리 임포터에 넣어 보면 무엇이 되고 무엇이 안 되는지 그대로 보인다.

다음 단계는 "확인하는 자리" 가 IFC 속성인 요구(R1·R3·R6·R10·R14·R15·R17·R18·R20~R24)를
`docs/requirements.ids` 로 옮기는 것이다. 기하로만 볼 수 있는 R2·R7·R8·R11·R12·R16 은 IDS 로
못 쓰고 우리가 열어 봐야 한다.

## 4. 편집 기능

편집은 3D 모델을 고치는 일이 아니라 **온톨로지를 고치는 일**이다. 차이는 한 번의 편집이 무엇을
무효로 만드는가에 있다. 벽을 하나 옮기면 물리존 경계가 바뀌고, 경계가 바뀌면 그 안에 있던 설비의
소속이 바뀌고, 소속이 바뀌면 이상 알림의 발생 위치와 탐색기 트리가 같이 바뀐다. 편집기가 할 일은
그 연쇄를 빠뜨리지 않고 다시 계산하는 것이다.

### 무엇을 고칠 수 있어야 하나

| # | 편집 | 바뀌는 피처 | 다시 계산해야 하는 것 |
|---|---|---|---|
| E1 | 물리존 이름 수정 | F3 | 없다 |
| E2 | 물리존 경계 수정 | F2 | F11 설비 소속, 면적 |
| E3 | 물리존 생성·삭제·분할·병합 | F1, F2 | F11 설비 소속, 공간 계층 |
| E4 | 벽·문·창 추가·삭제·이동 | F4, F5 | F2 물리존 경계, F15 로봇 통과 |
| E5 | 설비 이동 | F9 | F11 설비 소속 |
| E6 | 미배치 설비 배치 | F9 | F11 설비 소속 |
| E7 | 설비 추가·삭제·이름 수정 | F8 | F10 계통, F13 관제점 연결 |
| E8 | 계통 연결 수정 | F10 | 공조존 담당 관계 |
| E9 | 공조존 경계·담당 수정 | F12 | 계통도, serviceSpace |
| E10 | 커스텀존 지정 | F14 | Agent 질의 대상 |
| E11 | 관제점 ID 수정 | F13 | 없다 |

**E2 와 E5 가 편집기의 성격을 드러낸다.** 둘 다 결과가 화면에서 똑같아 보이지만, 온톨로지에서는
`brick:hasLocation` 한 줄이 바뀐다. 그 한 줄이 이상 알림의 발생 위치다. 편집기가 3D 모델 편집기와
다른 지점이 여기다.

**E11 은 BIM 과 무관하다.** 관제점은 BAS 에서 오고 설비의 관제점이 교체되는 일이 실제로 생기므로,
BIM 을 다시 받지 않고도 ID 를 고칠 수 있어야 한다.

### 편집기가 갖춰야 할 성질

| 성질 | 이유 |
|---|---|
| 편집 전후의 차이를 보여 준다 | 무엇이 바뀌는지 모르고 반영하면 되돌릴 근거가 없다 |
| 부분 반영을 만들지 않는다 | 기하만 바뀌고 의미가 안 바뀌면 두 파일이 어긋난다 |
| 되돌릴 수 있다 | 재계산이 잘못되면 이전 판으로 돌아가야 한다 |
| 재임포트와 편집분을 구분한다 | BIM 을 다시 받을 때 손으로 고친 것을 덮어쓰면 안 된다 |
| 한 층을 한 사람만 편집한다 | 같은 층을 둘이 고치면 재계산 결과가 갈린다 |

마지막 둘은 PRD #15 에서 #19 에 해당하며 저장 위치가 정해져야 구현할 수 있다. 앞의 셋은 저장
위치와 무관하므로 먼저 만든다.

### 지금 만든 범위

E1, E2, E5, E6 을 만들었다. 셋 다 같은 골격 위에 있다. 값을 고치고, 설비 소속을 다시 판정하고,
무엇이 바뀌었는지를 돌려준다.

E2 가 그중 가장 넓게 번진다. 물리존의 꼭짓점 하나를 옮기면 넓이가 다시 계산되고, 경계 밖으로
밀려난 설비의 `brick:hasLocation` 이 바뀐다. 실제로 확인한 모습은 이렇다.

```
사무실의 오른쪽 두 꼭짓점 x 를 10 에서 5 로

  사무실  80.0㎡ → 40.0㎡
  AT-101-02  사무실 → (소속 없음)      좌표 (7,4) 가 경계 밖으로 나갔다
  LIGHT-101-01  사무실 그대로           BIM 이 소속을 말해 둔 설비다
```

마지막 줄이 이 설계의 요점이다. BIM 이 소속을 명시한 설비는 좌표가 경계 밖이어도 소속을 지킨다.
설계자가 정한 값이 좌표 판정보다 정확하기 때문이다.

다각형이 자기 자신과 교차하면 알리되 막지는 않는다. 꼭짓점을 끌다 보면 잠깐 교차했다가 풀리는
일이 흔해서, 그때마다 조작을 되돌리면 편집을 할 수 없다.

## 5. BIM 이 못 주는 것을 어디서 채우나

| 피처 | 출처 | 비고 |
|---|---|---|
| F12 공조존 | IDF 또는 gbXML | 없으면 설비 담당 지정으로 수동 생성한다(PRD #11). BIM 이 `IfcZone` 에 실제 공조존을 담아 주면 여기서 받을 수 있다 |
| F13 관제점 | BAS | 설비 ID 와 관제점 ID 를 잇는 작업이 따로 필요하다. 센서가 어느 설비를 재는지(`IfcRelFlowControlElements`)는 BIM 이 줄 수 있는 자리가 있으나 실측 0 이다 |
| F14 커스텀존 | 운영자 | 물리존 위에 다각형으로 지정한다 |
| F11 설비 소속 물리존 | 계산 | 좌표와 외곽선으로 판정한다. 편집·합치기 때마다 다시 돌아야 한다. 설비 파일에 방이 없으면 건축 파일과 합쳐야 한다 |
| 좌표 정합 | 3D 스캔 대조 | BIM 의 공유 좌표가 스캔과 맞는지 임포트 단계에서 확인한다 |

기존 SR 온톨로지는 설비와 관제점만 있고 기하가 없다. 술어가 `feeds`, `hasLocation`, `hasPart`,
`hasPoint` 넷뿐이며 좌표가 하나도 들어 있지 않다. BIM 이 채우는 것이 정확히 그 빠진 절반이므로,
둘을 합칠 때 어느 쪽 ID 를 기준으로 삼을지를 먼저 정해야 한다.

| 기기와 도관 구분 | 된다. IFC 클래스 계층에서 역할을 읽어 기기와 덕트·배관을 따로 센다. 도관은 Brick 이 아니라 `fso:Segment`·`fso:Fitting` 으로 나간다 |
| 내보내기 | 된다. 기하는 GeoJSON, 의미는 Brick TTL 로 나간다. 방향을 아는 연결만 `brick:feeds` 로, 기기에는 덕트를 건너뛴 하류 기기까지 나간다. **실제 `ttl.go` 로 읽히는지 `check:sample` 이 본다.** GUID 의 `$` 키 어긋남은 `ttl.go` 쪽에서 풀어야 한다 |
| 길이 단위 변환 | 된다. 미터·밀리미터·피트를 확인했다 |
| 벽 두께, 개구부 치수, 공간 경계(F4, F5, F6) | 된다. **벽·문·창의 위치는 안 읽는다** — 3D Map 과 로봇 경로가 이것을 기다린다 |
| 파일 목록의 등급 칩 | 된다. dev 서버가 앱과 같은 임포터로 파일마다 공간·설비·소속·연결망·방향을 재서 목록에 보인다. 못 여는 파일은 이유와 함께 "열 수 없음" |
| 3D 로 확인 | 된다. 설비·배관을 실제 형상으로 그리고, 계통별로 색을 나누고, 고른 설비의 상류·하류를 칠한다 |
| 건축 모델과 설비 모델 합치기 | 된다. 층은 이름으로 맞추고, 좌표계가 어긋나면 경고한다. Duplex 건축+HVAC 에서 기기 40대 전부 소속 |
| 로봇 통과 여부(F15) | 개구부 하나의 통과 여부까지 된다. 방-문-방 연결 그래프는 아직이다(공간 경계에 재료는 있다) |
| 편집 | E1, E2, E5, E6 만 있다 |
| 공조존(F12) | 손도 대지 않았다. IDF 에서 받는 것이 기본이다. IFC 의 자리(`IfcZone`)는 실측 파일이 비워 둬서 읽을 것이 없다 |

## 7. 수치를 다시 재는 방법

```bash
npm run fetch:sample   # 실측 샘플을 data/ 로 받는다
npm run check:sample   # 개수와 넓이를 기준값과 대조한다

```

설비가 든 모델인지 세어 보려면 다음과 같이 한다.

```bash
grep -oE "^#[0-9]+= *IFC[A-Z0-9]+" 모델.ifc | sed -E 's/.*= *//' | sort | uniq -c | sort -rn | head -30
```

기존 SR 온톨로지의 클래스와 술어를 세는 방법은 다음과 같다.

```bash
F=~/git/dt/ieum-pipeline/data/ontology/SR_Building_ontology_260723.ttl
grep -oE '\ba\s+(brick|ex):[A-Za-z_]+' $F | awk '{print $2}' | sort | uniq -c | sort -rn | head
grep -oE '\b(brick|rdfs):[a-z][A-Za-z_]*' $F | sort -u
```
