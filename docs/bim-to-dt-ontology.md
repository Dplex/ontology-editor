# BIM 으로 DT 온톨로지를 어디까지 만들 수 있나

이 문서는 세 가지에 답한다.

1. DT 가 쓰려면 온톨로지에 무엇이 있어야 하는지를 정한다(피처 정의).
2. 그중 BIM 이 줄 수 있는 것이 어디까지인지를 실측으로 적는다.
3. 그러려면 고객사 BIM 에 최소한 무엇이 들어 있어야 하는지를 적는다.
4. 만들어진 온톨로지를 고치는 편집 기능이 무엇을 제공해야 하는지를 정한다.

BIM 으로 만드는 일과 만든 것을 고치는 일은 한 벌이다. BIM 이 못 주는 피처가 절반이고 BIM 이
주는 것도 현장과 어긋나므로, 편집이 없으면 온톨로지가 처음 한 번만 맞고 그 뒤로는 틀려 간다.

근거가 되는 수치는 전부 이 저장소의 코드로 다시 잴 수 있다. 재는 방법은 마지막 절에 있다.

기준일: 2026-09-22 · 관련 문서: `[DT2.0] PRD_011(온톨로지 구축 자동화 플랫폼)`

곁가지 둘을 따로 뺐다. **`docs/ifc-coverage.md`** 는 IFC 가 주는 것을 파일별로 잰 지도이고
(확장 등급표와 요구 항목의 지렛대 순서가 거기 있다), **`docs/research.md`** 는 선행 연구에서
무엇을 가져왔고 무엇이 우리 파일에서 안 됐는지의 기록이다. 이 문서가 정본이고 둘은 근거다.

## 1. DT 온톨로지의 피처

피처를 먼저 정하는 이유는 이것이 BIM 요구사항을 결정하기 때문이다. DT 의 어느 화면이 무엇을
묻는지를 적으면, 온톨로지가 들고 있어야 할 관계가 따라 나온다. 그 관계를 BIM 이 주는지 아닌지가
다음 절의 답이 된다.

### DT 가 온톨로지에 묻는 질문

| 소비처 | 질문 | 답하는 데 필요한 관계 |
|---|---|---|
| 이상 알림 | 이 설비는 어디서 났는가 | 설비 → 물리존 |
| 탐색기 트리 | 건물이 어떤 구조인가 | 사이트 → 건물 → 층 → 물리존 |
| 3D Map | 이 공간을 어떻게 그리는가 | 물리존의 외곽선과 높이 |
| 계통도 | 이 공조기가 담당하는 공간은 어디인가 | 설비 → 계통 → 공조존 |
| AI Agent | 회의실 온도가 몇 도인가 | 공간 이름 → 설비 → 관제점 |
| 로봇 관제 | 이 경로로 지나갈 수 있는가 | 벽·문·창의 통과 가능 여부 |

### 피처 목록

각 피처에 출처를 함께 적는다. **출처가 BIM 이 아닌 것이 절반이라는 점이 이 표의 요점이다.**

| # | 피처 | 관계·속성 | 출처 |
|---|---|---|---|
| F1 | 공간 계층 | `brick:hasPart` (사이트 > 건물 > 층 > 물리존) | BIM |
| F2 | 물리존 기하 | 외곽선 다각형, 면적, 층 높이 | BIM |
| F3 | 공간 이름 | `rdfs:label`, 방 번호 | BIM |
| F4 | 벽·문·창 형상 | 위치, 두께, 개구부 치수 | BIM |
| F5 | 개구부 소속 | 어느 벽에 난 문인가 | BIM |
| F6 | 공간 경계 | 이 물리존을 둘러싼 부재는 무엇인가 | BIM |
| F7 | 내력벽 | `loadBearing` | BIM (속성을 기입한 경우에만) |
| F8 | 설비 목록 | 종류, 이름, 용량 | BIM (MEP 를 포함한 경우에만) |
| F9 | 설비 위치 | x·y·z, 설치면 | BIM (MEP 를 포함한 경우에만) |
| F10 | 계통 | 공조기 → 덕트 → 토출구 | BIM (MEP 를 포함한 경우에만) |
| F11 | 설비 소속 물리존 | `brick:hasLocation` | **계산으로 만든다** |
| F12 | 공조존 | `brick:Zone`, 담당 관계 | IDF 또는 gbXML |
| F13 | 관제점 | `brick:hasPoint` | BAS |
| F14 | 커스텀존 | 운영자가 지정하는 다각형 | 사용자 |
| F15 | 로봇 통과 여부 | 문은 통과, 창문과 벽은 불가 | F4 에서 파생 |
| F16 | 설비 연결(상류·하류) | `brick:feeds` | BIM (포트에 흐름 방향이 있는 경우에만) |

**F11 이 이 과제의 핵심이다.** BIM 은 설비의 좌표를 주고 물리존의 외곽선을 주지만, "이 공조기가
회의실에 있다" 는 말은 하지 않는다. 그 관계는 좌표가 어느 외곽선 안에 드는지를 계산해서 만든다.
이것이 없으면 이상 알림이 발생 위치를 표시하지 못하고, 탐색기 트리에 설비가 걸리지 않는다.

**F12 와 F13 은 BIM 에서 나오지 않는다.** 공조존은 에너지 시뮬레이션 개념이라 IDF 나 gbXML 에
있고, 관제점은 BAS 가 들고 있다. BIM 만으로 온톨로지를 완성할 수 없다는 뜻이며, BIM 은 공간
골격과 설비 목록까지를 맡는다.

## 2. BIM 으로 어디까지 되는가

세 가지를 구분해서 적는다. 규격이 담을 수 있는 것과 우리가 뽑는 것과 실제 파일에 들어 있는 것이
서로 다르기 때문이다.

| 피처 | IFC4 규격 | 지금 임포터 | 실측 샘플(AC20-FZK-Haus) |
|---|---|---|---|
| F1 공간 계층 | `IfcBuildingStorey`, `IfcSpace` | 읽는다 | 층 2, 물리존 7 |
| F2 물리존 기하 | `FootPrint` 또는 `Body` 표현 | `FootPrint` + `Body/SweptSolid` 를 읽는다 | 7개 전부 추출, Buero 12.985㎡ |
| F3 공간 이름 | `Name`, `LongName` | 읽는다 | Schlafzimmer, Bad, Buero 등 7개 |
| F4 벽·문·창 | `IfcWall`, `IfcDoor`, `IfcWindow` | 개수와 이름만 읽는다 | 벽 13, 문 5, 창 11 |
| F4 벽 두께 | `IfcMaterialLayerSetUsage` | 읽는다 | 13장 전부. 내벽 0.24m · 외벽 0.3m |
| F4 개구부 치수 | `OverallHeight`, `OverallWidth` | 읽는다 | 16개 전부. 문 2.01 x 0.885m |
| F5 개구부 소속 | `IfcRelVoidsElement` + `IfcRelFillsElement` | 읽는다 | 16개 전부 벽에 이어짐 |
| F6 공간 경계 | `IfcRelSpaceBoundary` | 읽는다 | 7개 물리존 · 경계 66면 |
| F15 로봇 통과 | F4 에서 파생 | 읽는다 | 문 5개만 통과 가능 |
| 길이 단위 | `IfcUnitAssignment` | 읽어서 미터로 환산한다 | 미터 · 밀리미터 · 피트를 확인 |
| F7 내력벽 | `Pset_WallCommon.LoadBearing` | 읽는다 | **0 / 13. 속성 자체가 없음** |
| F8 설비 | `IfcDistributionElement` 하위 | 읽는다 | **0** |
| F9 설비 위치 | `ObjectPlacement` | 읽는다 | 해당 없음 |
| F10 계통 | `IfcSystem` + `IfcRelAssignsToGroup` | 읽는다 | **0** |
| F11 설비 소속 | 규격에 없다 | 계산해서 만든다 | 해당 없음 |
| F12 공조존 | **IFC 에 없다** | 해당 없음 | 없음 |
| F13 관제점 | **IFC 에 없다** | 해당 없음 | 없음 |

정리하면 이렇다.

- **공간 골격은 BIM 으로 충분히 만들어진다.** 층, 물리존, 외곽선, 면적, 이름이 전부 나온다.
  좌표 변환까지 포함해 실제 모델로 확인했다.
- **벽 두께, 개구부 치수, 공간 경계까지 읽는다.** 특히 `IfcRelSpaceBoundary` 는 물리존을 둘러싼
  부재를 BIM 이 직접 알려 주므로, 벽을 고칠 때 영향받는 물리존을 기하 연산 없이 찾을 수 있다.
- **설비는 파일에 들어 있어야 읽을 수 있고, 실제로는 대부분 없다.** 이것이 가장 큰 제약이다.

### 설비가 든 BIM 은 따로 있다

공개 샘플을 여러 곳에서 모아 확인한 결과, 설비는 **건축 모델과 다른 파일에 들어 있었다.**
같은 프로젝트라도 디스플린마다 파일이 갈린다.

| 모델 | 출처 | 스키마 | 물리존 | 설비 | 계통 | 포트 |
|---|---|---|---|---|---|---|
| AC20-FZK-Haus | web-ifc 테스트 모델 | IFC4 | 7 | 0 | 0 | 0 |
| C20-Institute-Var-2 | web-ifc 테스트 모델 | IFC4 | 82 | 0 | 0 | 0 |
| Office_A | web-ifc 테스트 모델 | IFC2x3 | 99 | 31 | 0 | 0 |
| dental_clinic | web-ifc 테스트 모델 | IFC2x3 | 269 | 102 | 0 | 0 |
| **ifc4Mep** | opensourceBIM/TestFiles | **IFC4** | 0 | **2,202** | **37** | **4,232** |
| Duplex COBie Design | NIBS · DURAARK | IFC2x3 | 22 | 133 | **10** | 0 |
| Duplex Eng-HVAC | NIBS · DURAARK | IFC2x3 | 1 | 498 | 0 | **970** |
| Duplex Eng-MEP | NIBS · DURAARK | IFC2x3 | 1 | 926 | 0 | 0 |

여기서 네 가지를 읽을 수 있다.

첫째, **건축 모델에는 설비가 없고 설비 모델에는 물리존이 없다.** 위 표에서 두 값이 동시에 큰
행이 하나도 없다. F11 설비 소속 물리존을 만들려면 두 파일을 합쳐야 하고, 합치려면 두 파일이
같은 좌표계를 써야 한다. 공유 좌표를 요구사항에 넣는 이유가 이것이다.

둘째, **계통이 든 파일은 드물고 종류가 둘이다.** `ifc4Mep` 은 `IfcDistributionSystem` 으로
37개를 담았고, Duplex 는 **COBie 판본에만** 10개가 있었다. COBie 는 시설관리 인수용 규격이라
계통과 자산 정보를 함께 담는다. 우리 용도와 목적이 같으므로, 고객사에 요구할 때 "IFC 에 MEP 를
포함" 만 적지 말고 **계통 정보를 함께 요구하는 편이 확실하다.**

셋째, **포트가 있으면 연결 관계를 알 수 있다.** `ifc4Mep` 은 포트 4,232개와
`IfcRelConnectsPorts` 2,024건을 담았다. 어느 덕트가 어느 토출구에 붙는지가 파일에 그대로 있다.
계통이 없어도 포트만 있으면 연결을 되살릴 수 있다. 다만 **포트가 있다고 흐름 방향까지 아는 것은
아니다** — 아래 2.3 에서 잰다.

넷째, **길이 단위가 파일마다 다르다.** 확인한 네 파일 중 둘은 미터가 아니었다.

| 모델 | 선언된 길이 단위 |
|---|---|
| AC20-FZK-Haus | METRE |
| ifc4Mep | METRE |
| Duplex Eng-HVAC | **MILLIMETRE** |
| Duplex Eng-MEP-1 | **FOOT** (환산 단위) |

`IfcUnitAssignment` 을 읽지 않으면 밀리미터 모델의 좌표가 1,000배로, 피트 모델이 3.28배로
들어온다. **오류가 나지 않고 숫자가 그럴듯해서 눈으로 보기 전에는 모른다.** 지금은 읽는다
(`src/lib/ifc/units.ts`). 같은 건물의 밀리미터 판본과 피트 판본이 같은 층 높이를 주는 것으로
교차 확인한다.

### 연결(F16)은 포트가 있어야 한다

설비가 이어져 있다는 것과 **어느 쪽으로 흐르는가**는 다른 문제다. 포트마다 `FlowDirection` 이
있고, 한쪽이 SOURCE 고 다른 쪽이 SINK 여야 방향을 안다. 실제로 세어 보면 이렇다.

| 모델 | 포트 | 연결 | 흐름 방향을 아는 연결 | 방향을 아는 비율 |
|---|---|---|---|---|
| ifc4Mep (IFC4) | 4,232 | **1,995** | **1,995** | 100% |
| Duplex Eng-HVAC (IFC2x3) | 970 | 485 | **190** | 39% |
| Duplex Eng-MEP (IFC2x3) | 0 | 0 | 0 | — |

Duplex HVAC 에서 나머지 61%가 빠지는 이유는 Revit 이 피팅과 덕트의 포트를 `SOURCEANDSINK` 로
내보내기 때문이다. **이어져 있다는 것만 알고 흐름은 모른다.** 그래서 요구사항에 "포트를 넣어
달라" 가 아니라 "포트에 흐름 방향을 넣어 달라" 를 적어야 한다.

**다만 모든 포트에 방향이 있을 필요는 없다. 연결마다 한쪽만 있으면 된다.** 한쪽이 SOURCE 면
반대쪽은 SINK 일 수밖에 없기 때문이다. 저작 도구가 모든 포트를 제대로 내보내게 만드는 것보다
이쪽이 훨씬 쉬우므로, 협의에서는 완화된 쪽을 먼저 제시한다(근거: Lilis 2025, `docs/research.md`).

**방향을 아는 길이 포트만은 아니다.** 요소의 역할(소스·싱크)을 알면 소스에서 싱크로 경로를 찾아
그 경로의 변에 방향을 줄 수 있고, 역할은 IFC 클래스 계층에서 공짜로 나온다. 그런데 **우리 파일
둘에서는 안 됐다** — 소스와 싱크가 같은 연결망 조각에 들어 있는 경우가 0 이었다(MEP 34조각,
HVAC 8조각). 보일러·펌프가 배관망과 기하적으로 닿아 있지 않아서다. 그러니 `brick:feeds` 가 비는
이유는 "포트가 없어서" 가 아니라 **"포트도 없고 소스·싱크가 한 망에 있지도 않아서"** 다.
측정표는 `docs/ifc-coverage.md` 에 있다.

포트를 요소에 매다는 관계는 스키마마다 다르다. IFC2x3 은 `IfcRelConnectsPortToElement`,
IFC4 는 `IfcRelNests` 다. **한쪽만 읽으면 다른 버전 파일에서 연결이 0 이 된다** — ifc4Mep 은
`IfcRelConnectsPortToElement` 가 92건뿐이고 나머지가 전부 `IfcRelNests` 에 있다.

**포트가 아예 없는 파일은 형상으로 추정한다.** Duplex MEP 판본(원본·Solibri 최적화본 모두)은
포트도 `IfcSystem` 도 0 이다. 그런데 요소 811개에 Revit 의 `System Name` 속성이 남아 있고,
배관 끝과 피팅 끝의 메시 꼭짓점이 5mm 안에서 맞닿는다. 계통이 같은 것끼리만 이으면 연결
690개가 나오고, 계통별 연결망이 아래처럼 갈라진다.

| 계통 | 이어진 요소 |
|---|---|
| Unit A/B Hydronic Supply In | 154 · 151 |
| Unit A/B Domestic Cold Water | 69 · 70 |
| Unit A/B Domestic Hot Water | 61 · 67 |

**못 이은 것은 이유를 갈라서 말한다.** 연결이 하나도 없는 설비를 "연결 없음" 하나로 뭉치면
고객사에 할 말을 정할 수 없다. 같은 계통의 상대가 50mm 안에 있으면 판정 오차 문제이고
(**"기준을 조정하겠다"**), 주변에 아무것도 없으면 접합 부재가 모델에 없는 것이다
(**"다시 그려 달라"**). Duplex MEP 의 224대를 갈라 보면 121대가 전자, 103대가 후자다.

**추정이 얼마나 맞는지도 쟀다.** ifc4Mep 은 포트가 완전해서 정답지가 되므로, 거기에 포트를
무시하고 형상 추정만 돌려 비교했다. 기본값 5mm 에서 **정밀도 79.6% · 재현율 75.8%** 다.
오차를 1mm 로 좁히면 정밀도가 88.8%로 오르지만 재현율이 47%로 떨어지고, 50mm 로 넓히면
재현율이 94.3%까지 오르지만 정밀도가 55.1%로 무너진다. **온톨로지는 틀린 관계가 들어가는
쪽이 빠지는 쪽보다 나쁘므로 5mm 를 유지한다.** 50mm 에서도 못 찾는 113개는 접합 부재가 아예
없는 것이라 알고리즘으로 메울 수 없다. 자세한 표는 `docs/ifc-coverage.md` §4.1 에 있다.

**추정은 추정으로 남긴다.** 연결마다 출처(`port` / `geometry`)를 들고 다니고, 형상으로 추정한
연결은 방향이 없으므로 `brick:feeds` 로 내보내지 않는다. 방향을 찍어서 내보내면, 온톨로지를
읽는 쪽이 BIM 이 말한 것과 우리가 추정한 것을 구별할 수 없다. 포트가 없는 BIM 에서 TTL 의
`feeds` 절이 통째로 비는 것이 맞고, **그 빈자리가 고객사에 포트를 요구하는 근거다.**

## 3. 고객사 BIM 최소 요구사항

없으면 무엇이 막히는지를 함께 적는다. 요구 항목만 나열하면 협의에서 우선순위를 정할 수 없다.

### 반드시 있어야 하는 것

| 항목 | 없으면 |
|---|---|
| 형상 정확도 LOD 300 이상 | 벽 두께와 위치가 개략이라 3D 스캔과 맞지 않는다 |
| `IfcSpace` 가 층 전체에 닫힌 경계로 정의 | 물리존이 안 만들어진다. 온톨로지의 공간 계층이 비어 버린다 |
| 공간 이름 | 이상 알림의 발생 위치와 탐색기 트리에 표시할 이름이 없다 |
| 벽, 슬래브, 문, 창, 층(`IfcBuildingStorey`) | 3D Map 을 그릴 수 없다 |
| 층 이름이 DT 층 표기와 일치 | 층 매칭이 안 되어 사람이 전부 손으로 맞춰야 한다 |
| 공유 좌표(3D 스캔과 같은 원점, 같은 북방향) | 오류 없이 통째로 어긋난다. 파싱은 성공하므로 눈으로 보기 전에는 모른다 |
| 형식 IFC4 (ADD2 TC1 이상) | **설비의 종류를 표준 필드로 알 수 없다.** IFC2x3 은 구체 클래스가 없어 전부 `IfcFlowTerminal` 같은 추상 클래스로만 들어오고 `PredefinedType` 도 비어 있다. Duplex 두 파일에서 실측했다 |

### 있으면 온톨로지가 크게 좋아지는 것

| 항목 | 없으면 |
|---|---|
| MEP 포함(`IfcDistributionElement`) | 설비가 0 이다. 계통도와 관제 연계가 전부 수동이 된다 |
| 건축과 설비가 같은 좌표계 | 설비가 어느 물리존에 있는지 판정할 수 없다. 둘이 다른 파일이면 특히 중요하다 |
| 포트(`IfcDistributionPort`) 연결 | 계통이 없을 때 연결 관계를 되살릴 방법이 없다 |
| **연결마다 한쪽 포트에는** 흐름 방향이 SOURCE 또는 SINK (양쪽 다 SOURCEANDSINK 가 아님) | 이어진 것만 알고 상류·하류를 모른다. `brick:feeds` 가 비고, "이 토출구가 어느 공조기 담당인가" 에 답할 수 없다 |
| 이어진 요소의 솔리드가 맞닿거나 겹칠 것 | 포트가 없을 때 형상으로 연결을 되살릴 수 없다. Duplex MEP 는 연결망이 34조각으로 끊겼다 |
| 설비 위치 x·y·z | 미배치 목록으로 빠져서 사람이 3D 에서 직접 놓아야 한다 |
| 설비 용량 파라미터 (**LOD 400**) | 공조존 용량 검증(Z-03)을 돌릴 수 없다. **LOD 300 에는 기대하면 안 된다** — 용량·효율·제어는 LOD 400 미만의 MEP-BIM 에 없는 것이 보통이고, 그때는 시설팀의 설비 대장을 따로 받아야 한다 |
| `IfcSystem` 으로 묶인 계통 | 어느 공조기가 어느 토출구를 담당하는지 알 수 없다 |
| 벽의 Structural 속성 | 내력벽 편집 제한이 걸리지 않는다. 실측 샘플이 13장 모두 이 상태였다 |
| GUID 유지 설정 | 재임포트 때 같은 공간을 같은 것으로 알아보지 못한다 |

### 없어도 되는 것

마감, 가구, 구조 해석, 상세 접합, 렌더 재질은 DT 가 쓰지 않는다. 요구 목록에 넣으면 협의만
길어진다.

### 요구사항을 파일로 확인하는 방법

위 목록을 그대로 담은 IFC4 파일이 `src/lib/ifc/fixtures/mep.ifc` 에 있다. 설비마다 좌표가 있고,
용량 파라미터가 붙고, `IfcSystem` 으로 묶이고, 포트로 연결된다. 빠진 경우도 일부러 넣어 두었다.
용량이 없는 토출구가 하나 있고, 좌표가 없는 센서가 하나 있다. 문서로 설명하는 대신 이 파일을
받아서 우리 임포터에 넣어 보면 무엇이 되고 무엇이 안 되는지 그대로 보인다.

## 4. 편집 기능

편집은 3D 모델을 고치는 일이 아니라 **온톨로지를 고치는 일**이다. 차이는 한 번의 편집이 무엇을
무효로 만드는가에 있다. 벽을 하나 옮기면 물리존 경계가 바뀌고, 경계가 바뀌면 그 안에 있던 설비의
소속이 바뀌고, 소속이 바뀌면 이상 알림의 발생 위치와 탐색기 트리가 같이 바뀐다. 편집기가 할 일은
그 연쇄를 빠뜨리지 않고 다시 계산하는 것이다.

### 무엇을 고칠 수 있어야 하나

| # | 편집 | 바뀌는 피처 | 다시 계산해야 하는 것 |
|---|---|---|---|
| E1 | 물리존 이름 수정 | F3 | 없다 |
| E2 | 물리존 경계 수정 | F2 | F11 설비 소속, 면적 |
| E3 | 물리존 생성·삭제·분할·병합 | F1, F2 | F11 설비 소속, 공간 계층 |
| E4 | 벽·문·창 추가·삭제·이동 | F4, F5 | F2 물리존 경계, F15 로봇 통과 |
| E5 | 설비 이동 | F9 | F11 설비 소속 |
| E6 | 미배치 설비 배치 | F9 | F11 설비 소속 |
| E7 | 설비 추가·삭제·이름 수정 | F8 | F10 계통, F13 관제점 연결 |
| E8 | 계통 연결 수정 | F10 | 공조존 담당 관계 |
| E9 | 공조존 경계·담당 수정 | F12 | 계통도, serviceSpace |
| E10 | 커스텀존 지정 | F14 | Agent 질의 대상 |
| E11 | 관제점 ID 수정 | F13 | 없다 |

**E2 와 E5 가 편집기의 성격을 드러낸다.** 둘 다 결과가 화면에서 똑같아 보이지만, 온톨로지에서는
`brick:hasLocation` 한 줄이 바뀐다. 그 한 줄이 이상 알림의 발생 위치다. 편집기가 3D 모델 편집기와
다른 지점이 여기다.

**E11 은 BIM 과 무관하다.** 관제점은 BAS 에서 오고 설비의 관제점이 교체되는 일이 실제로 생기므로,
BIM 을 다시 받지 않고도 ID 를 고칠 수 있어야 한다.

### 편집기가 갖춰야 할 성질

| 성질 | 이유 |
|---|---|
| 편집 전후의 차이를 보여 준다 | 무엇이 바뀌는지 모르고 반영하면 되돌릴 근거가 없다 |
| 부분 반영을 만들지 않는다 | 기하만 바뀌고 의미가 안 바뀌면 두 파일이 어긋난다 |
| 되돌릴 수 있다 | 재계산이 잘못되면 이전 판으로 돌아가야 한다 |
| 재임포트와 편집분을 구분한다 | BIM 을 다시 받을 때 손으로 고친 것을 덮어쓰면 안 된다 |
| 한 층을 한 사람만 편집한다 | 같은 층을 둘이 고치면 재계산 결과가 갈린다 |

마지막 둘은 PRD #15 에서 #19 에 해당하며 저장 위치가 정해져야 구현할 수 있다. 앞의 셋은 저장
위치와 무관하므로 먼저 만든다.

### 지금 만든 범위

E1, E2, E5, E6 을 만들었다. 셋 다 같은 골격 위에 있다. 값을 고치고, 설비 소속을 다시 판정하고,
무엇이 바뀌었는지를 돌려준다.

E2 가 그중 가장 넓게 번진다. 물리존의 꼭짓점 하나를 옮기면 넓이가 다시 계산되고, 경계 밖으로
밀려난 설비의 `brick:hasLocation` 이 바뀐다. 실제로 확인한 모습은 이렇다.

```
사무실의 오른쪽 두 꼭짓점 x 를 10 에서 5 로

  사무실  80.0㎡ → 40.0㎡
  AT-101-02  사무실 → (소속 없음)      좌표 (7,4) 가 경계 밖으로 나갔다
  LIGHT-101-01  사무실 그대로           BIM 이 소속을 말해 둔 설비다
```

마지막 줄이 이 설계의 요점이다. BIM 이 소속을 명시한 설비는 좌표가 경계 밖이어도 소속을 지킨다.
설계자가 정한 값이 좌표 판정보다 정확하기 때문이다.

다각형이 자기 자신과 교차하면 알리되 막지는 않는다. 꼭짓점을 끌다 보면 잠깐 교차했다가 풀리는
일이 흔해서, 그때마다 조작을 되돌리면 편집을 할 수 없다.

## 5. BIM 이 못 주는 것을 어디서 채우나

| 피처 | 출처 | 비고 |
|---|---|---|
| F12 공조존 | IDF 또는 gbXML | 없으면 설비 담당 지정으로 수동 생성한다(PRD #11) |
| F13 관제점 | BAS | 설비 ID 와 관제점 ID 를 잇는 작업이 따로 필요하다 |
| F14 커스텀존 | 운영자 | 물리존 위에 다각형으로 지정한다 |
| F11 설비 소속 물리존 | 계산 | 좌표와 외곽선으로 판정한다. 편집할 때마다 다시 돌아야 한다 |
| 좌표 정합 | 3D 스캔 대조 | BIM 의 공유 좌표가 스캔과 맞는지 임포트 단계에서 확인한다 |

기존 SR 온톨로지는 설비와 관제점만 있고 기하가 없다. 술어가 `feeds`, `hasLocation`, `hasPart`,
`hasPoint` 넷뿐이며 좌표가 하나도 들어 있지 않다. BIM 이 채우는 것이 정확히 그 빠진 절반이므로,
둘을 합칠 때 어느 쪽 ID 를 기준으로 삼을지를 먼저 정해야 한다.

| 3D 로 확인 | 된다. 설비·배관을 실제 형상으로 그리고, 계통별로 색을 나누고, 고른 설비의 상류·하류를 칠한다 |
| 건축 모델과 설비 모델 합치기 | 안 된다. 한 번에 파일 하나만 연다 |
| 로봇 통과 여부(F15) | F4 를 읽었으나 아직 파생하지 않는다 |
| 편집 | E1, E2, E5, E6 만 있다 |
| 공조존(F12) | 손도 대지 않았다. IDF 에서 오는 것이라 BIM 에 없다 |

## 7. 수치를 다시 재는 방법

```bash
npm run fetch:sample   # 실측 샘플을 data/ 로 받는다
npm run check:sample   # 개수와 넓이를 기준값과 대조한다
npm test               # 임포트와 내보내기 규칙을 전부 확인한다
```

설비가 든 모델인지 세어 보려면 다음과 같이 한다.

```bash
grep -oE "^#[0-9]+= *IFC[A-Z0-9]+" 모델.ifc | sed -E 's/.*= *//' | sort | uniq -c | sort -rn | head -30
```

기존 SR 온톨로지의 클래스와 술어를 세는 방법은 다음과 같다.

```bash
F=~/git/dt/ieum-pipeline/data/ontology/SR_Building_ontology_260723.ttl
grep -oE '\ba\s+(brick|ex):[A-Za-z_]+' $F | awk '{print $2}' | sort | uniq -c | sort -rn | head
grep -oE '\b(brick|rdfs):[a-z][A-Za-z_]*' $F | sort -u
```
