# BIM 으로 DT 온톨로지를 어디까지 만들 수 있나

이 문서는 세 가지에 답한다.

1. DT 가 쓰려면 온톨로지에 무엇이 있어야 하는지를 정한다(피처 정의).
2. 그중 BIM 이 줄 수 있는 것이 어디까지인지를 실측으로 적는다.
3. 그러려면 고객사 BIM 에 최소한 무엇이 들어 있어야 하는지를 적는다.

근거가 되는 수치는 전부 이 저장소의 코드로 다시 잴 수 있다. 재는 방법은 마지막 절에 있다.

기준일: 2026-09-22 · 관련 문서: `[DT2.0] PRD_011(온톨로지 구축 자동화 플랫폼)`

---

## 1. DT 온톨로지의 피처

피처를 먼저 정하는 이유는 이것이 BIM 요구사항을 결정하기 때문이다. DT 의 어느 화면이 무엇을
묻는지를 적으면, 온톨로지가 들고 있어야 할 관계가 따라 나온다. 그 관계를 BIM 이 주는지 아닌지가
다음 절의 답이 된다.

### DT 가 온톨로지에 묻는 질문

| 소비처 | 질문 | 답하는 데 필요한 관계 |
|---|---|---|
| 이상 알림 | 이 설비는 어디서 났는가 | 설비 → 물리존 |
| 탐색기 트리 | 건물이 어떤 구조인가 | 사이트 → 건물 → 층 → 물리존 |
| 3D Map | 이 공간을 어떻게 그리는가 | 물리존의 외곽선과 높이 |
| 계통도 | 이 공조기가 담당하는 공간은 어디인가 | 설비 → 계통 → 공조존 |
| AI Agent | 회의실 온도가 몇 도인가 | 공간 이름 → 설비 → 관제점 |
| 로봇 관제 | 이 경로로 지나갈 수 있는가 | 벽·문·창의 통과 가능 여부 |

### 피처 목록

각 피처에 출처를 함께 적는다. **출처가 BIM 이 아닌 것이 절반이라는 점이 이 표의 요점이다.**

| # | 피처 | 관계·속성 | 출처 |
|---|---|---|---|
| F1 | 공간 계층 | `brick:hasPart` (사이트 > 건물 > 층 > 물리존) | BIM |
| F2 | 물리존 기하 | 외곽선 다각형, 면적, 층 높이 | BIM |
| F3 | 공간 이름 | `rdfs:label`, 방 번호 | BIM |
| F4 | 벽·문·창 형상 | 위치, 두께, 개구부 치수 | BIM |
| F5 | 개구부 소속 | 어느 벽에 난 문인가 | BIM |
| F6 | 공간 경계 | 이 물리존을 둘러싼 부재는 무엇인가 | BIM |
| F7 | 내력벽 | `loadBearing` | BIM (속성을 기입한 경우에만) |
| F8 | 설비 목록 | 종류, 이름, 용량 | BIM (MEP 를 포함한 경우에만) |
| F9 | 설비 위치 | x·y·z, 설치면 | BIM (MEP 를 포함한 경우에만) |
| F10 | 계통 | 공조기 → 덕트 → 토출구 | BIM (MEP 를 포함한 경우에만) |
| F11 | 설비 소속 물리존 | `brick:hasLocation` | **계산으로 만든다** |
| F12 | 공조존 | `brick:Zone`, 담당 관계 | IDF 또는 gbXML |
| F13 | 관제점 | `brick:hasPoint` | BAS |
| F14 | 커스텀존 | 운영자가 지정하는 다각형 | 사용자 |
| F15 | 로봇 통과 여부 | 문은 통과, 창문과 벽은 불가 | F4 에서 파생 |

**F11 이 이 과제의 핵심이다.** BIM 은 설비의 좌표를 주고 물리존의 외곽선을 주지만, "이 공조기가
회의실에 있다" 는 말은 하지 않는다. 그 관계는 좌표가 어느 외곽선 안에 드는지를 계산해서 만든다.
이것이 없으면 이상 알림이 발생 위치를 표시하지 못하고, 탐색기 트리에 설비가 걸리지 않는다.

**F12 와 F13 은 BIM 에서 나오지 않는다.** 공조존은 에너지 시뮬레이션 개념이라 IDF 나 gbXML 에
있고, 관제점은 BAS 가 들고 있다. BIM 만으로 온톨로지를 완성할 수 없다는 뜻이며, BIM 은 공간
골격과 설비 목록까지를 맡는다.

## 2. BIM 으로 어디까지 되는가

세 가지를 구분해서 적는다. 규격이 담을 수 있는 것과 우리가 뽑는 것과 실제 파일에 들어 있는 것이
서로 다르기 때문이다.

| 피처 | IFC4 규격 | 지금 임포터 | 실측 샘플(AC20-FZK-Haus) |
|---|---|---|---|
| F1 공간 계층 | `IfcBuildingStorey`, `IfcSpace` | 읽는다 | 층 2, 물리존 7 |
| F2 물리존 기하 | `FootPrint` 또는 `Body` 표현 | `FootPrint` 만 읽는다 | 7개 전부 추출, Buero 12.985㎡ |
| F3 공간 이름 | `Name`, `LongName` | 읽는다 | Schlafzimmer, Bad, Buero 등 7개 |
| F4 벽·문·창 | `IfcWall`, `IfcDoor`, `IfcWindow` | 개수와 이름만 읽는다 | 벽 13, 문 5, 창 11 |
| F4 벽 두께 | `IfcMaterialLayerSetUsage` | **아직 안 읽는다** | 0.24m 로 들어 있음 |
| F4 개구부 치수 | `OverallHeight`, `OverallWidth` | **아직 안 읽는다** | 문 2.01 x 0.885m |
| F5 개구부 소속 | `IfcRelVoidsElement` + `IfcRelFillsElement` | **아직 안 읽는다** | 17건, 16건 |
| F6 공간 경계 | `IfcRelSpaceBoundary` | **아직 안 읽는다** | 81건 |
| F7 내력벽 | `Pset_WallCommon.LoadBearing` | 읽는다 | **0 / 13. 속성 자체가 없음** |
| F8 설비 | `IfcDistributionElement` 하위 | 읽는다 | **0** |
| F9 설비 위치 | `ObjectPlacement` | 읽는다 | 해당 없음 |
| F10 계통 | `IfcSystem` + `IfcRelAssignsToGroup` | 읽는다 | **0** |
| F11 설비 소속 | 규격에 없다 | 계산해서 만든다 | 해당 없음 |
| F12 공조존 | **IFC 에 없다** | 해당 없음 | 없음 |
| F13 관제점 | **IFC 에 없다** | 해당 없음 | 없음 |

정리하면 이렇다.

- **공간 골격은 BIM 으로 충분히 만들어진다.** 층, 물리존, 외곽선, 면적, 이름이 전부 나온다.
  좌표 변환까지 포함해 실제 모델로 확인했다.
- **벽 두께, 개구부 치수, 공간 경계는 파일에 들어 있는데 아직 안 읽는다.** 규격 문제가 아니라
  구현이 남은 부분이며, F4 와 F6 과 F15 가 여기에 걸린다.
- **설비는 파일에 들어 있어야 읽을 수 있고, 실제로는 대부분 없다.** 이것이 가장 큰 제약이다.

### 설비가 실제로 얼마나 없는가

공개 BIM 샘플 넷을 확인했다.

| 모델 | 스키마 | 물리존 | 공간 경계 | 설비 | 계통 | 설비로 읽힌 것의 정체 |
|---|---|---|---|---|---|---|
| AC20-FZK-Haus | IFC4 | 7 | 81 | 0 | 0 | 없음 |
| C20-Institute-Var-2 | IFC4 | 82 | 1,000 | 0 | 0 | 없음 |
| Office_A | IFC2x3 | 99 | 1,334 | 31 | 0 | 휴지걸이, 거울, 안전손잡이 |
| dental_clinic | IFC2x3 | 269 | 3,124 | 102 | 0 | 타월디스펜서, 거울, 소화기함 |

여기서 세 가지를 읽을 수 있다.

첫째, **공간 쪽은 넷 모두 충실하다.** 물리존이 7개에서 269개까지 있고 공간 경계도 함께 들어
있다. 공간 골격을 BIM 으로 만든다는 전제는 실제 파일로 뒷받침된다.

둘째, **설비 쪽은 넷 모두 비어 있다.** 뒤의 둘은 `IfcFlowTerminal` 로 분류되어 설비로 읽히지만
열어 보면 욕실 액세서리다. 넷 모두 `IfcSystem` 이 0 이라 계통이 없다. MEP 모델은 건축 모델과
따로 만들어지는 경우가 많으므로, "BIM 이 있다" 는 말이 "설비도 있다" 는 뜻은 아니다.

셋째, **뒤의 둘은 IFC2x3 인데도 공간과 설비를 읽어 냈다.** 그래도 요구사항에 IFC4 를 적는
이유는 설비 분류 체계가 다르기 때문이다. IFC2x3 은 공조기든 세면대든 `IfcFlowTerminal` 하나로
묶고 실제 종류를 별도 타입 객체에 둔다. IFC4 는 `IfcAirTerminal` 처럼 종류가 클래스로 드러나서,
Brick 클래스로 옮길 때 추측이 필요 없다.

## 3. 고객사 BIM 최소 요구사항

없으면 무엇이 막히는지를 함께 적는다. 요구 항목만 나열하면 협의에서 우선순위를 정할 수 없다.

### 반드시 있어야 하는 것

| 항목 | 없으면 |
|---|---|
| 형상 정확도 LOD 300 이상 | 벽 두께와 위치가 개략이라 3D 스캔과 맞지 않는다 |
| `IfcSpace` 가 층 전체에 닫힌 경계로 정의 | 물리존이 안 만들어진다. 온톨로지의 공간 계층이 비어 버린다 |
| 공간 이름 | 이상 알림의 발생 위치와 탐색기 트리에 표시할 이름이 없다 |
| 벽, 슬래브, 문, 창, 층(`IfcBuildingStorey`) | 3D Map 을 그릴 수 없다 |
| 층 이름이 DT 층 표기와 일치 | 층 매칭이 안 되어 사람이 전부 손으로 맞춰야 한다 |
| 공유 좌표(3D 스캔과 같은 원점, 같은 북방향) | 오류 없이 통째로 어긋난다. 파싱은 성공하므로 눈으로 보기 전에는 모른다 |
| 형식 IFC4 | 구버전은 설비 분류 체계가 달라 읽는 규칙이 갈라진다 |

### 있으면 온톨로지가 크게 좋아지는 것

| 항목 | 없으면 |
|---|---|
| MEP 포함(`IfcDistributionElement`) | 설비가 0 이다. 계통도와 관제 연계가 전부 수동이 된다 |
| 설비 위치 x·y·z | 미배치 목록으로 빠져서 사람이 3D 에서 직접 놓아야 한다 |
| 설비 용량 파라미터 | 공조존 용량 검증(Z-03)을 돌릴 수 없다 |
| `IfcSystem` 으로 묶인 계통 | 어느 공조기가 어느 토출구를 담당하는지 알 수 없다 |
| 벽의 Structural 속성 | 내력벽 편집 제한이 걸리지 않는다. 실측 샘플이 13장 모두 이 상태였다 |
| GUID 유지 설정 | 재임포트 때 같은 공간을 같은 것으로 알아보지 못한다 |

### 없어도 되는 것

마감, 가구, 구조 해석, 상세 접합, 렌더 재질은 DT 가 쓰지 않는다. 요구 목록에 넣으면 협의만
길어진다.

### 요구사항을 파일로 확인하는 방법

위 목록을 그대로 담은 IFC4 파일이 `src/lib/ifc/fixtures/mep.ifc` 에 있다. 설비마다 좌표가 있고,
용량 파라미터가 붙고, `IfcSystem` 으로 묶이고, 포트로 연결된다. 빠진 경우도 일부러 넣어 두었다.
용량이 없는 토출구가 하나 있고, 좌표가 없는 센서가 하나 있다. 문서로 설명하는 대신 이 파일을
받아서 우리 임포터에 넣어 보면 무엇이 되고 무엇이 안 되는지 그대로 보인다.

## 4. BIM 이 못 주는 것을 어디서 채우나

| 피처 | 출처 | 비고 |
|---|---|---|
| F12 공조존 | IDF 또는 gbXML | 없으면 설비 담당 지정으로 수동 생성한다(PRD #11) |
| F13 관제점 | BAS | 설비 ID 와 관제점 ID 를 잇는 작업이 따로 필요하다 |
| F14 커스텀존 | 운영자 | 물리존 위에 다각형으로 지정한다 |
| F11 설비 소속 물리존 | 계산 | 좌표와 외곽선으로 판정한다. 편집할 때마다 다시 돌아야 한다 |
| 좌표 정합 | 3D 스캔 대조 | BIM 의 공유 좌표가 스캔과 맞는지 임포트 단계에서 확인한다 |

기존 SR 온톨로지는 설비와 관제점만 있고 기하가 없다. 술어가 `feeds`, `hasLocation`, `hasPart`,
`hasPoint` 넷뿐이며 좌표가 하나도 들어 있지 않다. BIM 이 채우는 것이 정확히 그 빠진 절반이므로,
둘을 합칠 때 어느 쪽 ID 를 기준으로 삼을지를 먼저 정해야 한다.

## 5. 지금 상태와 남은 일

| 구분 | 상태 |
|---|---|
| 공간 골격 임포트(F1, F2, F3) | 된다. 실제 모델로 확인했다 |
| 설비 임포트(F8, F9, F10) | 된다. 실제 MEP 모델로는 아직 확인하지 못했다 |
| 설비 소속 판정(F11) | 된다 |
| 내보내기 | 된다. 기하는 GeoJSON, 의미는 Brick TTL 로 나간다 |
| 벽 두께, 개구부 치수, 공간 경계(F4, F5, F6) | 파일에는 있으나 아직 안 읽는다 |
| 로봇 통과 여부(F15) | F4 를 읽은 뒤에 파생한다 |
| 편집 | 없다 |

## 6. 수치를 다시 재는 방법

```bash
npm run fetch:sample   # 실측 샘플을 data/ 로 받는다
npm run check:sample   # 개수와 넓이를 기준값과 대조한다
npm test               # 임포트와 내보내기 규칙을 전부 확인한다
```

설비가 든 모델인지 세어 보려면 다음과 같이 한다.

```bash
grep -oE "^#[0-9]+= *IFC[A-Z0-9]+" 모델.ifc | sed -E 's/.*= *//' | sort | uniq -c | sort -rn | head -30
```

기존 SR 온톨로지의 클래스와 술어를 세는 방법은 다음과 같다.

```bash
F=~/git/dt/ieum-pipeline/data/ontology/SR_Building_ontology_260723.ttl
grep -oE '\ba\s+(brick|ex):[A-Za-z_]+' $F | awk '{print $2}' | sort | uniq -c | sort -rn | head
grep -oE '\b(brick|rdfs):[a-z][A-Za-z_]*' $F | sort -u
```
