## 1. R2(Phase 2) 범위

### 1.1 한 줄 요약

R2 의 본체는 **IDF 로 공조존을 자동으로 세우는 것**(#5, E04)이다. 거기에 다중 사용자 협업(권한·층 잠금), BIM 이 없는 현장의 수동 구축,
배관 규칙 보강, 로봇 시점, 공조 커버리지 분석이 붙는다. 티켓 31건 — P1 18 · P2 7 · P3 6.

> IDF = EnergyPlus 에너지 시뮬레이션 입력 파일. 설계사가 냉난방 부하를 계산하려고 만드는데, 그 안에 "어느 존을 어느 VAV·공조기가 맡는지"가
> 적혀 있다. BIM(IFC)에는 이 공조존이 대개 없어서 R1 은 사람이 손으로 그린다. R2 는 이걸 IDF 에서 읽어 와 자동으로 만든다.

## 2. 디자인 시스템 — 내가 정해야 할 것

### 2.1 먼저 알아 둘 현재 상태 (src/ 실측)

| 잰 것 | 값 | 뜻 |
|---|---|---|
| CSS 변수(토큰) | `styles.css` :root 21개 (`--accent` `--muted` `--radius` …) | 뼈대는 있다 |
| 코드에 박힌 색(#rrggbb 종류) | **281종** | 토큰을 안 거치고 색을 직접 쓴 곳이 대부분 |
| 글자 크기 종류 | 15종 이상(9~28px) | 위계가 없다 |
| 9~11px 글자 | 84곳 | 대형 모니터·노안에서 읽기 어렵다(최소 12px 권장) |
| 모서리 반경 종류 | 10종 | 2·4·6·7·8·9·10·14·999px 혼재 |
| `App.vue` | 13,950줄 · 버튼 250개 | 컴포넌트로 안 나뉘어 디자인 시스템을 "꽂을 자리"가 적다 |
| 화면 | 에디터 `index.html` · 플랫폼 `prototype.html` · 뷰어 `viewer.html` | 셋이 스타일을 따로 가진다 |

PRD 는 "UX 가이드 산출물"을 범위에서 뺐다(PRD_011 1.3 제외, "개발 주도"). 그래서 디자인 시스템은 개발 쪽 산출물이고, 정본은 `docs/dev/`
에 둔다(ADR 아님 — UI 는 `docs/dev/ui-notes.md` 규칙).

### 2.2 정할 것 체크리스트 (순서대로)

**0단계 — 범위·원칙 (이걸 안 정하면 뒤가 다 흔들린다)**

- [ ] 적용 화면: 에디터·플랫폼·뷰어 셋 다? 플랫폼만 먼저?
- [ ] 사용자·환경: BIM 담당·DT 운영자 / 사무실 노트북(1366·1920) · 대형 모니터 / 마우스 중심 / Chrome·Edge
- [ ] 밀도 원칙: 전문 도구라 "고밀도(compact)" 기본 + 필요하면 "편한(comfortable)" 한 단계
- [ ] 테마: 라이트만 / 다크까지 (3D 캔버스는 어두운 배경이 형상이 잘 보인다 — 다크를 하려면 처음부터 토큰을 두 벌로)
- [ ] 브랜드: 삼성 사내 가이드(One UI·SDS 디자인 시스템 등) 따를지, 독자 톤일지 — 따르면 색·폰트 상당수가 정해진다
- [ ] 원칙 3~5개 문장. 예) "3D 가 주인공, UI 는 비켜선다" · "기계가 정한 것과 사람이 고친 것을 항상 구별한다" · "반영 전엔 미리보기"

**1단계 — 파운데이션 토큰**

| 항목 | 정할 것 | 이 프로젝트에서 특히 |
|---|---|---|
| 색 — 중립 | 회색 10단계(배경·면·선·글자) | 지금 `--bg` `--surface` `--line` `--muted` 를 확장 |
| 색 — 의미 | 성공·경고·오류·정보 × (글자·배경·선) | `--warn-*` `--error-*` 이미 있음 |
| **색 — 도메인** | 계통 색(급기·환기·냉수…) · **출처 색**(BIM·계산·사전·편집) · 등급(0~5) · 상태(미리보기·잠금·미배치) | 이게 이 도구의 고유 언어다. 일반 디자인 시스템엔 없으니 직접 정의 |
| **색 — 3D 상호작용** | 호버·선택·다중 선택·미리보기(점선 액센트)·잠금·오류 강조 | 3D 와 목록·평면도에서 같은 의미 = 같은 색 |
| 글자 | 폰트(Pretendard 등)·크기 6단계(예: 12/13/14/16/20/24)·굵기 3·줄 높이·숫자 고정폭(좌표·면적 표) | 15종 → 6종 |
| 간격 | 4px 격자, 단계(4·8·12·16·24·32) | |
| 반경 | 3단계(4·8·pill) | 10종 → 3종 |
| 그림자·층(z-index) | 3D 위 오버레이 < 팔레트 < 패널 < 드롭다운 < 모달 < 토스트 | 3D 캔버스 위에 뜨는 게 많아서 층 순서를 표로 고정 |
| 움직임 | 길이(120·200ms)·곡선, `prefers-reduced-motion` | |
| 아이콘 | 세트 하나(Lucide 등) · 크기 16/20 | 지금 `⊙` `◇` 같은 글자 아이콘 |
| 단위·숫자 | m/mm, 소수 자리, 천 단위 구분, 면적 ㎡ | 좌표 칸·표에서 매번 다르면 틀린 값으로 읽힌다 |

**2단계 — 컴포넌트** (지금 있는 것 → 표준화)

- 동작: 버튼(주·보조·고스트·위험 × 크기 2), 아이콘 버튼, 세그먼트 토글(`[공간 | 설비]`), 단축키 표시
- 입력: 글자·숫자(단위 붙음)·선택·검색·체크·라디오, 검증 메시지
- 표시: 칩·배지(`TierChips` 등급, `Src` 출처), 미터(`Meter`), 툴팁(`HoverTip`), 범례
- 구조: 사이드바·탭·트리(층→방→설비)·**대용량 표**(성수 방 508·설비 수천 — 정렬·필터·가상 스크롤), 속성 패널(inspector), 접기(`Fold`)
- 오버레이: 모달·확인(`ExitEditDialog` `PublishDialog`), 배너(편집 중), 토스트, 진행률(대형 IFC 임포트)
- 상태: 빈 상태·로딩·오류·권한 없음·잠김

각 컴포넌트마다 적을 것: 용도 한 줄 · 변형 · 상태(기본·호버·포커스·눌림·비활성·로딩) · 키보드 · 쓰지 말아야 할 때.

**3단계 — 패턴 (여러 컴포넌트가 엮이는 흐름)**

- 미리보기 → [적용]/[반영하기] (D16, `ui-notes.md` 연결 방향) — 미리보기 표현을 한 가지로
- 되돌리기·다시 하기, 파괴적 작업 확인(삭제·반영) 기준: 언제 모달, 언제 되돌리기 토스트
- 선택 동기화: 3D ↔ 목록 ↔ 평면도 ↔ 속성 패널
- 경고·검증(W-01~03, 등급 게이트): 어디에, 얼마나 시끄럽게
- 레이아웃 격자: 사이드바·캔버스·인스펙터 폭, 접힘 규칙, 최소 해상도
- 긴 목록: 지금 "앞 200개 + 검색" — 기준을 정한다
- 단축키 체계(`ShortcutHelp`): 충돌 없는 규칙

**4단계 — 글(콘텐츠)**

- 용어: `docs/prd/glossary.md` 를 UI 라벨 정본으로 (물리존/룸/공조존/커스텀존)
- 버튼은 동사, 확인 대화상자는 결과를 말하기("3개 설비를 지웁니다")
- 말투 한 가지(지금 "~습니다" 와 명사형이 섞임)

**5단계 — 접근성 기준**

- 글자 대비 4.5:1, 큰 글자 3:1 · 포커스 링 항상 보이기 · 키보드로 모든 조작
- **색만으로 구분하지 않기** — 계통 색·출처 색에 라벨·패턴을 같이(색약 사용자, 흑백 인쇄 리포트)
- 클릭 영역 최소 24×24px (WCAG 2.2 2.5.8)

**6단계 — 운영(거버넌스)**

- 정본 위치: `src/styles/tokens.css` 한 파일 + `docs/dev/design-system.md`
- 이름 규칙: `--color-text-muted` 처럼 "용도" 이름(`--gray-500` 같은 값 이름은 원본 팔레트에만)
- 지키는 장치: stylelint 로 `#hex`·`px` 직접 쓰기 금지 · Playwright `toHaveScreenshot` 시각 회귀 · axe 접근성 검사
- 카탈로그: 컴포넌트 미리보기 HTML 한 장(Storybook 은 무겁다)
- 바꾸는 절차: 새 색·컴포넌트는 누가 승인, 어디에 기록

### 2.3 최소 버전 (2주 안에 할 수 있는 크기)

0단계 결정 + 토큰(색·글자·간격·반경·층) + 버튼·입력·칩·모달 4종 + 접근성 기준 3줄.
나머지는 화면을 고칠 때마다 그 컴포넌트를 표준화하며 늘린다.

## 3. 일반 사이트 UX 벤치마킹 — 방법 연구

### 3.1 지금 쓸 수 있는 도구

| web-fetch 에이전트 · WebSearch | 있음 | 공개 디자인 시스템 문서·제품 문서·사례 수집 |
| `web-artifacts-builder` skill | 있음 | 개선안 목업(React+shadcn)을 빠르게 만들어 비교 |
| `dataviz` skill | 있음 | 등급·커버리지 차트 색·형태 규칙 참고 |
| DesignSync (claude.ai/design 디자인 시스템 프로젝트 동기화) | 도구는 있으나 `/design-sync` skill 이 목록에 없음 | 토큰·컴포넌트를 정한 뒤 디자인 쪽과 공유할 때 후보 |
| axe-core · Lighthouse | 미설치 | `@axe-core/playwright` 를 dev 의존성으로 넣으면 e2e 안에서 접근성 자동 검사 |

### 3.2 무엇과 비교하나 — "일반 사이트" 를 세 층으로

전체 웹을 다 보는 게 아니라, **우리 과업과 닮은 화면**만 본다.

1. **같은 구조의 전문 도구**(캔버스 + 목록 + 속성 패널): Figma, Autodesk Forma·ACC 뷰어, Speckle, Matterport, Onshape
   → 선택 동기화, 도구 팔레트, 3D 위 오버레이, 미리보기·반영
2. **잘 만든 B2B 작업 도구**: Linear, Notion, GitHub, Vercel 대시보드
   → 대용량 목록·필터, 단축키, 빈 상태, 토스트·되돌리기, 설정 화면
3. **공개 디자인 시스템**(규칙을 빌려 오는 곳): IBM Carbon(데이터 밀집 엔터프라이즈 — 이 도구에 가장 가깝다), Atlassian, Material 3, GitHub Primer
   → 토큰 이름, 고밀도 표, 상태 정의, 접근성 기준

### 3.3 절차

```
① 과업 5개 고정
   BIM 가져오기→검토 · 물리존 이름 고치기 · 설비 옮기기 · 미리보기→반영 · 온톨로지 내보내기
② 우리 쪽 기준선 (Playwright, Duplex·성수)
   과업별 단계 스샷 · 클릭 수 · 걸린 시간 · 막힌 지점
③ 비교 대상 수집 (과업별 2~3개 제품)
   공개 문서·데모는 web-fetch + 스샷, 로그인 필요한 앱은 사람이 캡처
④ 평가
   - 닐슨 휴리스틱 10개 × 화면, 심각도 0~4
   - 접근성: axe 자동 + 키보드·대비 수동
   - 일관성 숫자: 색 종류(281) · 글자 크기 종류(15) · 반경 종류(10) — 개선 후 다시 잼
⑤ 백로그
   항목마다 [근거 스샷 · 비교 대상 · 심각도 · 영향 과업 · 비용], 심각도×빈도÷비용 순
⑥ 개선 → 같은 Playwright 과업으로 다시 재서 전후 숫자 비교
```

> 닐슨 휴리스틱 = UX 점검용 10개 체크 항목(상태가 보이나, 실수를 되돌릴 수 있나, 일관적인가 등). 사용자 시험 없이 전문가가 화면을 훑어
> 문제를 찾는 표준 방법이다. 싸고 빠르지만 "실제 사용자가 막히는 곳" 은 놓칠 수 있어, 가능하면 BIM 담당자 2~3명 과업 관찰을 한 번 곁들인다.

### 3.4 주의 — 일반 사이트 UX 를 그대로 가져오면 안 되는 곳

- 마케팅·소비자 사이트의 넓은 여백·큰 카드는 여기선 역효과다. 3D 캔버스 면적이 줄고 표 한 화면에 들어가는 행이 준다.
- 모바일 우선 반응형은 우선순위가 낮다(편집은 데스크톱). 대신 1366px 노트북에서 패널이 3D 를 가리지 않는지가 중요하다.
- 벤치마킹의 목적은 R1 출시 품질 — "BIM 을 넣고 고쳐서 온톨로지를 낸다" 과업이 덜 막히게. 새 기능을 늘리는 제안은 백로그에서 뺀다.
