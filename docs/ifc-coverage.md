# IFC 가 온톨로지에 줄 수 있는 것의 지도

이 문서는 하나만 묻는다. **IFC 에 무엇이 들어 있어야 온톨로지가 어디까지 만들어지는가.**

숫자는 전부 `data/` 의 실제 파일을 열어서 잰 것이다. 추정이나 스키마 문서 인용이 아니다.
재는 방법은 마지막 절에 있다. 개념의 출처는 `docs/research.md`, 피처 번호(F1…F16)와
요구사항 정본은 `docs/bim-to-dt-ontology.md` 다.

기준일: 2026-09-22 · 측정 대상 4개 파일

---

## 1. IFC 의 정보는 세 층으로 나뉜다

같은 "IFC 에 있다" 가 아니다. **스키마가 강제하는 것, 저작 도구가 채우기 나름인 것, 아예 없는
것**이 있고, 요구사항을 쓸 때 이 셋을 섞으면 협의가 망가진다.

| 층 | 성격 | 실측 충족률 |
|---|---|---|
| **A. 절대 비지 않는다** | IFC 클래스 계층 자체. 인스턴스가 존재하면 반드시 있다 | **100%** |
| **B. 채우기 나름이다** | 포트, `IfcSystem`, `PredefinedType`, 표준 Pset, 공간 포함 | **0 ~ 100%** |
| **C. IFC 에 없다** | 공조존, 관제점, 실시간 값, 운영 이력 | **0%** |

C 는 BIM 요구사항에 넣으면 안 된다. 협의만 길어진다. **싸움은 전부 B 에서 난다.**

## 2. A층 — IFC 클래스 계층이 곧 역할 분류다

이번 조사에서 가장 쓸모 있는 발견이다. `IfcDistributionFlowElement` 의 하위 추상 타입이
**소스·싱크·도관·제어**라는 역할을 이미 담고 있다. 그리고 **이건 절대 비지 않는다** —
요소가 존재하면 어떤 클래스든 반드시 그중 하나다.

| IFC 추상 타입 | 역할 | 예 |
|---|---|---|
| `IfcEnergyConversionDevice` | **소스** (에너지를 만든다) | 보일러, 칠러, 공조기, 열교환기 |
| `IfcFlowMovingDevice` | **소스** (흐름을 민다) | 펌프, 팬, 압축기 |
| `IfcFlowStorageDevice` | 저장 | 탱크 |
| `IfcFlowTerminal` | **싱크** (소비한다) | 토출구, 라디에이터, 위생기구, 콘센트 |
| `IfcFlowTreatmentDevice` | 처리 | 필터 |
| `IfcFlowController` | 제어 | 밸브, 댐퍼 |
| `IfcFlowSegment` | **도관** | 덕트·배관 구간 |
| `IfcFlowFitting` | **도관** | 엘보, 티, 레듀서 |
| `IfcDistributionControlElement` | 계측 | 센서, 액추에이터 |

### 실측 — 네 파일 모두 100% 분류된다

| | ifc4Mep (IFC4) | Duplex MEP (IFC2x3) | Duplex HVAC (IFC2x3) |
|---|---|---|---|
| 설비 총계 | 2,202 | 926 | 498 |
| EnergyConversionDevice | 45 | 16 | 2 |
| FlowMovingDevice | 0 | 4 | 2 |
| FlowTerminal | 220 | 105 | 16 |
| FlowController | 34 | 14 | 20 |
| DistributionControlElement | 7 | 2 | 0 |
| **FlowSegment** | **1,075** | **427** | **231** |
| **FlowFitting** | **820** | **358** | **227** |
| 분류 안 됨 | 1 | **0** | **0** |

**두 가지가 바로 나온다.**

**① 설비의 85%는 기기가 아니라 도관이다.** Duplex MEP 926개 중 구간·피팅이 785개(85%),
실제 기기는 141개다. ifc4Mep 은 2,202 중 1,895개(86%)가 도관이고 기기는 307개다.
DT 에 "설비 926대" 로 내보내면 거짓말이 된다. Brick 과 FSO 가 역할을 나누는 이유가 이것이다 —
도관은 `fso:Segment`·`fso:Fitting`, 기기만 `brick:*` 다.

**이 구분은 이제 코드에 들어 있다.** `Equipment.role` 이 위 표의 아홉 가지를 그대로 들고,
화면은 기기와 덕트·배관을 따로 세고, TTL 은 도관을 FSO 로 낸다. 역할 분포는
`npm run check:sample` 에 박혀 있다(Duplex MEP: segment 427 · fitting 358 · terminal 105 ·
conversion 16 · control 14 · moving 4 · sensing 2).

**② 역할은 공짜로 얻는다.** 포트가 없어도, `IfcSystem` 이 없어도, `PredefinedType` 이 없어도
"이건 소스, 저건 싱크" 를 안다. 흐름 방향을 유도하려는 시도의 출발점이 여기다.

## 3. B층 — 여기서 갈린다

| 항목 | ifc4Mep | Duplex MEP | Duplex HVAC | AC20-FZK-Haus |
|---|---|---|---|---|
| 스키마 | IFC4 | IFC2x3 | IFC2x3 | IFC4 |
| 설비 | 2,202 | 926 | 498 | **0** |
| **포트** | **4,232** | **0** | 970 | 0 |
| 포트 흐름 방향 | SOURCE 2,099 / SINK 2,103 / 없음 30 | — | SOURCE 190 / SINK 190 / **SOURCEANDSINK 590** | — |
| 방향을 아는 연결 비율 | **100%** | — | **39%** | — |
| `IfcSystem` | 37 | **0** | **0** | 0 |
| Revit `System Name` 속성 | — | 811 | 498 | — |
| `PredefinedType` (말단 기준) | **0%** | **0%** | **0%** | — |
| 구체 클래스 | 있음 (AirTerminal, LightFixture…) | **없음** (전부 추상 클래스) | **없음** | — |
| `IfcSpace` | **0** | 42 | 1 | 7 |
| 공간에 직접 담긴 설비 | 0 | 167 | 2 | 0 |
| Pset 붙은 설비 | 1,243 / 2,202 (56%) | 926 / 926 | 498 / 498 | — |
| Pset 이름 | 표준 (`Pset_FlowSegmentPipeSegment` 등) | **전부 `PSet_Revit_*`** | **전부 비표준** | — |
| `IfcBuildingElementProxy` | 49 | 0 | 0 | 0 |

### 여기서 읽을 것 다섯

**① 포트는 전부 아니면 전무에 가깝다.** 4,232 / 0 / 970. 중간이 없다. 저작 도구 설정과
모델링 방식이 결정하기 때문이다. UCL 사례에서도 급기 덕트 연결의 5%만 포트로 왔다
(`docs/research.md` §1). **포트는 "있으면 좋은 것" 이 아니라 "없으면 다른 길을 가야 하는 것" 이다.**

**② `SOURCEANDSINK` 가 방향을 죽인다.** Duplex HVAC 는 포트가 970개나 있는데 590개(61%)가
`SOURCEANDSINK` 라 방향이 안 나온다. 요구사항에 "포트를 넣어 달라" 가 아니라 **"포트에 흐름
방향을 넣어 달라"** 를 적어야 하는 이유다.

**③ IFC2x3 은 설비의 종류를 말하지 않는다.** Duplex 두 파일은 구체 클래스가 하나도 없다.
105개가 전부 그냥 `IfcFlowTerminal` 이고 `PredefinedType` 도 비어 있다. 열어 보면 이렇다.

```
ObjectType:  "Duplex Receptacle"×47   "Single Pole"×14   "150W - 120V"×8   "Private - 6.1 Lpf"×4
```

콘센트, 스위치, 조명, 변기다. **공조 말단이 아니다.** Brick 클래스(`Air_Diffuser`, `VAV`…)로
매핑하려면 이 문자열을 해석해야 한다. IFC4 인 ifc4Mep 도 구체 클래스까지는 주지만
(`IfcAirTerminal` 43개) `PredefinedType` 은 비어서 급기인지 환기인지는 모른다 —
타입 이름이 `"GV011200x200"` 같은 제조사 코드다.

**→ 이것이 "형식 IFC4" 를 필수로 요구해야 하는 진짜 근거다.** 지금까지는 "구버전은 분류
체계가 달라서" 라고만 적혀 있었다. 실제로는 **IFC2x3 에서 설비 종류가 표준 필드로는 복구
불가능**하다.

**④ MEP 파일에는 공간이 없다.** ifc4Mep 은 설비 2,202개인데 `IfcSpace` 가 **0개**다.
건축 모델과 설비 모델이 따로 만들어지기 때문이고, 이건 예외가 아니라 정상이다(PRD 용어집의
MEP 항목이 같은 말을 한다). **설비 소속 물리존(F11)은 원천적으로 한 파일로 안 된다.**
우리 임포터는 지금 파일 하나만 받는다 — 이게 구조적 한계다.

Duplex MEP 는 반대로 공간 42개가 있고, 그중 **167개 설비를 BIM 이 직접 공간에 담아 줬다**
(926 중 18%). 나머지 759개는 좌표 판정이 필요하다.

**⑤ 표준 Pset 은 거의 안 쓰인다.** Revit 은 전부 `PSet_Revit_Mechanical`,
`PSet_Revit_Type_Fitting` 처럼 내보낸다. 대신 **COBie 필드는 926개 전부 채워져 있다**
(`AssetIdentifier`, `SerialNumber`, `WarrantyStartDate`, `ExpectedLife`, `ReplacementCost`…).
자산 관리 쪽 확장 여지가 오히려 넓다.

계통 관련해서는 Revit 이 `System Name` 과 `System Type` 을 남긴다.

```
Duplex MEP  System Type (811건)
  "Hydronic Supply"×351  "Domestic Cold Water"×144  "Sanitary"×134  "Domestic Hot Water"×134
```

**`System Type` 이 유체 종류를 준다.** 우리는 지금 `System Name` 만 쓴다. `System Type` 을
같이 읽으면 냉수/온수/급수/오수 계통 구분이 생기고, Brick 클래스 선택의 근거가 된다.
그리고 이 속성이 없는 115개가 곧 전기 계열이라, **도메인 분리도 여기서 나온다.**

## 4. 되살릴 수 있는 것과 없는 것

BIM 에 빠진 것을 우리가 계산으로 채울 수 있는지의 경계다.

| 빠진 것 | 되살리나 | 방법 | 근거 |
|---|---|---|---|
| 요소 사이의 연결 | **된다 (정밀도 80% · 재현율 76%)** | 메시 꼭짓점 5mm 접촉, 같은 계통끼리만 | 아래 §4.1 |
| 계통 묶음 | **된다** | Revit `System Name`·`System Type` | 811 / 926 |
| 설비 소속 물리존 | **된다** | 좌표가 외곽선 안에 드는지 | 단, 같은 파일에 공간이 있어야 |
| 요소 자체가 없음 | **안 된다** | — | 1차 결손. 없는 것은 없다 (아래 §4.2) |
| 흐름 방향 | **안 된다 (지금은)** | 소스·싱크 경로 탐색 | **아래 참조** |
| 설비의 구체 종류 | **부분적** | Revit 패밀리 이름 해석 | 규칙으로는 불가, 분류 필요 |
| 용량 파라미터 | **안 된다** | — | LOD 400 문제 |

### 4.1 기하 추정이 얼마나 맞는가 — 처음으로 쟀다

지금까지 못 쟀던 이유는 맞춰 볼 정답지가 없어서다. 포트가 없는 파일에서 추정을 돌리니 답이
없었다. **ifc4Mep 이 정답지다** — 포트 4,232개에 `SOURCEANDSINK` 가 0개라 연결 1,995개가
전부 확정이다. 이 파일에서 포트를 일부러 무시하고 형상 추정만 돌려 비교했다.

정답지는 **양쪽 다 메시가 있는 연결 1,972개**로 잡았다. 메시가 없으면 기하로는 애초에 못
찾으니, 그것까지 못 맞혔다고 세면 알고리즘이 아니라 입력을 탓하는 것이 된다.

| 허용오차 | 추정한 연결 | 맞음 | 틀림(FP) | 놓침(FN) | 정밀도 | 재현율 | F1 |
|---|---|---|---|---|---|---|---|
| 1mm | 1,044 | 927 | 117 | 1,045 | **88.8%** | 47.0% | 61.5% |
| **5mm (기본값)** | 1,878 | 1,494 | 384 | 478 | **79.6%** | **75.8%** | 77.6% |
| 10mm | 2,226 | 1,658 | 568 | 314 | 74.5% | 84.1% | **79.0%** |
| 20mm | 2,733 | 1,763 | 970 | 209 | 64.5% | 89.4% | 74.9% |
| 50mm | 3,372 | 1,859 | 1,513 | 113 | 55.1% | **94.3%** | 69.6% |

**읽을 것 넷.**

**① 지금 기본값은 나쁘지 않다.** 5mm 에서 열 중 여덟을 맞히고 넷 중 셋을 찾는다. F1 최고점은
10mm(79.0%)지만 5mm(77.6%)와 차이가 작고, 정밀도가 5%p 떨어진다. **온톨로지는 틀린 관계가
들어가는 쪽이 빠지는 쪽보다 나쁘므로 5mm 를 유지한다.**

**② 허용 오차를 0 에 가깝게 두는 선택지는 없다.** 1mm 에서 재현율이 47%다. 접합부의 꼭짓점이
딱 맞물리게 그려진 모델이 드물다는 뜻이다.

**③ 50mm 까지 넓혀도 113개는 끝내 못 찾는다.** 이건 오차 문제가 아니라 접합 부재가 아예 없는
것(1차 결손)이다. **알고리즘으로 메울 수 없는 바닥이 여기다.**

**④ FP 384개가 전부 우리 잘못은 아니다.** 그중 **339개가 같은 계통끼리**다. 같은 계통의 두
요소가 5mm 안에서 닿아 있는데 BIM 이 연결이라 말하지 않았다면, 붙어만 있고 안 이어진 것일
수도 있지만 **BIM 쪽이 빠뜨린 것일 수도 있다**(Lilis 2025 의 혼동행렬). 둘을 자동으로는 못
가른다. 실제 정밀도는 79.6% 보다 높을 가능성이 있고, 이 차이를 좁히려면 사람이 봐야 한다 —
그게 에디터가 할 일이다.

**계통 필터는 이 파일에서 거의 일하지 않았다.** 끄면 연결이 1,878 → 1,884 로 6개 늘 뿐이고
정밀도는 79.6% → 79.4% 다. Duplex MEP 에서는 계통이 섞이는 것을 막는 핵심 장치였는데
(냉수관과 온수관이 나란히 달린다), ifc4Mep 은 계통에 묶인 설비가 1,683/2,153 뿐이고 계통이
굵어서 거를 것이 없다. **필터의 값어치는 파일마다 다르다. 빼면 안 되지만 믿어서도 안 된다.**

이 수치는 `npm run check:sample` 의 "형상 추정의 정확도" 항목에 박혀 있다. 추정 알고리즘을
고치면 이 값이 움직이므로, 좋아졌는지 나빠졌는지가 바로 보인다.

### 4.2 못 이은 것을 이유별로 가른다

연결이 하나도 없는 설비를 "연결 없음" 하나로 뭉치면 **고객사에 할 말을 정할 수 없다.**
이유가 둘이고 대응이 정반대이기 때문이다(Lilis 2025 의 1차·2차 결손).

| 종류 | 무엇인가 | 할 말 |
|---|---|---|
| **2차 결손** | 상대는 있는데 판정 오차 밖이다 | "우리가 판정 기준을 조정하겠다" |
| **1차 결손** | 주변에 상대가 아예 없다 | **"모델을 다시 그려 달라"** |

경계는 50mm 로 뒀다. 실측에서 온 값이다 — §4.1 에서 허용 오차를 키워 보면 50mm 에서 재현율이
94.3%로 포화하고, 그래도 안 붙는 113개는 더 키워도 안 붙었다. 계통이 다른 상대는 세지 않는다.
오차를 키워도 어차피 안 이을 것이라, 세면 "오차 문제" 라고 잘못 말하게 된다.

Duplex MEP-Optimized 에서 연결이 없는 설비 **224대**를 갈라 보면 이렇다.

| | 대수 | 비율 |
|---|---|---|
| 2차 결손 (50mm 안에 상대가 있다) | **121** | 54% |
| 1차 결손 (주변에 상대가 없다) | **103** | 46% |

**절반 이상이 되살릴 수 있는 쪽이다.** 판정 오차를 키우는 것만으로 121대가 연결망에 붙는다 —
다만 §4.1 의 표대로 오차를 키우면 정밀도가 떨어지므로, 전역으로 키우는 대신 고립된 요소
주변에서만 넓히는 쪽이 맞다. 아직 안 했다.

나머지 103대는 알고리즘으로 못 메운다. 이 숫자가 고객사 BIM 요구사항의 "이어진 요소의
솔리드가 맞닿거나 겹칠 것" 이 왜 필요한지의 근거다.

이 구분은 임포트 경고로 바로 뜬다.

> 설비 224대에 연결이 하나도 없습니다. 그중 121대는 50mm 안에 이을 상대가 있어 판정 오차
> 문제이고, 나머지 103대는 주변에 상대가 없습니다(접합 부재 누락).

### 흐름 방향을 유도하려 했지만 실패했다

이론은 이렇다. 역할은 공짜로 안다(§2). 소스에서 싱크로 경로를 찾으면 그 경로의 변에 방향을
줄 수 있다. 그러려면 **하나의 연결망 조각 안에 소스와 싱크가 같이 있어야 한다.** 재 봤다.

| 파일 | 연결 | 연결망 조각 | 소스·싱크가 **같이** 있는 조각 | 연결이 없는 설비 |
|---|---|---|---|---|
| Duplex MEP-Optimized | 690 | 34 | **0** | 224 / 926 |
| Duplex HVAC | 485 | 8 | **0** | 12 / 498 |

**하나도 없다.** 보일러·펌프가 배관망과 기하적으로 닿아 있지 않다. 플렉시블 접속부나 연결
부재가 모델에 없어서다(1차 결손). Duplex MEP 의 말단 105개는 애초에 전기·위생기구라 배관망에
있을 이유도 없다.

**결론: `brick:feeds` 를 비워 두는 판단은 유지한다.** 다만 이유가 정밀해졌다. "포트가 없어서"
가 아니라 **"포트도 없고, 소스와 싱크가 같은 연결망에 있지도 않아서"** 다. 그리고 이건 고칠
수 있는 종류의 결손이 아니다 — 고객사가 모델을 다시 그려야 한다.

## 5. 온톨로지 확장 등급 — 이 BIM 으로 어디까지 나오나

고객사 파일을 받았을 때 **"여기까지 됩니다" 를 한 줄로 말하기 위한 등급표**다.

| 등급 | 나오는 것 | 필요한 IFC 요소 | 도달한 샘플 |
|---|---|---|---|
| **0. 공간** | F1–F7. 공간 계층, 외곽선, 벽·문·창, 공간 경계 | `IfcSpace`(닫힌 FootPrint), `IfcBuildingStorey`, 벽·개구부, 배치 사슬 | AC20-FZK-Haus |
| **1. 설비 목록** | + F8·F9. 설비 종류·이름·좌표 | `IfcDistributionElement` + 배치 | Duplex MEP |
| **2. 설비 소속** | + F11. `brick:hasLocation` | **같은 파일**에 `IfcSpace` + 같은 좌표계 | Duplex MEP (167은 BIM 이 직접) |
| **3. 계통·연결망** | + F10·F16(방향 없음). 계통별 연결망, 상·하류 없는 이웃 | `IfcSystem` 또는 Revit `System Name`, **닿는 솔리드 기하** | Duplex MEP (690 연결) |
| **4. 흐름 방향** | + F16(방향 있음). `brick:feeds` | **포트 + SOURCE/SINK** (또는 소스·싱크가 한 망에) | **ifc4Mep 만** (1,995 / 1,995) |
| **5. 운영** | + F12·F13. 공조존, 관제점 | **IFC 에 없다.** IDF·gbXML·BAS 필요 | 없음 |

**대부분의 고객사 BIM 은 1~3 등급에서 멈춘다.** 4등급은 포트를 의식하고 내보낸 파일에서만
나오고, 5등급은 BIM 얘기가 아니다.

## 6. 고객사 IFC 에 반드시 필요한 것 — 지렛대 순서

없으면 무엇이 막히는지가 아니라, **하나를 고치면 등급이 몇 칸 오르는지**로 정렬했다.
협의에서 우선순위를 정하는 표다.

| 순위 | 요구 항목 | 넣으면 오르는 등급 | 넣지 않으면 |
|---|---|---|---|
| 1 | **`IfcSpace` 를 층 전체에 닫힌 경계로** | 0등급 자체가 성립 | 온톨로지의 공간 계층이 빈다. 아무것도 안 된다 |
| 2 | **건축과 설비를 같은 좌표계로** (파일이 둘이어도) | 1 → 2 | 설비가 어느 물리존인지 판정 불가. ifc4Mep 이 이 상태다 |
| 3 | **형식 IFC4** (ADD2 TC1 이상) | 1 → 2·3 | **설비 종류를 표준 필드로 알 수 없다.** IFC2x3 실측에서 확인 |
| 4 | **모든 MEP 요소에 솔리드 기하** | 3 성립 | 기하 추정이 불가능해져 연결망이 통째로 빈다 |
| 5 | **이어진 요소의 솔리드가 닿거나 겹칠 것** | 3 품질 | 연결망이 조각난다. Duplex MEP 가 34조각이다 |
| 6 | **`IfcDistributionPort` + 흐름 방향 SOURCE/SINK** | 3 → 4 | `brick:feeds` 가 통째로 빈다. 상류·하류를 못 묻는다 |
| 7 | 변마다 한쪽만 방향이 있으면 된다 | 6의 완화된 형태 | — (6을 못 맞출 때의 차선) |
| 8 | `IfcSystem` 으로 계통을 묶을 것 | 3 품질 | Revit `System Name` 으로 대체 가능. **필수는 아니다** |
| 9 | 설비 좌표 | 1 품질 | 미배치 목록으로 빠져 사람이 3D 에서 놓는다 |
| 10 | GUID 유지 설정 | 재임포트 | 같은 공간을 같은 것으로 못 알아본다 |
| 11 | 용량 파라미터 | 공조존 검증(Z-03) | **LOD 400 이야기다.** LOD 300 에는 기대하지 말 것 |
| 12 | `IfcBuildingElementProxy` 를 쓰지 말 것 | 분류 품질 | 역할·종류를 알 수 없다. ifc4Mep 에 49개 있다 |

**6번과 7번의 차이가 협의의 핵심이다.** "모든 포트에 SOURCE/SINK" 는 저작 도구가 잘 안 해
주지만, "연결마다 한쪽만" 은 훨씬 쉽다. 그리고 그것으로 충분하다 — 한쪽이 SOURCE 면 반대쪽은
SINK 일 수밖에 없다.

### 요구사항을 파일로 확인하는 방법

위 목록을 그대로 담은 IFC4 가 `src/lib/ifc/fixtures/mep.ifc` 다. 설비마다 좌표가 있고, 용량이
붙고, `IfcSystem` 으로 묶이고, 포트가 SOURCE→SINK 로 이어진다. 일부러 빠뜨린 것도 있다
(용량 없는 토출구 하나, 좌표 없는 센서 하나, `SOURCEANDSINK` 로 둔 포트 한 쌍).
**문서로 설명하는 대신 이 파일을 보내면 무엇이 되고 무엇이 안 되는지 그대로 보인다.**

다음 단계는 이 표를 `docs/requirements.ids` 로 옮기는 것이다. 그러면 고객사가 자기 도구로
검사한다. 단 IDS 는 속성만 검사하고 기하는 못 한다 — 4·5번은 여전히 우리가 열어 봐야 한다.

## 7. 재는 방법

이 문서의 숫자는 전부 `data/` 의 파일에서 다시 잴 수 있다.

```
npm run fetch:sample        # data/ 를 받는다 (gitignore 다)
npm run check:sample        # 기준값이 박힌 실측 테스트
```

A층·B층 표의 항목은 `web-ifc` 로 직접 센 것이다. 세는 축은 셋뿐이다.

- 역할별 개수 — `GetLineIDsWithType(model, IFCFLOWTERMINAL, true)` 처럼 **상속 포함**으로 조회
- 포트와 방향 — `IFCDISTRIBUTIONPORT` 의 `FlowDirection`
- 속성 — `IFCRELDEFINESBYPROPERTIES` 를 타고 Pset 이름과 속성 이름을 모은다

연결망 조각과 소스·싱크 동거 여부는 `src/lib/topology.ts` 의 `inferConnections()` 결과를
무향 그래프로 보고 연결 요소를 센 것이다.

**상속 포함(`true`)을 빠뜨리면 전부 0 이 나온다.** IFC2x3 파일에서는 구체 클래스가 없어서
추상 타입으로만 잡히고, IFC4 파일에서는 반대로 구체 클래스로만 잡힌다. 두 경우를 한 번에
세려면 상속 조회가 필수다.
